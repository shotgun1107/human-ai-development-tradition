# 중앙 인간–AI 개발 전통 시스템 v2 독립 기획·설계 시작 프롬프트

첨부된 공통 기준선과 연구 문서를 모두 읽고, 여러 프로젝트와 여러 AI 세대의 경험을 연결하는 **중앙 인간–AI 개발 전통 시스템**을 제품 기획부터 목표 시스템 설계까지 독립적으로 다시 정의하라.

이번 작업은 기존 설계의 요약·수정·확장이 아니다. 이전 설계 경쟁은 첫 검증을 작게 만드는 과정에서 중앙 시스템 전체를 작은 행동 패치 체계로 축소했다. 이번에는 다음 두 수준을 반드시 분리한다.

```text
1. 중앙 시스템이 완성됐을 때 가져야 할 전체 책임과 능력
2. 그 전체 구조를 검증하기 위한 작고 독립적인 첫 구축 범위
```

## 강제 사실과 경계

- 사용자의 목표는 개인 성장 일기가 아니라 AI 측 계승 능력과 인간–AI 공동 작업 체계의 장기 성장이다.
- 실패뿐 아니라 성공, 결정, 실험, 방향 변경, 반례, 비용, 사람 수정, AI 간 충돌을 여러 프로젝트에 걸쳐 연결해야 한다.
- 결과는 필요에 따라 사례, 판단 기준, Skill, 프롬프트, 체크리스트, 테스트, 템플릿, 행동 규칙 등 서로 다른 형태가 될 수 있다.
- 시스템은 프로젝트마다 완성본을 복사하는 도구가 아니라 여러 프로젝트를 분리·연결하는 하나의 중앙 시스템을 목표로 한다.
- 각 프로젝트에는 장기적으로 멀티 AI 오케스트레이션과 Project Brain 또는 대표 역할이 있을 가능성이 높다.
- 원천 오케스트레이터는 현재 구축·시험·비용 판단 단계다. Brain 역할, 로그, 완료 보고, 통신 형식은 아직 안정되지 않았다.
- 중앙 시스템의 내부 책임과 목표 구조는 설계하되 실제 Project Brain 메시지, API, 파일 형식, 실시간 통신 규격은 확정하지 마라.
- 중앙 전통 시스템도 오케스트레이터와 병렬적으로 기획·구축·단위 시험될 예정이다. 따라서 오케스트레이터에 종속되지 않는 첫 구현 조각을 설계하라.
- 이번 작업은 기획·설계만이다. 코드, 구현, 저장소 수정, 실제 데이터 생성은 하지 마라.
- 현재 운영 효과와 실제 통합 결과는 존재하지 않는다. 만들어내지 마라.

## 독립성 규칙

- 첨부된 공통 입력만 사용하라. 웹 검색과 추가 자료 조사를 하지 마라.
- 기존 `system-design`, 월간 플레이북, 로드맵, 행동 패치 후보 설계, 이전 Ultra/Pro 제안서, Claude/Codex/Ultra 심사 보고서는 보지 않았다고 전제하라.
- 상대 설계안을 추측하거나 모방하지 마라.
- 기존 연구 문서의 제안을 정답으로 취급하지 마라.
- 문서 상단에 실제 사용 모델·인터페이스·작성일과 확인한 입력 파일을 기록하라.

## 설계 태도

- 최소 기능 수를 목표로 하지 마라. 사용자의 최초 목적을 충족하는 전체 책임을 먼저 설계하라.
- 동시에 모든 개념을 첫 단계부터 별도 서비스·DB·파일로 구현하도록 요구하지 마라.
- 전체 구조와 첫 구현 범위를 혼동하지 마라.
- 행동 패치를 유용한 구성요소로 제안할 수 있지만 그것만으로 중앙 시스템 전체를 대체하지 마라.
- `사실 → 경험 → 교훈 → 교리` 같은 고정 수명주기를 그대로 받아들일 필요는 없다. 유지·분기·대체할 수 있지만, 사실에서 작업 자산과 적용 결과까지의 계보는 잃지 마라.
- 자동화를 기본으로 생각하되, 사람이 모든 기록을 수작업으로 관리하거나 반대로 AI가 공통 규칙을 자동 승인하는 양극단을 피하라.
- 설계 복잡성을 줄일 때 어떤 사용자 목적을 잃는지 명시하라.
- 중앙집중 때문에 모든 프로젝트가 같은 방식으로 굳고 탐색이 줄어드는 위험을 다뤄라.

## 반드시 수행할 작업

1. 첨부 파일을 모두 확인하고 현재 상태와 고정된 사용자 목적을 짧게 재구성하라.
2. 중앙 시스템 전체에 대해 최소 3개의 서로 다른 구조 대안을 제시하라.
3. 각 대안을 목적 충족, 장기 계승, 프로젝트 분리, 자동화, 검증 가능성, 비용, 확장 위험으로 비교하라.
4. 하나의 주설계를 선택하되 선택하지 않은 대안에서 유지할 가치가 있는 요소를 설명하라.
5. `central-system-v2-design-brief.md`의 필수 사용 상황 10개를 선택한 구조에 실제로 통과시켜라.
6. 확인된 사실, 연구에서 가져온 근거, 설계자의 추론, 아직 검증되지 않은 제안을 구분하라.
7. 핵심 결정마다 반증 또는 재검토 조건을 붙여라.
8. 목표 제품, 단계적 구축, 첫 독립 구현 조각을 별도 장으로 분리하라.
9. 단위 시험, 가상 프로젝트 흐름 시험, 향후 실제 효과 시험이 각각 무엇을 증명하고 무엇을 증명하지 못하는지 구분하라.
10. Project Brain 통신 방식과 현재 정할 수 없는 수치·기술은 미결정으로 남겨라.
