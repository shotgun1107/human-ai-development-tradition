# 중앙 인간–AI 개발 전통 시스템 v2: 독립 기획·설계 공통 브리프

> 버전: 2.0.0-design-brief  
> 기준일: 2026-08-05  
> 상태: 독립 기획·설계 경쟁용 공통 문제 정의  
> 범위: 제품 기획과 전체 시스템 설계  
> 금지: 구현, 코드, 저장소 구조 확정, 실제 Project Brain 통신 규격 확정

## 0. 이 브리프가 필요한 이유

이전 설계 경쟁은 검증 가능성, 1인 운영비용, 잘못된 교훈의 고착 방지를 강화했다. 그 결과 `행동 패치`와 작은 시험 체계는 정교해졌지만, 사용자가 처음 원한 **여러 프로젝트와 여러 AI 세대의 경험을 연결하는 중앙 전통 시스템 전체**가 하나의 작은 규칙 엔진으로 축소됐다.

이번 과업은 이전 안을 확장하거나 고치는 일이 아니다. 사용자의 최초 목적과 새로 확인된 중앙 시스템 전제를 기준으로 **제품 기획부터 목표 구조까지 다시 정의**하는 독립 설계다.

중요한 구분은 다음과 같다.

```text
전체 완성 구조를 충분히 설계한다.
+
첫 구현 범위는 작고 검증 가능하게 정한다.
```

`처음 작게 만든다`는 이유로 `최종 시스템의 책임과 능력`까지 삭제하면 안 된다. 반대로 전체 구조를 설계한다는 이유로 모든 기능을 첫 구현에 넣어서도 안 된다.

## 1. 사용자에게서 확정된 목적

다음은 설계자가 임의로 축소할 수 없는 상위 목적이다.

1. 사용자의 개인 성장 일지가 아니라 **AI 측 계승 능력과 인간–AI 공동 작업 체계의 성장**을 우선한다.
2. 더 좋은 모델이 나와도 같은 실수와 시행착오가 반복되는 문제를 줄인다.
3. 외주, 공모전, 자체 개발 등 여러 실제 프로젝트의 경험을 장기간 연결한다.
4. 실패와 오류뿐 아니라 성공, 중요한 결정, 실험, 방향 변경, 반례, 비용, 사람의 수정, AI 간 충돌도 다룬다.
5. 경험은 필요에 따라 사례, 판단 기준, Skill, 프롬프트, 체크리스트, 테스트, 템플릿, 행동 규칙 등 서로 다른 형태로 이어질 수 있다.
6. 모델·도구·오케스트레이션이 바뀌어도 유효한 작업방식을 다시 시험하고 계승한다.
7. 인간과 여러 세대 AI가 반복해서 보여주는 품질, 검증, 책임, 수정 방식의 계보를 공동 브랜드로 만든다.
8. 잘못된 경험과 규칙은 격리, 범위 축소, 수정, 폐기할 수 있어야 한다.
9. 자동화 수준을 높이되 인간은 가치, 위험, 비밀, 외부 공개, 중요한 승격·폐기의 책임을 가진다.
10. 토큰, 현금, 사람 능동시간, 재작업, 대기, 기회비용을 숨기지 않는다.

## 2. 새로 확정된 배치 전제

이 시스템은 프로젝트마다 완성본을 복사해 독립 운용하는 도구가 아니다.

> **여러 프로젝트의 경험과 작업 자산을 분리해서 보존하고, 필요할 때 연결·비교·재사용하는 하나의 중앙 시스템을 목표로 한다.**

각 프로젝트에는 장기적으로 멀티 AI 오케스트레이션과 이를 조정하는 `Project Brain` 또는 이에 준하는 대표 역할이 존재할 가능성이 높다. 그러나 원천 오케스트레이터는 현재 구축·시험·비용 판단 단계이며, Brain 역할·완료 보고·로그·통신 형식은 아직 안정되지 않았다.

따라서 이번 설계는 다음을 지켜야 한다.

- 중앙 시스템이 무엇을 책임지는지와 내부적으로 어떤 능력이 필요한지는 설계한다.
- 프로젝트별 분리, 여러 프로젝트의 비교, 공통 지식의 생성·배포·철회 책임은 설계한다.
- Project Brain과 중앙의 의미상 경계는 제안할 수 있다.
- 실제 메시지 형식, API, 파일 구조, 실시간 통신 순서, 오케스트레이터 내부 변경은 확정하지 않는다.
- 미래 통신 방식이 바뀌어도 중앙 내부 핵심이 유지될 수 있는 경계를 제안한다.

## 3. 현재 병렬 개발 상황

두 프로젝트는 서로 기다리지 않고 병렬적으로 발전한다.

### 원천 멀티 오케스트레이션

- 역할 구조, Brain, 병렬 작업, 결과 합성 방식 기획·구축·시험
- 단일 AI 대비 품질·속도·비용·충돌·사람 수정 측정
- 여러 실제 프로젝트에서 지속 가능한지 판단

### 중앙 전통 시스템

- 중앙 제품 기획과 목표 구조 설계
- 오케스트레이터에 종속되지 않는 내부 핵심의 단계적 기획·구현·단위 시험 가능성 제시
- 가상 프로젝트나 중립 입력으로 시험할 수 있는 첫 조각 정의
- 실제 Project Brain 연결은 경계가 안정된 뒤 별도 설계

중앙 전통 시스템이 병렬 개발된다는 이유로 미완성 오케스트레이터의 현재 형식을 영구 계약으로 고정하면 안 된다.

## 4. 중앙 시스템이 반드시 다뤄야 할 범위

설계는 적어도 다음 질문에 완결된 답을 제공해야 한다.

### 4.1 프로젝트와 실행 계보

- 프로젝트, 작업, 개별 실행, 결과물, 모델, 도구, AI 역할, 사람 승인 사이의 관계를 어떻게 표현하는가?
- 서로 비슷한 이름의 프로젝트와 작업을 어떻게 분리하는가?
- 한 프로젝트의 여러 시도와 방향 변경을 어떻게 연결하는가?
- 모델·도구·오케스트레이션 구성이 달라졌을 때 과거 결과를 어떻게 해석하는가?

### 4.2 경험의 폭

- 성공, 실패, 사건, 중요한 결정, 실험, 근접 실패, 반례, 외부 평가, 사람 수정, 비용을 어떻게 다루는가?
- 당장 행동 규칙이 되지 않는 경험도 나중의 비교와 브랜드 계보에 사용할 수 있는가?
- 우연한 성공과 재현 가능한 작업방식을 어떻게 구분하려 하는가?

### 4.3 프로젝트별 지식과 공통 지식

- 개별 프로젝트에서 나온 경험은 어디까지 그 프로젝트에만 남는가?
- 특정 종류의 프로젝트에 공통인 지식과 전체 공통 지식을 어떻게 구분하는가?
- 공통화가 더 높은 권위나 자동 적용을 뜻하지 않도록 어떻게 막는가?
- 다른 프로젝트·모델로 옮길 때 무엇을 다시 시험하는가?

### 4.4 여러 프로젝트의 비교와 학습

- 서로 다른 프로젝트의 비슷한 사건과 성공을 어떻게 발견·비교하는가?
- 같은 원자료를 여러 AI가 요약한 것을 독립 증거로 잘못 세지 않는가?
- 모순되는 경험을 투표나 최신순으로 덮지 않고 어떻게 보존·판정하는가?
- 중앙집중이 모든 프로젝트를 같은 방식으로 만들어 탐색과 다양성을 해치지 않도록 어떻게 하는가?

### 4.5 실행 가능한 작업 자산

- 경험이 언제 사례로 남고, 언제 판단 기준·Skill·프롬프트·체크리스트·테스트·템플릿·행동 패치가 되는가?
- 하나의 고정된 정제 사다리를 강제하지 않으면서도, 사실에서 실행 자산까지의 계보를 어떻게 잃지 않는가?
- 자산의 적용 조건, 금지 조건, 판본, 근거, 반례, 결과를 어떻게 연결하는가?
- 프로젝트에 이미 더 좋은 native test·체크리스트가 있다면 중앙 자산을 중복 생성하지 않는가?

### 4.6 검색·선택·전달

- 중앙에 많은 기록과 자산이 있어도 현재 프로젝트에 필요한 것만 어떻게 선택하는가?
- 프로젝트의 Brain 또는 대표 AI가 무엇을 요청하고 무엇을 돌려받는지는 의미상 어떻게 구분되는가?
- 중앙의 모든 과거를 컨텍스트에 넣지 않고도 필요한 근거와 행동을 전달할 수 있는가?
- 오래되거나 철회된 자산이 다시 전달되는 것을 어떻게 막는가?

### 4.7 피드백과 수정

- 프로젝트가 중앙 자산을 사용·거부·변형·오적용했을 때 결과가 중앙으로 어떻게 돌아오는가?
- 검색 실패, 채택 실패, 실행 실패, 자산 자체의 실패를 어떻게 구분하는가?
- 중대한 음의 전이, 비밀 문제, 품질 회귀가 생겼을 때 얼마나 빨리 중지할 수 있는가?
- 규칙과 자산이 폐기돼도 원래 프로젝트·결정·결과의 계보는 어떻게 남는가? 단, 삭제 의무는 어떻게 우선하는가?

### 4.8 정기적 학습과 지속적 학습

- 작업 직후의 자동 처리와 월간·정기 종합은 각각 무엇을 하는가?
- 월간 학습이 문서 생산 할당량이나 형식적 회의가 되지 않도록 어떻게 하는가?
- 여러 프로젝트를 가로지르는 패턴, 모순, 사용되지 않는 자산, 비용 악화를 어떻게 정기적으로 확인하는가?
- 변경할 근거가 없을 때 `변경 없음`을 정상 결과로 허용하는가?

### 4.9 자동화와 사람 책임

- 자동 수집, 분류, 요약, 비교, 후보 생성, 검색, 적용, 결과 측정 중 무엇을 AI가 맡는가?
- 사람이 매번 모든 기록을 읽지 않으면서도 중요한 승인과 책임을 유지할 수 있는가?
- 인간 관리시간은 고정 의례가 아니라 자동화의 순가치를 판단하는 지표로 사용되는가?
- 어떤 판단은 사람 승인 없이는 절대 활성화·외부 공개할 수 없는가?

### 4.10 공동 브랜드

- 공동 브랜드를 홍보문구나 특정 모델 이름이 아니라 어떤 관찰 가능한 계보로 표현하는가?
- 프로젝트별 성과, AI 기여, 사람 결정, 검증, 비용, 철회와 수정이 어떻게 장기 변화로 연결되는가?
- 성공 사례만 편집하거나 AI의 기여를 과장하는 것을 어떻게 막는가?
- 외부 공개용 이야기와 내부 근거의 차이를 어떻게 관리하는가?

## 5. 반드시 분리해야 할 세 수준

설계는 다음 세 수준을 혼동하면 안 된다.

### 5.1 목표 제품

여러 프로젝트와 모델 세대가 실제로 연결됐을 때 중앙 시스템이 가져야 할 전체 책임과 능력이다.

### 5.2 단계적 구축

목표 제품을 어떤 순서로 검증하고 확장할지에 대한 로드맵이다. 각 단계에는 시작 조건, 산출물, 실패·중단 조건, 다음 단계 조건이 필요하다.

### 5.3 첫 번째 독립 구현 조각

Project Brain의 실제 통신 형식 없이도 가상 프로젝트나 중립 입력으로 구현·단위 시험할 수 있는 가장 작은 세로 한 바퀴다. 이번 과업에서는 **설계만** 하며 구현하지 않는다.

첫 조각이 작다고 목표 제품을 그 크기로 축소하지 않는다. 목표 제품이 크다고 첫 조각에 모든 객체·서비스·화면을 넣지 않는다.

## 7. 설계 자유와 금지되는 축소

설계자는 기존의 `사실 → 경험 → 교훈 → 교리 → 산출물` 수명주기를 유지, 수정, 분기 또는 거부할 수 있다. 행동 패치도 유지하거나 다른 구성요소로 대체할 수 있다.

그러나 다음과 같은 축소는 완결된 중앙 시스템 설계로 인정하지 않는다.

- 행동 패치·체크리스트 저장소만 제안하고 프로젝트·실행·결정·실험·모델 계보를 다루지 않음
- 첫 구현이 작다는 이유로 장기 목표 제품의 책임을 정의하지 않음
- 모든 경험을 즉시 규칙으로 바꾸거나, 규칙이 되지 않는 경험을 가치 없음으로 처리함
- 중앙 시스템이라고 하면서 프로젝트별 분리·공통화·철회·배포·피드백을 설계하지 않음
- 비용을 줄인다는 이유로 공동 브랜드와 장기 계보 목적을 삭제함
- 반대로 개념상 구분한 모든 정보를 별도 서비스·DB·파일로 첫 단계부터 구현하도록 요구함

## 8. 필수 사용 상황

제안서는 최소한 다음 상황을 자신의 설계에 끝까지 통과시켜야 한다.

1. 프로젝트 하나가 완료되고 성공·실패·결정·비용·AI 기여가 들어온다.
2. 성공했지만 원인이 불분명하고, 다음 행동 규칙으로 만들지 여부를 판단한다.
3. 세 프로젝트에서 비슷한 실패가 나타나지만 모델·도구·조건이 다르다.
4. 기존 공통 원칙과 반대되는 결과가 한 프로젝트에서 나온다.
5. 새 모델로 교체되며 기존 Skill과 프롬프트가 여전히 필요한지 모른다.
6. 프로젝트 전용 지식을 다른 프로젝트가 요청한다.
7. 근거가 삭제·철회되거나 비밀정보 문제가 발견된다.
8. 중앙 자산을 프로젝트가 거부·변형·오적용한다.
9. 사용자가 지난 기간의 반복 패턴, 실제 재사용, 비용 변화, 작업방식 변화를 질문한다.
10. 월간 종합 시 변경할 충분한 근거가 없다.

각 상황에서 입력, 중앙 판단, AI 역할, 사람 승인, 결과, 실패·복구 경로를 설명해야 한다. 실제 통신 기술은 정하지 않는다.

## 10. 품질 기준

좋은 제안은 다음을 만족한다.

- 중앙 시스템 전체를 설명하지만 첫 구현을 과대하게 만들지 않는다.
- 특정 저장 기술이나 모델을 전체 구조와 혼동하지 않는다.
- 개념을 많이 나열하는 데 그치지 않고 관계와 사용 흐름을 설명한다.
- 실제 사용 상황에서 어떤 정보가 왜 필요한지 보여준다.
- 자동화를 전제로 하되 자동화된 잘못된 학습의 위험을 다룬다.
- 1인 소유자의 책임을 인정하되 사람이 모든 기록을 수작업으로 관리하게 만들지 않는다.
- 모델 자체 향상, 사용자 숙련, 도구 변화, 전통 효과를 구분할 수 없을 때 주장 강도를 낮춘다.
- 기존 연구의 확인된 사실, 추론, 설계 제안을 구분한다.
- 거대한 완성품을 한 번에 구현하지 않고도 핵심 전체 순환을 시험할 수 있다.

## 11. 치명적 결격 조건

다음 중 하나면 총점과 무관하게 불완전 설계다.

- 구현 또는 코드를 작성함
- 중앙 시스템의 목표 제품을 작은 행동 패치 저장소로 축소함
- 반대로 첫 구현에 전체 플랫폼을 요구함
- 프로젝트별 비밀·권한·지식 분리를 다루지 않음
- 성공·결정·실험을 제외하고 실패만 다룸
- 모델·도구·프로젝트 범위를 무시하고 경험을 자동 일반화함
- Project Brain의 실제 인터페이스가 이미 확정됐다고 꾸밈
- 현재 오케스트레이터가 안정적으로 운영된다는 허위 전제를 사용함
- AI 합의나 자기평가를 독립 증거로 간주함
- 사람 승인 없이 공통 규칙·외부 공개·고위험 적용을 자동화함
- 현재 존재하지 않는 운영 결과나 효과를 만들어냄

## 12. 이번 과업의 완료 조건

완료란 중앙 시스템을 구현하는 것이 아니다. 다음이 한 문서 안에서 서로 모순 없이 연결된 상태다.

- 최초 목적
- 중앙 시스템 전체 책임
- 여러 프로젝트와 모델 세대의 장기 관계
- 다양한 경험과 작업 자산
- 자동화와 사람 책임
- 검증·수정·폐기
- 전체 목표 구조
- 독립적인 첫 구현 조각
- 단계적 로드맵
- 미정으로 남길 Project Brain 통신과 기타 불확실성

최종 설계의 크기는 기능 수가 아니라 사용자의 최초 목적을 얼마나 잃지 않고, 작은 구현으로 얼마나 정직하게 검증할 수 있는지로 판단한다.
