## 0. 설계 요약

### 한 문장 설계

전통을 경험 창고나 교리 계층으로 만들지 않고, **현재 과제의 행동을 작게 바꾸는 조건부 지시와 그 효과를 판정할 검사를 한 장에 묶은 소수의 “작업 패치”**로 운영한다.

### 핵심 판단

개인용 시스템의 가장 큰 위험은 경험을 잊는 것만이 아니다. 검증되지 않은 설명을 정제 과정에서 권위화하고, 관련 없는 과제에 주입하며, 이를 관리하느라 실제 작업을 방해하는 것도 같은 크기의 위험이다. 따라서 이 설계는 `사실 → 경험 → 교훈 → 교리 → 산출물`이라는 다단계 정제를 기본 경로로 채택하지 않는다.

대신 원자료는 원래 위치에 두고, 반복 가능성과 검증 가능성이 있는 경우에만 다음을 하나의 실행 단위로 만든다.

```text
적용 조건(IF)
+ 바꿀 행동(DO)
+ 쓰지 않을 조건(DO NOT)
+ 판정 검사(VERIFY)
+ 즉시 중지 조건(STOP)
+ 지지·반대 근거 포인터
= 증거 부착 작업 패치
```

전통의 성장은 패치 수가 아니라, 새 세션이나 새 모델이 이 패치로 **현재 최선의 작업방식보다 순이익을 내고 중대한 회귀를 만들지 않았는가**로 판단한다.

### 기존 초안과 가장 크게 다른 선택 5개

1. 경험·교훈·교리·산출물을 별도 영구 객체로 만들지 않고, 검증 가능한 행동 변화인 `작업 패치` 하나로 압축한다.
2. 월간 회고를 기본 의례로 두지 않고, 적용 결과가 쌓였거나 모순·변경이 생겼을 때만 여는 **증거량 기반 검토**로 바꾼다.
3. 범용 교리로 “승격”하지 않는다. 프로젝트 패치에서 공통 핵심을 **새로 분기**하고, 새 프로젝트에서는 다시 시험한다.
4. RAG나 원로그 자동 주입을 초기 경로에서 제외한다. 승인된 소수 패치를 정확한 조건 필터로만 제안한다.
5. 시스템 전체에 명시적 비용 상한과 폐기 시험을 둔다. 이득이 없으면 프로젝트 고유 테스트·체크리스트만 남기고 전통 계층을 없앤다.

### 가장 큰 비용·위험·미확인 가정

- 짧은 패치가 복잡한 맥락을 지나치게 압축해 유용한 예외를 잃을 수 있다.
- 적용 조건을 사람이 잘못 붙이면 정확 검색도 정확한 오적용을 만들 수 있다.
- 한 사람의 반복 과제는 표본이 작고 학습·모델·도구 변화가 얽혀 있어 인과 효과를 강하게 추정하기 어렵다.
- 패치를 만들고 검토하는 비용이 재작업 절감보다 클 수 있다.
- 공동 브랜드가 고객 신뢰나 수익으로 이어지는지는 현재 증거가 없다.

## 1. 문제 정의와 비목표

### 1.1 해결할 문제

이 체계의 사용자는 한 명의 인간 운영자와 매번 달라질 수 있는 AI 구성이다. 직접 수혜자는 실제 프로젝트의 사용자·고객이며, 최종 승인과 외부 책임은 인간에게 있다. 해결하려는 문제는 다섯 가지다.

1. **연속성:** 세션·모델·도구가 바뀌면 검증된 작업방식이 사라진다.
2. **선택:** 기억이 있어도 현재 과제에 맞는 항목을 고르지 못하면 무용하거나 해롭다.
3. **검증:** 좋은 설명과 실제로 더 나은 행동을 구분하기 어렵다.
4. **경제성:** 기록·검색·회고가 실제 프로젝트보다 무거워질 수 있다.
5. **공동 정체성:** 특정 모델의 인격이 아니라, 인간과 여러 AI가 함께 지키는 품질·검증·책임 방식의 계보를 보여줘야 한다.

따라서 문제를 “경험을 얼마나 잘 보존할 것인가”가 아니라 다음과 같이 다시 정의한다.

> 과거의 어떤 작은 행동 변화가 현재 최선의 작업방식에 추가 이득을 주는지, 최소 비용으로 선택·적용·반증하고 다음 AI에게 넘길 수 있는가?

### 1.2 성장으로 계산하는 것과 계산하지 않는 것

성장으로 계산하는 것은 새 세션·새 모델·새 프로젝트에서 관찰되는 다음 변화다.

- 중대한 반복 오류 감소
- 객관적 인수 기준이나 테스트 품질 향상
- 같은 품질을 위한 인간 능동시간·재작업·토큰·현금 감소
- 잘못된 과거 규칙의 더 빠른 거부
- 사실·추론·불확실성·AI 기여·인간 승인의 일관된 표현

다음은 단독으로 성장 증거가 아니다.

- 문서·패치·회고 수 증가
- AI의 자신감이나 자기평가
- 사용자의 “빨라진 느낌”
- 새 모델 자체의 성능 향상
- 사용자의 숙련 향상
- 고객 결과가 좋아진 단일 사례
- 공동 브랜드에 관한 홍보문구

### 1.3 비목표

- 모델 가중치 업데이트와 파인튜닝
- AI 인격·의식·동일성의 보존 또는 주장
- 사용자의 개인 성장 일지나 자기계발 점수
- 모든 대화·로그·고객 자료의 영구 보관
- 오류 중심 incident 데이터베이스의 확장
- 범용 교리집, 지식 그래프, 온톨로지의 구축
- 에이전트 수·역할 수·자동화율의 극대화
- 고객 납품을 열등할 수 있는 조건에 배정하는 실험
- 공동 브랜드를 특정 모델명이나 의인화된 서사로 만드는 일
- 현재 원천 오케스트레이터의 구현·성능·운영 효과 판정

### 1.4 현재 상태 경계

원천 AI 오케스트레이터는 별도 저장소에서 구축·테스트 중이다. 일부 구성요소와 smoke test가 있으나 전체가 안정적으로 운영되는 상태가 아니며, 현재 개발 incident는 이 전통 시스템의 운영 효과를 증명하지 않는다. 이 문서는 연구·기획·시스템 설계만 다루고 T0 결과를 가정하지 않는다.

## 2. 핵심 철학의 독립적 해석

### 2.1 “AI의 성장”은 계승 가능한 행동 차이다

이 설계는 AI 성장의 단위를 모델도, 문서도, 인간의 회상도 아닌 **재현 가능한 행동 차이**로 본다. 새 AI가 과거 문장을 아는 것보다, 관련 조건에서 더 나은 행동을 선택하고 검사를 수행하며 틀린 기억을 거부하는 것이 중요하다.

외부 기억은 성장 그 자체가 아니라 행동 차이를 운반하는 매체다. 패치를 주입했지만 행동·결과가 달라지지 않았다면 계승은 일어나지 않은 것이다.

### 2.2 공동 브랜드는 “검증 영수증의 계보”다

공동 브랜드는 AI에게 이름이나 인격을 붙이는 일이 아니다. 다음 흔적이 여러 프로젝트와 모델에서 반복될 때 생긴다.

- 출처와 불확실성을 숨기지 않는다.
- 결과를 테스트하거나 인수 조건으로 확인한다.
- 고객 가치·비밀·권리를 내부 학습보다 앞에 둔다.
- AI가 만든 부분과 인간이 승인한 범위를 구분한다.
- 틀린 패치를 조용히 덮지 않고 중지·수정 이유를 남긴다.

이를 별도 “브랜드 기억” 객체로 만들 필요는 없다. 패치의 계보와 적용 영수증, 결과물의 검증 흔적이 브랜드의 증거다. 외부 공개는 고객 동의와 비밀 경계를 통과한 경우에만 한다.

### 2.3 규범과 경험 규칙을 분리한다

고객 비밀 보호, 열등할 수 있는 실험의 무단 배정 금지, 인간 최종 승인 같은 규범은 성능 실험에서 승패를 겨루는 교리가 아니다. 반면 특정 체크리스트나 프롬프트가 시간을 줄인다는 주장은 경험적으로 반증돼야 한다.

이 둘을 한 증거 등급 체계에 넣으면 “증거가 적으니 비밀 보호를 trial로 둔다”거나 “안전 규범이니 모든 작업 패치도 강제한다”는 오류가 생긴다. 따라서 다음 두 층을 분리한다.

- **보호 규범:** 인간이 소유하는 짧은 불가침 경계. 법·계약·안전·비밀·책임을 다룬다.
- **경험 패치:** 품질·시간·비용·위험을 바꿀 수 있다는 가설. 범위와 검사가 붙고 언제든 중지될 수 있다.

### 2.4 보존보다 선택적 망각이 기본값이다

전통은 모든 경험을 보존해서 생기지 않는다. 반복 가능성, 행동 변화, 검증 가능성, 안전한 비식별화가 모두 없는 경험은 전통으로 만들지 않는다. 원자료가 법적·업무상 보존될 이유가 있으면 원래 시스템의 정책에 따르되, 전통 저장소가 별도 사본을 만들지 않는다.

### 2.5 헌장에 대한 이의와 해석

목적·철학 헌장의 핵심 목적과 가치 우선순위에는 이의를 제기하지 않는다. 다만 “검증된 경험을 모델 밖에 보존한다”는 문장을 **검증된 경험마다 별도 기억 객체를 만든다**는 뜻으로 읽는 것은 비용 원칙과 잊을 권리와 충돌한다고 본다. 이 설계는 보존 단위를 경험 서술이 아니라 검증된 행동 패치와 최소 근거 포인터로 좁혀 해석한다.

## 3. 기준선 전제의 유지·거부·조건부 수용

| 사람만 활성화·범위 확대·재활성화 가능 | 유지 | AI는 제안·검색·비평·긴급 보류 요청만 한다. |

| Experience/Lesson/Doctrine/Application/Evaluation/Review 별도 객체 | 거부 | T0에는 과도하다. 패치 카드와 사용 영수증 두 종류로 충분한지 먼저 시험한다. |
| E0~E4 같은 단일 증거 사다리 | 거부 | 사실 확인과 효과, 증거 확실성과 행동 강도를 한 축으로 오해하게 한다. 근거 서술과 적용 모드를 분리한다. |
| 매월 60~90분 회고 | 거부 | 자료가 없는데도 의례와 산출물 압력을 만든다. 증거·모순·변경 사건으로 검토를 연다. |
| 모든 교리를 체크리스트·프롬프트·테스트 등 새 산출물로 변환 | 조건부 | 이미 프로젝트 테스트·runbook에 표현돼 있으면 새 사본을 만들지 않고 링크한다. |
| 범용 active 교리 계층 | 거부 | 범용성은 영구 지위가 아니라 새 맥락에서 반복해서 확인할 가설이다. 공통 패치를 새로 분기한다. |
| exact/keyword 검색 우선 | 조건부 유지 | 실제 패치 수와 검색 누락이 생긴 뒤 도입한다. T0는 수작업 선택도 가능하다. |
| 의미 검색·RAG | 보류 | exact 기준선의 측정된 실패와 안전한 삭제·권한 통제가 먼저다. |
| 모델 중립 핵심과 모델별 어댑터 | 조건부 | 실제 이주에서 표현 차이가 반복될 때만 분리한다. 미리 프레임워크를 만들지 않는다. |
| 파인튜닝 | 폐기(현 범위) | 작고 편향된 개인 데이터에서 삭제·롤백·출처 추적이 더 어렵다. 장기 연구 게이트조차 별도 제안으로 다룬다. |

## 4. 주요 결정의 근거·추론·제안·반증

| 결정 | 근거 | 추론 | 제안 | 반증 조건 |
|---|---|---|---|---|
| D1. 다단계 정제 대신 작업 패치 | 조사 문서들은 기록이 실제 행동으로 이어지지 않는 실패와 외부 기억의 음의 전이를 함께 경고한다. | 객체를 늘리면 계보는 풍부해지지만 1인 유지비와 맥락 손실도 늘어난다. | 조건·행동·검사·중지·근거를 한 카드로 묶는다. | 원로그 또는 다단계 선례가 패치보다 반복적으로 더 정확하고 예외 손실이 적으며 순비용도 낮다. |
| D2. 월간 회고 대신 증거량 기반 검토 | 최적 월간 주기에 대한 직접 증거가 없고, “승격 없음”이 정상일 수 있다. | 달력은 표본과 무관해 억지 정제를 유도한다. | 적용 영수증 축적, 모순, 위험, 모델·도구 변경 때만 검토한다. | 사건 기반 운영이 중요한 항목을 계속 놓치거나 오래된 패치가 방치되고, 짧은 정기 검토가 순이익을 낸다. |
| D3. 프로젝트 전용 기본값 | 전이 문헌은 near/far/migration을 구분하며 과거 기억의 음의 전이를 경고한다. | 한 프로젝트의 성공은 다른 맥락의 권위가 아니다. | 공통화는 승격이 아니라 새 패치 분기와 재시험으로 한다. | 프로젝트별 중복 관리비가 크고, 공통 패치가 여러 맥락에서 오적용 없이 안정적 이득을 낸다. |
| D4. 패치와 검사를 한 단위로 관리 | 체크리스트·Skill의 존재·사용과 효과는 다르다. | 행동 지시와 판정 기준이 떨어지면 형식적 준수가 생긴다. | 모든 경험 패치는 `VERIFY`와 `STOP`을 가져야 한다. | 검사 정의가 불가능한 고가치 지식이 반복적으로 유용하고, 독립 검토만으로 안전하게 관리된다. |
| D5. 승인된 패치만 소수 주입 | 긴 컨텍스트·오검색·프롬프트 주입·지속 오염 위험이 있다. | 원자료 자동 주입은 정보량과 공격면을 동시에 키운다. | 정확 조건 필터 후 최대 소수 패치만 “증거 기반 제안”으로 주입한다. | 소수 제한 때문에 중요한 recall 손실이 반복되고, 더 넓은 검색이 guardrail 내에서 순성과를 높인다. |
| D6. 보호 규범과 경험 규칙 분리 | 증거 확실성과 권고 강도는 다른 축이며 고객 의무는 실험 대상이 아니다. | 하나의 상태·등급은 안전 규범과 효율 가설을 혼동시킨다. | 1쪽 보호 규범과 가역적 경험 패치를 별도 관리한다. | 분리로 충돌·누락이 늘고 단일 체계가 더 명확하게 책임과 적용을 관리한다. |
| D7. 현재 최선 workflow를 T0 대조군으로 사용 | 고객 과제에 열등 조건을 배정할 수 없고 현재 오케스트레이터 효과도 미확인이다. | 의도적으로 약한 대조군을 이겨도 가치가 없다. | 안전한 내부 과제에서 현재 최선 workflow 대 `+패치`를 비교한다. | 과제 간 변동 때문에 비교가 불가능하거나 오염이 심해 의미 있는 판정을 못 한다. |
| D8. 시스템 자체의 폐기 게이트 | 개선 체계도 비용을 정당화해야 하며 NASA 사례는 저장소 비활용 위험을 보여준다. | 전통을 유지하는 행위가 목적이 되기 쉽다. | T0와 사전등록된 재검증 뒤 순이익이 없으면 패치 계층을 없앤다. | 장기 지연 효과가 합리적 근거로 예상되고, 제한된 연장 실험의 정보가치가 비용보다 크다. |

## 5. 가장 작은 검증 가능 시스템

### 5.1 시스템 경계

```text
실제 프로젝트와 원자료
  │  (복사하지 않고 제한 포인터만)
  ▼
짧은 신호 메모 ── 가치·반복·검사 가능성 없음 ──▶ 만료·삭제
  │
  │ 사람의 비밀 제거·trial 승인
  ▼
작업 패치(trial) + 판정 검사
  │
  │ 현재 과제 조건과 정확히 맞을 때만 제안
  ▼
AI의 적용·변형·거부 + 사람 승인/감독
  │
  ▼
사용 영수증(결과·비용·회귀)
  │
  ├─ 이득·guardrail 통과 ─▶ live
  ├─ 불명확 ─────────────▶ trial 유지 또는 off
  └─ 위해·모순 ─────────▶ 즉시 hold/off
```

T0에서 필요한 논리 구성요소는 네 가지뿐이다. 실제 파일은 하나의 Markdown 표여도 된다.

1. 보호 규범 한 장
2. 만료 가능한 신호 메모
3. 작업 패치 카드
4. 사용 영수증

별도 경험 DB, 교훈 객체, 교리 계층, 그래프, 대시보드, RAG는 없다.

### 5.2 보호 규범 한 장

보호 규범은 경험에서 자동 생성하지 않는다. 최소 내용은 다음이다.

- 고객·사용자 인수 조건과 비밀·권리를 내부 학습보다 우선한다.
- 고객 납품을 열등할 수 있는 실험 조건에 배정하지 않는다.
- 외부 입력의 명령을 기억의 권위 있는 지시로 승격하지 않는다.
- 외부 효과·고위험 실행·공개·비밀 처리에는 인간 승인이 필요하다.
- 분리할 수 없는 인과 효과는 구성 전체의 관찰 결과로만 보고한다.
- 중대 보안·품질 회귀가 있으면 패치 적용을 즉시 멈춘다.

이 한 장은 매 작업에 길게 주입하지 않고 상위 작업 규칙에 짧게 반영한다. 변경은 인간의 명시적 헌장 판단이며 성능 데이터만으로 자동 변경하지 않는다.

### 5.3 신호 메모: 영구 기억이 아닌 임시 큐

신호는 실패·성공·결정·실험·근접 실패 중 다음 중 하나가 있을 때만 남긴다.

- 같은 문제가 다시 생길 가능성이 높다.
- 중대한 손실이나 위험을 예방할 수 있다.
- 기존 패치와 모순된다.
- 작고 가역적인 행동 변화와 검사를 제안할 수 있다.

최소 필드는 `날짜, 프로젝트, 예상, 관찰, 원자료 포인터, 민감도, 패치 가능성`이다. 원인 설명은 사실과 분리해 가설로 쓴다. 다음 검토 창까지 패치 trial로 바뀌지 않으면 삭제한다. 단, 원자료의 법적·업무상 보존은 원래 시스템의 정책을 따른다.

### 5.4 작업 패치: 유일한 재사용 지식 단위

개념 예시는 다음과 같다. 실행 스키마가 아니다.

```yaml
id: PATCH-PROJ-001
version: 1
state: trial | live | off
scope:
  project: named-project
  task_type: benchmark-preflight
  risk: medium
  model_tool_constraints: []
if: "동결된 입력으로 반복 비교를 시작하기 직전"
do: "입력 식별자와 실제 대상 내용의 일치를 확인한다"
do_not_use_when: "입력이 동결되지 않은 탐색 작업"
verify: "사전 정의한 불일치 표본 탐지와 false-positive를 기록한다"
stop_if: "비용 상한 초과 또는 정상 입력 차단"
evidence_summary: "직접 관찰 1건; 효과 비교는 아직 없음"
source_refs: [redacted-pointer-with-integrity]
counterevidence_refs: []
action_mode: experiment | suggest | require
configuration_fingerprint: "model/tool/prompt versions if relevant"
owner: human
recheck_triggers: [model-change, tool-change, contradiction]
replacement: null
```

핵심 원칙은 다음과 같다.

- `evidence_summary`는 숫자 등급이 아니라 무엇을 직접 봤고 무엇을 아직 모르는지 쓴다.
- `action_mode`는 증거와 별개다. 저비용 보안 차단은 근거가 적어도 `require`일 수 있고, 평균 이득이 있어도 비싼 절차는 `suggest`일 수 있다.
- `VERIFY`가 없는 항목은 작업 패치가 아니라 참고 메모다. 참고 메모는 기본 주입 대상이 아니다.
- 체크리스트·프롬프트·Skill·테스트를 복사해 넣지 않고 정확한 판본을 참조한다. 행동 의미가 바뀌면 패치도 새 판본이 된다.
- 모델·도구 버전이 효과에 관여할 가능성이 있으면 구성 지문을 남긴다.

### 5.5 사용 영수증: 최소 적용 데이터

패치가 제안된 작업에서 다음만 남긴다.

```text
과제 식별자(비식별)
프로젝트·과제 유형·구성 지문
PATCH-ID@version
결정: 사용 / 변형 / 거부 / 비적용
검사 결과와 중대 회귀
인간 능동시간, 벽시계 시간, 토큰·현금, 재작업의 가용 값
거부·변형 이유
```

전체 대화나 사고과정은 저장하지 않는다. 사용 영수증은 적용률을 높이기 위한 감시가 아니라 패치가 검색됐는지, 맞게 선택됐는지, 실제 이득이 있었는지를 구분하기 위한 최소 데이터다.

## 6. 경험을 규칙·Skill·체크리스트·테스트로 바꾸는 과정

### 6.1 직접 변환 경로

```text
신호
→ 원자료와 사실 확인
→ 비밀·개인정보 제거
→ “다음에 바꿀 한 행동” 선택
→ 적용/금지 조건 작성
→ 검사와 중지 조건 사전 작성
→ 사람의 제한 trial 승인
→ 안전한 신선 과제 적용
→ 사용 영수증 판정
→ live / 수정 trial / off
```

AI는 신호 군집화, 유사 패치 찾기, 반례 후보, 패치 문장, 검사 후보를 제안할 수 있다. AI의 자기성찰은 원자료가 아니며 단독으로 trial을 활성화하지 못한다.

### 6.2 표현 선택 우선순위

같은 행동 변화를 여러 방식으로 표현할 수 있다면 다음 순서를 선호한다.

1. 프로젝트의 결정적 테스트·정적 검사·인수 조건
2. 짧은 체크리스트나 템플릿
3. 도구가 실행할 수 있는 작은 Skill
4. 버전이 있는 프롬프트 조각
5. 설명 문서

높은 순위가 항상 옳다는 뜻은 아니다. 핵심은 가장 적은 해석으로 검증할 수 있는 표현을 택하는 것이다. 이미 프로젝트에 테스트가 있다면 전통에 복제하지 않고 패치가 그 테스트를 호출한다.

### 6.3 정제 자체가 불필요한 조건

다음이면 패치를 만들지 않는다.

- 같은 행동이 프로젝트 테스트·runbook·인수 기준에 이미 충분히 표현돼 있다.
- 일회성 사건이고 반복 가능성이나 큰 위험이 없다.
- 행동 변화를 반증할 검사나 독립 검토가 없다.
- 비밀·개인정보를 안전하게 제거할 수 없다.
- 곧 사라질 도구의 세부 우회법이며 재탐색 비용이 매우 작다.
- 원인이 불명확하고 여러 설명 중 하나를 선택할 근거가 없다.
- 법·계약·사용자 요구처럼 경험 교리가 아니라 보호 규범으로 다뤄야 한다.
- 다음 적용 기회가 없어 trial을 평가할 수 없다.
- 패치 작성·검색 비용이 다시 알아내는 비용보다 클 것으로 합리적으로 예상된다.

이 경우 선택지는 `원 프로젝트 직접 수정`, `원자료만 보존`, `신호 만료`, `추가 증거 대기` 중 하나다. 모든 경험이 전통 자산이 될 필요는 없다.

## 7. 프로젝트 전용 지식과 범용 지식의 관계

### 7.1 프로젝트 우선

모든 경험 패치는 프로젝트 전용 `trial`로 시작한다. 프로젝트 조건은 단순한 태그가 아니라 유효성의 일부다. 프로젝트가 끝나면 패치는 자동으로 범용 지위를 얻지 않고 기본적으로 `off` 또는 보관 제한 상태가 된다.

### 7.2 승격 대신 분기

두 프로젝트에서 비슷한 패치가 유용해 보여도 기존 프로젝트 패치를 범용으로 승격하지 않는다. 다음 조건을 만족할 때 **새 공통 패치**를 분기한다.

- 표면 문장이 아니라 작동 메커니즘이 같다.
- 독립된 맥락에서 각자 판정 검사를 통과했다.
- 도구·모델·저장소 특수 부분을 제거해도 행동 의미가 남는다.
- 반대 사례와 금지 조건을 함께 설명할 수 있다.
- 공통화가 선택 비용과 오적용 위험을 줄이는지 시험할 수 있다.

서로 다른 두 맥락은 필요한 시작 신호이지 충분한 증거 임계값이 아니다. 새 공통 패치는 다른 프로젝트에서 처음에는 `suggest` 또는 `experiment`이고, 로컬 패치를 이기지 않는다.

### 7.3 충돌 우선순위

1. 법·계약·보안·사용자 명시 요구
2. 현재 프로젝트의 검증된 패치
3. 조건이 맞는 공통 패치
4. trial과 과거 off 기록

공통 패치가 프로젝트 패치와 충돌하면 둘을 합치지 않고 자동 제안을 멈춘다. 현재 프로젝트의 근거를 우선하되, 충돌은 판별 실험 후보로 남긴다.

### 7.4 모델·도구 이주

모델 또는 핵심 도구가 바뀌면 관련 패치의 과거 결과는 사라지지 않지만 현재 효력은 자동으로 보장되지 않는다.

- 표현만 달라지고 핵심 행동과 검사가 같으면 새 어댑터 판본을 trial한다.
- 핵심 행동이나 오류 경계가 달라지면 새 패치로 분기한다.
- 이주 시험 전에는 `suggest` 이하로 낮추거나 적용을 보류한다.
- 새 모델이 더 좋아졌다는 이유만으로 패치 효과를 주장하지 않는다.

모델별 어댑터 체계는 실제로 두 번째 표현이 필요해질 때만 만든다.

## 8. 승격·강등·수정·폐기 규칙

### 8.1 최소 상태

상태는 세 개만 둔다.

- `trial`: 이름 붙은 안전한 과제와 사전 검사 안에서만 사용
- `live`: 조건이 맞을 때 제안 가능
- `off`: 신규 적용 금지; 이유와 대체 관계만 유지

`hold`는 상태가 아니라 긴급 차단 플래그다. AI나 자동 검사가 중대 위험을 발견하면 `hold`를 요청할 수 있고, 인간이 확인하기 전에는 적용하지 않는다.

### 8.2 trial → live

모두 필요하다.

- 사전에 정한 주요 판정 기준을 신선한 과제에서 충족
- 중대 품질·보안·비밀 guardrail 위반 없음
- 패치가 실제로 검색·채택·핵심 기능대로 적용됨
- 증가 비용을 포함한 순효과가 사용자 승인 기준을 통과
- 반대 사례와 불확실성 검토
- 인간의 판본·범위·적용 모드 승인

표본이 작거나 결과가 혼재하면 `trial`을 유지하거나 `off`로 둔다. 억지로 live를 만들지 않는다.

### 8.3 live → trial 또는 off

- 모델·도구·요구 변경으로 핵심 전제가 달라짐: `trial`
- 새로운 반례가 있으나 좁은 범위에서는 가능성 있음: 범위를 좁힌 새 `trial`
- 반복 무효, 선택 비용 과다, 중복, 사용 기회 소멸: `off`
- 중대 오류·보안·비밀 침해 유발: 즉시 `hold`, 검토 뒤 `off`가 기본
- 더 단순한 프로젝트 테스트가 같은 효과를 냄: 패치는 `off`, 테스트만 유지

### 8.4 수정

- 오탈자·링크 수정처럼 행동 의미가 바뀌지 않으면 같은 판본의 편집 이력으로 처리할 수 있다.
- `IF`, `DO`, `DO NOT`, `VERIFY`, `STOP` 중 하나가 바뀌면 새 판본의 `trial`이다.
- 고위험 반례가 기존 live를 깨면 새 판본 시험 중에도 옛 판본을 유지하지 않는다.

### 8.5 폐기와 삭제

일반 폐기는 ID, off 이유, 날짜, 대체 패치만 남기고 본문을 활성 목록에서 제거한다. 비밀·개인정보 삭제 의무가 있으면 파생 패치, 요약, 인덱스, 캐시의 민감 내용도 실제로 지우며 “역사 보존”을 이유로 남기지 않는다. 법적으로 허용되고 민감하지 않은 경우에만 내용 없는 tombstone을 둔다.

## 9. 모순되는 경험과 잘못된 교훈

### 9.1 모순 처리

같은 과제 조건에 서로 다른 행동을 요구하는 패치가 검색되면 시스템은 하나를 고르지 않는다.

1. 두 패치를 `conflict`로 묶고 자동 주입을 중지한다.
2. 프로젝트, 과제 유형, 위험, 모델·도구, 데이터, 검사 방식 차이를 비교한다.
3. 조건 차이로 설명되면 각각의 `IF/DO NOT`을 좁힌 새 trial을 만든다.
4. 같은 조건의 진짜 모순이면 어느 결과가 어느 패치를 지지할지 사전 작성한 판별 시험을 한다.
5. 판정 전에는 둘 다 권위 있는 기본값이 아니다. 미적용 위험이 크면 사람이 가장 가역적이고 보수적인 보호 조치를 선택한다.

증거 건수 투표, 최신 항목 우선, AI confidence, 모델 다수결은 판정 기준으로 쓰지 않는다. 같은 원자료의 여러 요약은 하나의 근거다.

### 9.2 잘못된 교훈의 조기 신호

- 패치가 검색됐지만 자주 거부되거나 크게 변형된다.
- 검사 완료율은 높지만 실제 결함·재작업이 줄지 않는다.
- 평균은 좋아졌지만 최악 사례나 중대한 오류가 악화된다.
- 특정 모델·도구에서만 작동한다.
- 쉬운 과제에는 이득이 있으나 어려운 사례에 큰 음의 전이를 만든다.
- 적용 조건이 결과를 본 뒤 계속 추가돼 반증 불가능해진다.

중대한 반례 한 건은 다수의 사소한 성공보다 우선할 수 있다. 특히 비밀·보안·고객 위해는 평균 효과와 상쇄하지 않는다.

### 9.3 성공과 실패의 대칭성

성공·실패라는 라벨만 저장하지 않는다. 패치 판단에는 `예상, 실제, 과정의 적합성, 외부 요인, 검사 결과`를 본다. 나쁜 과정으로 우연히 성공한 경우는 지지 근거가 아니라 근접 실패 또는 반례다. 좋은 과정이 실패한 경우는 환경 변화나 검사 오류를 찾는 자료이지 자동 폐기 근거가 아니다.

## 10. 사람 승인 게이트와 AI의 실질적 역할

### 10.1 사람 승인 게이트

| 게이트 | 사람이 실제로 확인할 것 | 결과 |
|---|---|---|
| G0 수집 | 원자료 포인터, 최소 수집, 비밀·개인정보 제거 | 신호 유지 또는 삭제 |
| G1 trial | 행동 변화, 적용/금지 조건, 검사, 비용·중지 기준, 고객 격리 | 제한 trial 허용 또는 거부 |
| G2 live | 원자료와 영수증, guardrail, 순효과, 반례 | live / trial 유지 / off |
| G3 범위 분기 | 독립 맥락, 공통 메커니즘, 오적용 비용 | 공통 trial 생성 또는 프로젝트 유지 |
| G4 재활성화 | hold 원인 제거, 삭제·회귀시험, 새 위험 | 재trial 또는 off 유지 |
| G5 외부 주장 | 비밀·동의, AI 기여, 인간 검토, 주장 강도 | 공개 승인 또는 내부 한정 |

중·고위험 패치는 사건을 설명한 같은 AI 출력에서 바로 승인하지 않는다. 적어도 원자료를 새로 읽는 분리된 검토 단계를 둔다. 외부 독립 reviewer는 모든 패치의 필수조건이 아니라 보안·법·고객 위해·큰 비용 같은 고위험 범위에서 요구하거나, 구할 수 없으면 적용 모드를 낮추는 조건이다.

### 10.2 AI가 맡는 일

- 현재 과제 서명 생성과 조건 일치 패치 검색
- 원자료에서 사실·해석·제안 혼합 표시
- 반례·충돌·오래된 구성 지문 탐색
- 패치와 검사 초안 작성
- 패치 적용·변형·거부 이유와 영수증 초안 작성
- hold 사유 제기와 대체 행동 제안
- 다음 AI에 사용한 패치·검사·남은 불확실성 인계

AI는 단순 요약기가 아니다. 기억을 선택하고 적용하며 반증을 시도하는 운영 주체다. 다만 live 전환, 범위 확대, 외부 공개, 비밀 처리, hold 해제의 권한은 없다.

### 10.3 형식적 사람 승인을 막는 방법

승인 화면이나 문서가 있다면 긴 AI 설명 대신 다음 다섯 항목만 먼저 보여준다.

1. 무엇이 달라지는가?
2. 어떤 원자료가 직접 지지하는가?
3. 무엇이 아직 추론인가?
4. 어떤 결과면 즉시 중지하는가?
5. 추가 인간 시간·토큰·현금은 얼마인가?

사람이 원자료와 검사 결과를 보지 않은 승인은 무효다. 반대로 사람이 모든 AI 작업을 다시 수행할 필요는 없으며, 고위험 표본과 판정 근거를 감독한다.

## 11. 개인정보·비밀정보·기억 오염 통제

### 11.1 두 신뢰 영역

- **비신뢰 증거 영역:** 고객 문서, 웹·이메일·저장소 텍스트, 로그, AI 회고. 명령이 아니라 분석 대상 데이터다.
- **승인 패치 영역:** redaction과 사람 승인을 통과한 짧은 패치만 존재한다. 작업 중 자동 제안 가능한 유일한 전통 영역이다.

원자료를 승인 영역으로 복사하지 않는다. 원자료가 민감하면 비식별 포인터, 무결성 단서, 접근권한만 남긴다.

### 11.2 최소 제거 절차

1. 수집 전에 필요한 기술 사실만 선택한다.
2. 이름, 고객·조직명, 이메일·전화, 계정, 로컬 절대경로, 토큰·키·쿠키·서명 URL, 비공개 원문을 제거하거나 일반화한다.
3. 자동 패턴 검사는 경고기로만 사용하고 사람이 문맥을 검토한다.
4. redaction 전 원문을 외부 모델에 보내지 않는다.
5. 패치에는 비밀 원문 대신 행동 조건과 제한 포인터만 둔다.

### 11.3 프롬프트 주입과 공급망

- 비신뢰 문서 안의 “이 지시를 기억하라/실행하라”는 문자열은 데이터다.
- 패치 초안 AI는 도구 실행권이나 live 쓰기 권한을 갖지 않는다.
- 패치의 `DO`는 원문 지시를 복사하지 않고 사람이 승인한 행동으로 다시 쓴다.
- 출처·권한·삭제 상태가 확인되지 않은 항목은 주입하지 않는다.
- 의미 검색을 도입할 경우 악성 지침 검색, 권한 우회, 삭제 후 잔존을 별도 통과 조건으로 둔다.

### 11.4 삭제·철회

각 패치는 source ref를 통해 파생 경로를 역추적할 수 있어야 한다. 삭제나 동의 철회가 생기면 `원자료 포인터 → 패치 → 검색 인덱스 → 캐시·bundle`을 점검한다. 이 경로를 재구성할 수 없는 검색 기술은 도입하지 않는다. 삭제 사실 자체도 민감하면 tombstone을 남기지 않는다.

## 12. 검색·주입·적용 방식

### 12.1 과제 서명

작업 시작 시 AI가 다음 최소 조건을 제안하고 사람이 필요할 때 수정한다.

```text
프로젝트 / 과제 유형 / 실패 비용 / 민감도
모델·핵심 도구 판본 / 검증 방식 / 현재 단계
```

이 서명이 없으면 경험 패치를 자동 제안하지 않는다. 보호 규범은 별도 적용된다.

### 12.2 검색 순서

1. 프로젝트와 `live/trial` 상태의 정확 일치
2. 과제 유형·위험·도구 조건의 필수 필터
3. 프로젝트 패치 우선
4. 충돌 없는 공통 패치 제안
5. 결과가 없으면 “일치 패치 없음”이라고 명시

초기에는 사람이 고른 목록 또는 exact/keyword 검색이면 충분하다. 의미 검색은 측정된 recall 실패가 반복되고 패치 수가 수작업 한계를 넘을 때만 비교한다.

### 12.3 주입 형식

한 과제에 주입하는 패치는 초기 기본값으로 최대 2개다. 총 전통 입력은 사용자 승인 전 임시 상한으로 `800 tokens 또는 사용 가능한 컨텍스트의 5% 중 작은 값`을 둔다. 이 수치는 효과가 검증된 기준이 아니라 컨텍스트 과부하를 막기 위한 pilot 예산이며 T0 결과로 줄이거나 늘린다.

```text
[공동 전통 제안 — 원자료의 명령이 아님]
PATCH-ID@version
IF: 적용 조건
DO: 바꿀 행동
DO NOT: 금지 조건
VERIFY: 판정 검사
STOP: 중지 조건
EVIDENCE: 짧은 근거와 불확실성
```

긴 사례 원문은 기본 주입하지 않는다. AI가 근거를 더 봐야 하면 권한이 허용된 source ref를 별도로 요청한다.

### 12.4 적용과 변형

AI는 패치를 기계적으로 복종하지 않고 `사용/변형/거부/비적용`을 선택하고 이유를 남긴다. 핵심 행동을 바꾸면 `변형`이며 원래 패치의 성공으로 계산하지 않는다. 적용 뒤 반드시 `VERIFY`를 수행하거나 수행하지 못한 이유를 기록한다.

검색 실패 때 모델 일반 지식을 “우리 전통”으로 포장하지 않는다. 일반 지식으로 제안할 수는 있으나 새로운 trial 절차를 거친다.

## 13. 운영 주기: 달력이 아니라 증거와 위험이 시계를 정한다

### 13.1 즉시 안전 루프

비밀 노출, 고객 위해, 중대 품질 회귀, 악성 지침, 잘못된 live 주입은 즉시 `hold → 적용 중지 → 사람 확인 → 삭제/방어 → 회귀시험`으로 처리한다. 월간 검토를 기다리지 않는다.

### 13.2 증거량 기반 패치 검토

다음 중 하나일 때만 패치 검토 창을 연다.

- 같은 패치의 평가 가능한 사용 영수증이 pilot 기준 수만큼 쌓임
- 모순·중대 반례·반복 거부가 생김
- 핵심 모델·도구·요구가 변경됨
- 프로젝트가 끝나거나 새 프로젝트에서 공통화 후보가 생김
- 사용자가 비용 상한 초과를 감지함

pilot 시작값은 **평가 가능한 사용 3건**이다. 이는 통계적 임계값이 아니라 한 번의 우연을 곧바로 live로 만들지 않기 위한 최소 운영값이다. 결과 변동이 크면 더 모으거나 `inconclusive`로 끝낸다.

검토 창은 패치 하나당 30분을 넘기지 않는 것을 초기 상한으로 둔다. 시간이 부족하면 증거를 꾸며내지 않고 `trial 유지` 또는 `off`로 둔다.

### 13.3 경량 청소와 시스템 메타 검토

- live/trial 패치가 있으면 6주마다 최대 15분 동안 만료 신호, 구성 변경, 비용 누락만 확인한다. 결정할 증거가 없으면 아무것도 승격하지 않는다.
- T0 이후에는 90일 또는 두 개의 평가 블록 중 먼저 오는 시점에 최대 30분의 시스템 생존 검토를 한다.
- 시스템 생존 검토는 “전통이 없었을 때보다 순이익이 있었는가, 실제 작업을 방해했는가, 더 단순한 프로젝트 테스트로 대체 가능한가”만 묻는다.

이 수치들은 과학적 최적값이 아니라 1인 운영을 보호하는 취소 가능한 예산이다. 실제 baseline 뒤 사용자 승인으로 조정한다. 패치나 사건이 없으면 회의를 열지 않는다.

## 14. 비용·시간·토큰 통제

### 14.1 pilot 운영 봉투

| 항목 | 초기 상한 | 초과 시 행동 |
|---|---:|---|
| 사건 신호 포착 | 건당 2분 | 원자료 포인터만 남기거나 포착하지 않음. 안전 사건은 예외 |
| 한 패치 trial 설계·승인 | 30분 | 범위를 줄이거나 off |
| rolling 30일 C 활동 인간 능동시간 | 45분 | 신규 패치 동결, 기존 프로젝트 방식으로 작업 |
| 동시에 진행하는 trial | 2개 | 기존 trial 판정 전 신규 생성 금지 |
| live 패치 | 5개 | 중복 제거·프로젝트 직접 테스트 전환 |
| 과제당 주입 | 최대 2개, 총 800 tokens/5% 이하 | 사람이 하나를 선택하거나 무주입 |
| 별도 유료 도구·서비스 | T0에서는 0원 | 사용자 별도 투자 승인 전 도입 금지 |

상한은 성능 목표가 아니라 관료주의 방지용이다. 중요한 안전 패치는 개수보다 우선하지만, 그 경우 다른 패치를 제거해 총부담을 유지한다.

### 14.2 순가치 장부

패치 효과는 다음을 한 점수로 억지 합산하지 않고 병렬로 보고한다.

- 객관 품질과 중대 오류
- 절감 또는 증가한 인간 능동시간
- 벽시계 시간과 대기
- 토큰·원화
- 재작업과 되돌림 비용
- 위험 감소의 근거와 불확실성

현금 손익과 학습 자산을 별도 장부로 둔다. “향후 유용할 수 있다”는 말은 현재 비용 절감으로 계산하지 않는다. 위험 감소를 돈으로 환산할 근거가 없으면 별도 guardrail 성과로만 보고한다.

### 14.3 자동화 게이트

같은 수작업 마찰이 적어도 두 검토 창에서 반복되고, 자동화 예상 절감이 구현·유지 비용보다 클 때만 자동화를 검토한다. 자동화는 먼저 필터·bundle 생성·판본 확인처럼 결정적 작업에 한정한다. AI 자동 승격은 장기 방향에도 포함하지 않는다.

### 14.4 A/B/C 활동과 외주·공모전 장부

이 설계에서 A 활동은 실제 개발·외주·공모전 산출물을 만드는 일, B 활동은 작업 패치·테스트로 다음 A 작업을 개선하는 일, C 활동은 패치 선택·평가·폐기 방식 자체를 고치는 일이다. 우선순위는 항상 A의 사용자 가치와 의무가 먼저다. C 활동은 앞의 rolling 시간 상한 안에서만 내부 수행하고, 공식 문서·기존 프로젝트 테스트·공개 벤치마크·독립 심사로 대체할 수 있는 검증은 새 내부 체계로 복제하지 않는다.

외주·공모전마다 현금 손익과 학습 장부를 분리한다. 사용자에게 감수 가능한 월 손실 한도가 있더라도 그 금액 자체는 학습 투자의 증거가 아니다. 내부 trial이나 탐색비를 쓰기 전 `줄일 불확실성, 최대 현금·인간시간·토큰, 중단 조건, 실패해도 남길 재사용 자산`을 적는다. 수익이 없고 새 정보·재사용 자산·후속 선택권도 남지 않으면 단순 손실로 기록한다. 고객 과제에서는 패치를 관찰할 수는 있지만 열등할 수 있는 조건을 배정하지 않으며, 학습을 위해 납기·품질·비밀을 희생하지 않는다.

- 경험·교훈·교리·산출물·평가를 위한 다중 스키마와 상태 그래프

## 16. 오케스트레이터 안정화 이후의 최소 T0

### 16.1 진입 조건

모두 충족하기 전에는 T0를 시작하지 않는다.

- 원천 오케스트레이터 또는 다른 대상 workflow가 반복 가능하고 안정적으로 실행된다.
- 개입 전 현재 최선 workflow의 품질·시간·비용 baseline이 있다.
- 같은 과제군의 신선하고 난이도가 비슷한 내부 과제를 만들 수 있다.
- 객관적 테스트나 사전 정의된 사람 인수 기준이 있다.
- 고객 납품과 분리된 자체 개발·연습·비영향 내부 검토 층이다.
- 모델·도구·프롬프트 구성 지문을 기록할 수 있다.
- 사용자가 시간·토큰 예산, 중단 조건, 원자료 범위를 승인한다.

현재 개발 incident는 후보 주제를 찾거나 형식을 리허설하는 데만 쓸 수 있고, T0 운영 효과의 지지 사례로 세지 않는다.

### 16.2 최소 연구 질문

> 하나의 짧은 작업 패치를 현재 최선 workflow에 추가하면, 같은 구성의 신선한 내부 과제에서 순품질 또는 순효율이 좋아지고 중대한 회귀가 생기지 않는가?

이 T0는 인간 단독, AI 단독, 단일 AI 보조, 오케스트레이션 전체 중 누가 가장 나은지를 판정하는 시험이 아니다. 그 비교는 안정화된 오케스트레이터의 별도 평가 문제다. 여기서는 모델·도구·오케스트레이션을 가능한 한 고정해 **패치의 추가 효과**만 가장 작게 묻는다. 전체 workflow가 인간 단독이나 단일 AI보다 낫다는 근거가 아직 없으면 그 사실을 별도로 유지하며, T0 성공으로 오케스트레이션의 우월성을 대신 증명하지 않는다.

### 16.3 최소 설계 단위

- 패치 1개
- 반복 가능한 과제군 1개
- 동결한 모델·도구·프롬프트 구성 1개
- 사전 정의 검사 1개 이상
- 현재 최선 workflow `A`와 동일 workflow `+패치 B`
- 최소 3개의 신선한 난이도 대응 과제쌍

3개 대응쌍은 통계적 확증이 아니라 반복 가능성의 최소 feasibility 신호다. baseline 변동이 크면 표본을 늘리거나 `inconclusive`로 끝내며, 유의성을 가장하지 않는다.

### 16.4 수행

1. baseline 결과를 보고 최소 가치 차이와 guardrail을 사람이 사전 고정한다.
2. 각 과제쌍의 A/B 순서를 가능한 범위에서 무작위화하거나 균형화한다.
3. 새 세션을 사용하고 다른 조건의 결과·정답을 보지 않게 한다.
4. 사람 평가가 필요한 경우 가능하면 패치 조건을 가린 산출물로 판정한다.
5. 패치 검색 여부, 적용·변형·거부, 검사 결과를 기록한다.
6. 품질, 중대 오류, 인간 능동시간, 벽시계, 토큰·원화, 재작업을 함께 기록한다.
7. 결과를 본 뒤 성공 기준이나 적용 조건을 바꾸지 않는다. 새 설명은 다음 trial 가설이다.

### 16.5 판정

- 사전 최소 가치 차이 충족, guardrail 통과, 비용 상한 이내: 해당 과제·구성에 한해 `live` 후보
- 평균 이득이나 중대 회귀 발생: `off`
- 이득과 비용이 혼재하거나 변동이 큼: `trial` 또는 `inconclusive`
- 검색됐지만 적용되지 않음: 패치 효과가 아니라 retrieval/adoption 실패
- 적용됐지만 검사 미수행: 시행 충실도 실패

T0가 성공해도 “전통 시스템이 효과 있다”, “오케스트레이션이 성장했다”, “모델을 넘어 전이된다”라고 말하지 않는다. 허용되는 주장은 “이 패치가 이 과제군과 이 구성에서 현재 workflow에 추가 이득을 보였다”까지다.

### 16.6 다음 최소 실험

첫 결과가 양수일 때만 다음을 순차 검토한다.

1. **표현 가치:** 원자료 포인터만 제공한 조건과 작업 패치를 비교해 정제의 한계효과를 본다.
2. **near transfer:** 같은 과제군의 다른 표면 과제에서 재시험한다.
3. **migration transfer:** 다른 모델의 자체 baseline과 `+같은 핵심 패치`를 비교한다.
4. **공통화:** 다른 프로젝트에서 독립적으로 유용한 경우에만 공통 trial을 분기한다.

한 번에 2모델×다수 기억 표현을 모두 시험하지 않는다. 작은 순차 실험으로 가치 없는 가지를 빨리 버린다.

## 17. 평가 지표와 인과 추론 한계

### 17.1 지표 구조

| 층 | 핵심 질문 | 예시 지표 |
|---|---|---|
| 결과 | 산출물이 실제로 좋아졌는가? | 인수 실패, 회귀 결함, 중대 오류, 블라인드 품질 판정 |
| 효율 | 같은 품질의 총비용이 줄었는가? | 인간 능동시간, 벽시계, 토큰·원화, 재작업 |
| 선택 | 맞는 패치가 제안됐는가? | 관련 패치 recall, 무관 패치 수, 충돌 탐지, 무패치 선언 정확성 |
| 실행 | 패치 핵심 기능을 사용했는가? | 사용·변형·거부, VERIFY 수행, stop 준수 |
| 전이 | 다른 조건에서도 이득인가? | near/far/migration별 효과 방향과 guardrail |
| 유지 | 시간이 지나도 순이익인가? | 재검증 결과, 구성 변경 후 회귀, 유지비 |
| 브랜드 | 작업방식이 반복되는가? | 사실/추론 구분, 검증 흔적, 수정 투명성, 책임 표기 |

단일 종합 점수는 만들지 않는다. 평균 개선이 중대 오류 한 건을 가리지 못하게 결과와 guardrail을 별도로 본다.

### 17.2 인과 주장 등급

이 설계는 숫자 증거 등급 대신 **허용 주장 수준**을 기록한다.

1. **제한적 패치 효과:** 같은 구성, 신선 대응 과제, 사전 지표, 균형화 비교가 있을 때 해당 과제군에 한해 말할 수 있다.
2. **연관:** 전후 관찰만 있거나 사람 숙련·난이도가 함께 바뀌었으면 “함께 좋아졌다/나빠졌다”고만 말한다.
3. **구성 전체 성과:** 모델·도구·프롬프트·사용자·전통이 함께 바뀌었으면 어느 한 요소의 효과로 귀속하지 않는다.
4. **서술 신호:** 만족도, 자기평가, 고객 한 건, 브랜드 반응은 가설 생성 신호다.

고객 과제는 관찰 자료가 될 수 있지만 열등할 수 있는 조건에 배정하지 않으므로 인과 식별이 약하다. 이를 숨기지 않고 품질·비밀을 우선한 대가로 명시한다.

### 17.3 혼란변수 최소 기록

각 평가에는 가능한 범위에서 다음을 남긴다.

- 모델·도구·프롬프트·패치 판본
- 과제 유형과 난이도 근거
- 사용자의 사전 친숙도와 병렬 작업 여부
- 검사기·AI judge·사람 reviewer 판본 또는 역할
- 순서, 시간 경과, 다른 동시 변경

완전 고정이 불가능하면 누락을 꾸며내지 않고 주장 수준을 낮춘다.

### 17.4 공동 브랜드 평가

브랜드는 별도 실험 점수보다 서로 다른 프로젝트 산출물의 블라인드 표본에서 다음이 재현되는지 본다.

- 사실과 추론의 구분
- 검증과 인수 기준의 명시
- 모름·제약·비용의 정직한 보고
- 잘못된 결과의 빠른 수정
- AI 기여와 인간 승인·책임의 투명성

이 일관성이 고객 선호나 수익을 유발한다는 주장은 별도 장기 자료 없이는 하지 않는다.

## 18. 실패 조건과 시스템 자체의 폐기 조건

### 18.1 패치 수준 즉시 실패

- 비밀·개인정보·악성 지침을 작업 컨텍스트에 확산
- 고객·사용자에게 중대한 위해나 인수 실패 유발
- `DO NOT/STOP` 조건을 무시하게 함
- 다른 조건에서 심각한 음의 전이를 만듦
- 원자료와 다른 주장을 권위 있게 주입

즉시 hold하고 사람 확인 전 재사용하지 않는다.

### 18.2 운영 실패

- 패치 찾기와 승인 때문에 작업 시작이 반복 지연됨
- 사용자는 패치를 자주 무시하고 이유 데이터도 남지 않음
- 패치 수는 늘지만 VERIFY 완료와 결과 판정은 늘지 않음
- 신호·영수증을 남기느라 rolling 비용 상한을 계속 초과
- 프로젝트 테스트로 더 단순하게 대체 가능한데 패치 계층을 유지
- 사람 승인이 원자료 확인 없는 도장으로 변함
- AI 결과를 사람이 전부 재수행해야 해 계승 이득이 사라짐

### 18.3 시스템 축소 순서

1. 신규 패치 동결
2. live 패치를 안전·고가치 1~2개로 축소
3. 패치 주입을 중단하고 프로젝트 native 테스트·체크리스트만 유지
4. 사용 영수증 수집 중단
5. 보호 규범 한 장과 필요한 법적·업무 원자료만 남김

### 18.4 시스템 폐기 판정

T0와 사전등록된 한 번의 재검증에서 다음이 모두 참이면 PATCHLINE을 폐기한다.

- 현재 최선 workflow 대비 순품질·순효율 이득이 확인되지 않음
- 중대 위험 감소도 확인되지 않음
- 유지비가 승인 상한을 넘거나 실제 작업을 방해함
- 더 단순한 프로젝트 테스트·체크리스트가 같은 가치를 제공함

또한 삭제·권한·출처 경계를 재구성할 수 없는 구조적 비밀 노출이 발생하면 효과와 무관하게 중단한다. 폐기는 연구 실패를 숨기는 일이 아니라 헌장의 비용·정직성 원칙을 지키는 성공적인 판단이다.

## 19. 단계적 로드맵

### 단계 R-1 — 현재: 설계 비교만

- 이 문서를 다른 독립안과 비교한다.
- 구현, 기존 로그 변환, T0 수행, 원천 오케스트레이터 변경을 하지 않는다.
- 통과 기준: 최소안의 목적 정합성, 안전성, 반증 가능성, 1인 비용을 판단할 수 있음.

### 단계 R0 — 준비 대기

- 오케스트레이터 또는 대상 workflow의 안정화와 반복 과제군을 기다린다.
- 현재 최선 workflow의 개입 전 baseline을 먼저 얻는다.
- 안전한 내부 trial, 신선 과제, 인수 기준, 예산을 사용자와 고정한다.
- 통과하지 않으면 대기하며 개발 incident를 운영 증거로 대체하지 않는다.

### 단계 R1 — 수작업 T0

- 보호 규범 1장, 패치 1개, 영수증 표 1개만 사용한다.
- 최소 대응 과제쌍으로 현재 workflow 대 `+패치`를 비교한다.
- 통과 기준: 사전 최소 가치와 guardrail, 비용 상한 충족.
- 실패하면 전통 시스템을 구현하지 않는다.

### 단계 R2 — 작은 프로젝트 패치 묶음

- live 최대 5개, trial 최대 2개 안에서 서로 다른 패치 2개 이상을 시험한다.
- 정확 조건 선택, 거부·변형, 충돌 처리, off 경로가 실제로 작동하는지 본다.
- 통과 기준: 적어도 한 패치의 순이익과 한 패치의 정직한 수정·폐기 경험. 수치는 성공을 만들기 위한 할당량이 아니다.

### 단계 R3 — 모델 이주와 공통 패치 분기

- 다른 모델의 자체 baseline을 먼저 측정한다.
- 유용한 프로젝트 패치 하나의 migration transfer를 시험한다.
- 별도 프로젝트에 같은 메커니즘이 있을 때만 공통 trial을 분기한다.
- 통과 기준: 새 모델·프로젝트에서 추가 이득 또는 명확한 적용 경계 발견.

### 단계 R4 — 결정적 자동화

- 반복 마찰이 입증된 경우에만 상태 필터, 판본 확인, 짧은 bundle 생성, 삭제 추적을 자동화한다.
- 자동화 전후 인간 시간·오검색·비용을 비교한다.
- live 자동 승격과 고객 조건 배정은 자동화하지 않는다.

### 단계 R5 — 검색 확장 여부 결정

- 패치 수가 exact 검색 한계를 실제로 만들고 relevance 정답표가 있을 때만 keyword/hybrid/semantic을 비교한다.
- active 상태·권한·삭제 필터를 우회하거나 음의 전이를 늘리면 도입하지 않는다.
- 파인튜닝은 이 로드맵의 예정 단계가 아니다.

각 단계는 상위 단계로만 가는 사다리가 아니다. 비용이나 효과가 나쁘면 앞 단계 또는 “프로젝트 native 테스트만” 상태로 되돌아간다.

## 20. 아직 증거가 없어 결정하면 안 되는 사항

1. 작업 패치가 원로그 검색이나 기존 다단계 정제보다 실제로 낫다는 주장
2. 월간·6주·증거 3건 중 어떤 검토 주기가 최적인지
3. live 5개, trial 2개, 800 tokens 같은 pilot 상한의 적정값
4. 범용 분기에 필요한 프로젝트 수와 효과 임계값
5. 새 모델에서도 같은 패치가 전이되는지와 모델별 어댑터 필요성
6. exact/keyword 검색이 언제 수작업보다 유리해지는지
7. RAG가 패치 선택과 반례 recall을 순개선하는지
8. 오케스트레이터가 언제 T0를 할 만큼 안정적인지
9. 전통이 외주·공모전 수익성, 수주율, 고객 신뢰를 높이는지
10. 공동 브랜드의 품질 흔적을 고객이 실제로 인식하고 선호하는지
11. 외부 reviewer가 제공하는 순가치와 어떤 위험부터 의무화할지
12. 장기적으로 파인튜닝이 필요하거나 경제적인지

이 항목은 설계 공백이 아니라 의도적으로 보존한 미결정 영역이다. 구현 편의나 기대 서사로 채우지 않는다.

## 22. 결론

이 설계가 제안하는 전통은 기억을 많이 가진 AI가 아니다. **과거로부터 가져온 아주 작은 행동 변화가 현재 과제에 맞는지 먼저 묻고, 적용하면 검사하며, 이득이 없거나 해로우면 즉시 버리는 인간–AI 작업 관계**다.

공동 브랜드도 그 과정 밖에 따로 세우지 않는다. 서로 다른 AI가 같은 모델 이름이나 말투를 재현해서가 아니라, 출처를 밝히고, 고객 가치를 지키고, 검사를 수행하고, 틀린 패치를 폐기하며, 인간이 책임 있게 승인하는 행동이 반복될 때 계보가 생긴다.

PATCHLINE의 첫 성공은 훌륭한 지식 시스템을 구축하는 것이 아니다. 오케스트레이터가 안정된 뒤, 단 하나의 패치가 현재 최선의 workflow에 순이익을 더하는지 정직하게 판정하고, 답이 아니면 시스템을 만들지 않는 것이다.
