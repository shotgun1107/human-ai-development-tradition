**[확인된 사실]** 사용자가 원하는 것은 개인 성장 일지나 실패 기록 저장소가 아니다. 여러 실제 프로젝트에서 인간과 여러 AI가 함께 얻은 성공·실패·결정·실험·반례·비용·수정·충돌을 모델 밖에 보존하고, 새 세션과 새 모델이 이를 필요한 순간에 이어받아 더 나은 행동을 하게 만드는 중앙 시스템이다.

**[확인된 사실]** 원천 멀티 AI 오케스트레이터와 Project Brain은 구축·시험·비용 판단 단계이며 역할, 로그, 완료 보고, 통신 형식이 안정되지 않았다. 중앙 전통 시스템은 이에 종속되지 않고 병렬적으로 기획·구축·시험돼야 한다.

**[연구 근거]** 저장된 기록 자체는 학습이 아니며, 출처와 맥락을 보존한 경험이 검색되고, 행동 자산으로 적용되고, 결과가 검증되고, 틀리면 수정·폐기될 때 비로소 계승 가능한 기억이 된다. 인간–AI 조합과 Skill, 체크리스트, 회고는 자동으로 성능 향상을 보장하지 않는다.

**[설계자의 추론]** 따라서 중앙 시스템의 중심 단위는 ‘교훈 문서’도 ‘행동 패치’도 아니라, 원근거에서 현재 행동과 적용 결과까지 끊기지 않는 **계보 있는 조건부 선례와 실행 자산의 포트폴리오**여야 한다.

### 1.4 문서 내 근거 표기

- **[확인된 사실]**: 공통 기준선·브리프·철학 헌장이 직접 고정한 상태와 목적
- **[연구 근거]**: 두 연구 문서가 소개한 확인된 선행 원리와 한계
- **[설계자의 추론]**: 근거와 목적을 결합해 이 시스템에 적용한 논리적 판단
- **[미검증 제안]**: 아직 구현·운영·효과 시험을 거치지 않은 구조 선택

## 2. 제품 한 문장 정의

**여러 프로젝트와 여러 AI 세대에서 생긴 공동 작업 경험을 출처·조건·결정·구성·반례·적용 결과가 연결된 중앙 계보로 보존하고, 현재 프로젝트에 맞는 조건부 선례와 실행 자산만 골라 전달한 뒤 결과를 다시 회수해 다음 행동을 개선하는 인간–AI 공동 작업 전통 시스템이다.**

## 3. 문제 정의와 비목표

### 3.1 해결하려는 문제

더 강한 모델이 등장해도 프로젝트 경험은 자동으로 계승되지 않는다. 대화는 종료되고, 컨텍스트는 잘리고, 모델·도구·프롬프트·역할 구성이 바뀐다. 이때 다음 단절이 발생한다.

1. 같은 실패와 재작업이 다른 프로젝트에서 반복된다.
2. 성공의 원인이 보존되지 않아 재현 가능한 방법과 운 좋은 성공이 섞인다.
3. 중요한 결정의 당시 제약과 대안이 결과물 뒤에서 사라진다.
4. Skill·프롬프트·체크리스트가 특정 모델이나 프로젝트에 과적합된다.
5. 여러 AI의 합의가 같은 원자료와 오류를 공유한 중복 증거인지 구분되지 않는다.
6. 사용·거부·변형·오적용 결과가 중앙 기억으로 돌아오지 않는다.
7. 프로젝트별 비밀과 권한을 보존하면서도 공통 패턴을 연결하기 어렵다.
8. 모델 자체 향상, 사용자 숙련, 도구 변화, 전통 효과가 혼동된다.
9. 문서와 회고가 늘어도 실제 작업 행동과 결과가 바뀌지 않을 수 있다.
10. 중앙집중이 성공한 한 방식을 모든 프로젝트에 강요해 탐색을 줄일 수 있다.

### 3.2 비목표

이 시스템은 다음을 목표로 하지 않는다.

- 모델 가중치 학습, 파인튜닝 또는 동일 AI 인격의 영속화
- 사용자의 자기계발 일기나 개인 평가 점수
- 모든 대화·파일·작업의 무기한 중앙 수집
- 실패만 모으는 incident 저장소
- 모든 프로젝트에 같은 절차를 강제하는 범용 교리집
- 에이전트 수, 자동화율, 문서량 자체의 극대화
- Project Brain의 실제 API·메시지·로그 형식 선점
- 고객 프로젝트를 열등할 수 있는 실험 조건에 무단 배정
- AI의 법적·도덕적 공동 책임자 지위 주장
- 공동 브랜드를 위한 성공 사례 편집 또는 AI 기여 과장
- 시스템 운영비를 학습이라는 이유로 무조건 정당화

## 4. 사용자 목적과 성공·실패의 정의

### 4.1 사용자 목적의 독립적 해석

**[설계자의 추론]** 사용자가 원하는 ‘AI 측 계승’은 과거 답변을 보관하는 것이 아니라 다음 구성의 AI가 과거의 검증된 차이를 더 낮은 시행착오로 재현하는 능력이다. 따라서 시스템의 제품 가치는 저장량이 아니라 다음 네 단계가 실제로 이어지는지로 판단해야 한다.

1. 필요한 경험을 찾는다.
2. 현재 조건에 맞게 선택·변형한다.
3. 검증 가능한 행동으로 실행한다.
4. 결과를 원래 계보에 되돌려 다음 선택을 바꾼다.

### 4.2 성공의 정의

목표 제품이 성공했다고 주장하려면 장기적으로 다음 신호가 필요하다.

- 새 세션·새 모델이 신선한 동등 과제에서 중대한 반복 실수를 덜 한다.
- 과거 자산이 같은 프로젝트뿐 아니라 다른 프로젝트나 모델에서도 조건부 이득을 보인다.
- 어떤 자산이 왜 선택됐고 어떤 수정과 결과를 만들었는지 추적할 수 있다.
- 성공·실패·결정·반례가 다음 행동 자산과 연결되지만, 모두가 억지로 규칙으로 변환되지는 않는다.
- 음의 전이가 발견되면 자산이 신속히 중지·축소·폐기된다.
- 사람 능동시간, 토큰, 현금, 재작업, 대기, 기회비용이 투명하게 비교된다.
- 공동 브랜드의 품질·검증·책임 방식이 서로 다른 모델과 프로젝트에서 관찰된다.
- ‘변경 없음’, ‘근거 부족’, ‘공통화 실패’가 정상 결과로 허용된다.

### 4.3 실패의 정의

다음 상태가 반복되면 설계를 축소하거나 폐기해야 한다.

- 기록량은 늘지만 다음 프로젝트의 선택과 행동이 달라지지 않는다.
- 원로그 검색보다 정제 자산이 낫지 않거나 중요한 예외를 지운다.
- 검색·승인·회고 비용이 절감한 재작업과 위험보다 지속적으로 크다.
- 중앙 자산 때문에 탐색 다양성이 줄고 오류 상관이 커진다.
- 프로젝트 비밀이나 삭제 의무를 중앙 계보가 침해한다.
- 새 모델 자체의 향상을 전통 성과로 과장한다.
- 인간 승인이 형식적 도장이 되거나 모든 세부를 다시 읽는 병목이 된다.
- 사용되지 않는 자산과 의례적 월간 문서가 축적된다.
- 공동 브랜드가 내부 근거와 분리된 홍보 서사가 된다.

### 4.4 핵심 제품 가설

| 가설 | 지지 신호 | 반증·재검토 조건 |
|---|---|---|
| H1 중앙 계보가 프로젝트 간 반복 오류를 줄인다 | 신선한 과제에서 같은 실패의 감소 | 반복 실패 감소가 없고 관리비만 증가 |
| H2 조건부 자산이 원로그만 제공하는 것보다 낫다 | 품질·시간·오검색·수정량 중 반복 우위 | 차이가 없거나 예외·반례가 사라짐 |
| H3 자산의 사용 결과 회수가 다음 선택을 개선한다 | 오적용·거부 이력이 검색·권고를 실제 변경 | 피드백이 쌓여도 전달 결과가 동일 |
| H4 모델을 바꿔도 핵심 작업 방식 일부가 이주한다 | 새 모델에서 양의 추가 효과 | 효과 소멸, 음의 전이, 중대 오류 증가 |
| H5 중앙화와 프로젝트 자율성을 함께 유지할 수 있다 | 공통화와 분기·거부가 모두 작동 | 중앙 자산이 사실상 의무 규칙으로 굳음 |
| H6 공동 브랜드가 근거 있는 작업 일관성을 표현한다 | 블라인드 결과에서도 품질·검증 태도 재현 | 모델명·서사만 남고 결과 일관성 없음 |

## 5. 중앙 시스템의 의미와 책임 경계

### 5.1 ‘중앙’의 의미

중앙은 모든 프로젝트 데이터를 한곳에 무제한 복사한다는 뜻이 아니다. 중앙의 본질은 다음 책임을 하나의 권한·계보 체계에서 일관되게 수행하는 데 있다.

- 프로젝트별 기록의 구분과 연결
- 원근거와 파생 해석·자산의 계보 유지
- 프로젝트 간 비교와 모순 보존
- 프로젝트 전용·종류 공통·전체 공통 범위 관리
- 현재 과제에 맞는 자산 선택과 안전한 전달
- 사용·거부·변형·오적용·성과의 회수
- 자산의 승격·중지·강등·폐기
- 모델·도구 교체 시 이주 검증
- 삭제·비밀·권한·오염 대응
- 내부 근거와 외부 브랜드 표현의 분리

### 5.2 중앙이 책임지지 않는 것

- 프로젝트 실행을 직접 지휘하는 일
- Project Brain의 내부 역할 배정과 실시간 스케줄링
- 프로젝트 산출물의 최종 품질 보증 자체
- 모든 프로젝트 원자료의 소유권 획득
- 프로젝트별 native test와 절차를 중앙 형식으로 강제 변환
- 단일 진실을 만들어 모든 모순을 제거하는 일
- 사람의 가치·법적·윤리적 책임을 대체하는 일

### 5.3 의미상 경계

| 경계 주체 | 프로젝트 내부 책임 | 중앙과 교환할 의미 |
|---|---|---|
| 프로젝트 또는 Project Brain | 목표 달성, 작업 분해, 실행, 현장 판단, 산출물 검증 | 상황 설명, 완료·사건·결정·비용·자산 사용 결과 |
| 중앙 전통 시스템 | 장기 계보, 비교, 범위, 선택, 전달, 회수, 철회 | 관련 사례·자산·경고·시험·근거 묶음 |
| 사용자 | 목적, 예산, 비밀, 위험 허용, 중요 승인, 외부 책임 | 승격·공개·삭제·고위험 적용·중단 판단 |

**[핵심 결정 D1]** 중앙은 프로젝트 실행 엔진이 아니라 장기 계보와 전이의 통제면으로 둔다.  
**재검토 조건:** 실제 운영에서 중앙 판단이 프로젝트 실행 맥락을 지나치게 늦게 받아 반복적으로 부적절한 자산을 전달하거나, 반대로 중앙이 실행 지휘까지 맡지 않으면 계승 효과를 만들 수 없다는 증거가 나타날 때 경계를 다시 검토한다.

## 6. 사용자·AI·Project Brain·중앙 역할과 책임

### 6.1 사용자

- 목적, 가치 우선순위, 예산, 위험 허용치를 정한다.
- 프로젝트 간 정보 공유 기본값과 예외를 승인한다.
- 전체 공통 자산 활성화, 고위험 규칙, 외부 공개를 승인한다.
- 삭제·법적·윤리적 충돌에서 최종 책임을 가진다.
- 시스템 자체의 운영 순가치를 판단하고 축소·중단할 수 있다.

### 6.2 프로젝트 작업 AI

- 프로젝트 안에서 탐색·생성·비평·검증·실행을 수행한다.
- 자신의 출력과 관찰을 자동으로 확인된 사실로 승격하지 않는다.
- 사용한 중앙 자산, 변형 내용, 거부 이유, 적용 결과를 보고할 책임을 가진다.
- 프로젝트 비밀과 중앙에 전달 가능한 정보를 구분한다.

### 6.3 Project Brain 또는 대표 역할

Project Brain은 아직 구현·통신 방식이 미정이므로 의미상 책임만 정의한다.

- 프로젝트의 목표·제약·현재 상태를 대표한다.
- 중앙에 필요한 기억의 종류와 현재 상황을 요청한다.
- 중앙이 돌려준 후보를 프로젝트 맥락에서 선택·거부·변형한다.
- 적용 결과, 검증 결과, 사람 수정과 비용을 중앙에 반환한다.
- 중앙 자산이 프로젝트 native 자산보다 우선한다고 가정하지 않는다.

### 6.4 중앙 자동화 AI

- 원자료에서 사건·결정·실험·비용·기여 후보를 추출한다.
- 사실·해석·제안의 혼합과 누락을 탐지한다.
- 유사 사례, 반례, 모순, 중복 파생을 찾는다.
- 범위·권한·상태에 맞는 검색 후보를 순위화한다.
- 자산 초안, 적용 조건, 금지 조건, 시험 후보를 제안한다.
- 오래됨, 미사용, 음의 전이, 삭제 파급을 감시한다.
- 승인권을 가진 인간 대신 공통 규칙을 확정하지 않는다.

### 6.5 중앙 관리 기능

하나의 AI 인격이나 단일 서비스가 아니라 다음 책임의 집합이다.

1. 계보 보존
2. 신뢰·권한·삭제 통제
3. 비교·모순 분석
4. 선례·자산 포트폴리오 관리
5. 검색·선택·전달
6. 적용 결과 회수·평가
7. 모델 이주 관리
8. 비용·품질·전이 보고
9. 내부 브랜드 근거 관리

**[핵심 결정 D2]** 역할은 논리적 책임으로 먼저 정의하고, 모델 수·에이전트 수·서비스 경계를 지금 확정하지 않는다.  
**재검토 조건:** 단위 시험에서 책임 혼합 때문에 오류 추적이나 권한 검증이 불가능하면 일부 역할을 별도 실행 경계로 분리한다. 반대로 역할 분리가 사람 관리비만 늘리면 다시 합친다.

## 7. 세 가지 이상 전체 구조 대안

### 7.1 대안 A: 중앙 교리·자산 레지스트리형

중앙이 승인된 Skill, 프롬프트, 체크리스트, 테스트, 템플릿과 적용 규칙을 관리하고 프로젝트가 이를 검색·사용하는 구조다.

**장점**

- 활성 자산이 작고 명확해 초기 사용이 쉽다.
- 검색과 배포를 단순화하기 좋다.
- 사용·버전·폐기 상태를 운영하기 쉽다.

**한계**

- 규칙으로 정제되지 않은 성공·결정·실험·모순의 가치가 약해진다.
- 왜 해당 자산이 존재하는지 계보가 빈약해질 수 있다.
- 중앙 규칙집이 권위화돼 프로젝트 탐색을 줄일 위험이 크다.
- ‘행동 패치 저장소’로 다시 축소될 가능성이 높다.

### 7.2 대안 B: 프로젝트 연합형 분산 기억

각 프로젝트가 자체 사례·결정·자산을 보존하고 중앙은 색인, 공통 태그, 접근권한, 비교 요청만 중개한다. 공통화는 프로젝트 간 합의로 생성한다.

**장점**

- 프로젝트 자율성과 비밀 분리가 강하다.
- 각 프로젝트의 native 구조와 탐색 다양성을 보존한다.
- 중앙 장애나 잘못된 공통 규칙의 파급을 줄인다.

**한계**

- 프로젝트마다 기록 품질과 표현이 달라 비교·검색 비용이 커진다.
- 모델·도구 교체 시 공통 이주 시험을 조직하기 어렵다.
- 여러 프로젝트를 가로지르는 장기 브랜드 계보가 약해질 수 있다.
- 1인 사용자가 프로젝트별 체계를 중복 관리하게 될 위험이 있다.

### 7.3 대안 C: 시간순 증거 원장과 파생 뷰형

모든 사건·결정·실험·결과·자산 적용을 시간순 변경 사건으로 보존하고, 현재 교리·자산·보고서는 그 원장에서 계산되는 파생 뷰로 만든다.

**장점**

- 무엇이 언제 왜 바뀌었는지 재구성하기 강하다.
- 삭제·철회·대체·모델 변경의 영향 분석에 유리하다.
- 과거 판정을 새 기준으로 다시 평가할 수 있다.

**한계**

- 모든 것을 사건으로 모델링하면 초기 복잡성이 높다.
- 현재 프로젝트가 필요한 소수 자산을 받는 제품 경험이 뒤로 밀릴 수 있다.
- 구현 기술 선택이 설계 전체를 지배하기 쉽다.
- 사용자가 원한 ‘다음 행동 변화’보다 기록 완전성이 목적이 될 위험이 있다.

### 7.4 대안 D: 계보형 선례·자산 포트폴리오형

원근거 계보, 조건부 선례, 실행 자산, 적용·평가 결과를 서로 다른 책임으로 유지하되 하나의 중앙 관계망에서 연결한다. 프로젝트는 모든 과거를 받지 않고 현재 맥락에 맞는 ‘전통 전달 묶음’을 받는다.

**장점**

- 규칙이 되지 않은 경험과 실행 가능한 자산을 모두 보존한다.
- 사실에서 행동, 행동에서 결과까지 계보를 잃지 않는다.
- 프로젝트 전용·종류 공통·전체 공통을 권위가 아니라 적용 범위로 다룰 수 있다.
- 모순과 반례를 자산의 적용 경계로 보존한다.
- 오케스트레이터와 독립된 중앙 핵심을 먼저 시험할 수 있다.

**한계**

- 개념 관계가 많아져 과잉 스키마와 관료주의 위험이 있다.
- 좋은 검색·선택이 없으면 계보만 풍부한 문서 창고가 된다.
- 자산의 범위와 증거를 판단하는 사람 승인 부담이 생긴다.
- 첫 구현 범위를 엄격히 제한하지 않으면 전체 플랫폼으로 팽창한다.

### 8.2 주설계

**대안 D, ‘계보형 선례·자산 포트폴리오’를 주설계로 선택한다.**

선택 이유는 다음과 같다.

1. 사용자의 목적은 행동 패치만이 아니라 여러 프로젝트와 AI 세대의 공동 경험 전체를 연결하는 것이다.
2. 사실·결정·실험·성공·실패·반례가 곧바로 동일한 산출물로 정제되지 않아도 가치를 유지해야 한다.
3. 다음 프로젝트에는 전체 기록이 아니라 현재 조건에 맞는 소수의 실행 자산과 근거·반례·검증 기준이 필요하다.
4. 모델과 도구가 바뀌면 과거 자산을 그대로 복사하지 않고 이주 시험해야 한다.
5. 프로젝트 전용 기억의 분리와 중앙 비교를 동시에 지원해야 한다.

### 8.3 선택하지 않은 대안에서 유지할 요소

- **A에서 유지:** 작은 활성 자산 목록, 명확한 버전·상태·폐기, 현재 작업에 소수만 전달하는 원칙

- **C에서 유지:** 변경 이력의 비가역적 추적, 과거 판정 재구성, 삭제·철회 파급 경로

| 12. 안전·삭제 | 무엇을 격리·삭제·철회해야 하는가? | 파생 영향 추적, 오염 차단, 최소권한 |

## 10. 핵심 정보와 관계

### 10.1 최소 개념 집합

다음은 논리적 개념이며 정확한 스키마는 미정이다.

- **Project**: 독립 목적·비밀·이해관계·예산을 가진 작업 맥락
- **Task**: 프로젝트 안의 목표 단위
- **Run/Attempt**: 특정 구성으로 수행한 한 번의 시도
- **Team Configuration**: 인간 역할, 모델·버전, 도구, Skill, 기억 상태, 오케스트레이션, 평가·승인 정책의 묶음
- **Evidence**: 원파일, 로그, 테스트, 외부 평가, 사람 수정 등 판단 근거
- **Observation**: 무엇이 일어났다는 보고 또는 관찰
- **Decision**: 당시 맥락·대안·선택·이유
- **Experiment**: 사전 가설·조건·측정·중단 기준이 있는 비교 또는 변화 시험
- **Outcome**: 품질, 실패, 성공, 근접 실패, 비용, 지연, 외부 평가
- **Contribution**: 인간·AI·도구가 한 기여와 수정
- **Claim**: 경험을 설명하는 인과·판단 가설
- **Case/Precedent**: 맥락·판단·이유·반례를 갖춘 조건부 참고 사례
- **Asset**: 실제 작업을 바꾸는 Skill, 프롬프트, 체크리스트, 테스트, 템플릿, 행동 규칙 등
- **Application**: 특정 프로젝트가 자산을 제안받고 사용·거부·변형·오적용한 사건
- **Evaluation**: 적용 결과가 기대와 비용·위험에 미친 영향
- **Scope**: 프로젝트 전용, 프로젝트 종류 공통, 전체 공통 등의 적용 범위
- **Permission/Restriction**: 접근·전달·외부 공개 가능 범위
- **Revision/Retirement**: 대체·축소·중지·폐기와 이유
- **Brand Claim**: 외부에 표현하려는 주장과 그 내부 근거

### 10.2 핵심 관계

- Run은 특정 Team Configuration을 사용한다.
- Evidence는 Run, Decision, Experiment, Outcome을 뒷받침하거나 반박한다.
- Claim은 하나 이상의 Evidence에서 파생되지만 Evidence와 동일하지 않다.
- Case는 Claim과 맥락·판단·반례를 묶는다.
- Asset은 하나 이상의 Case·Claim·Evidence에서 파생될 수 있다.
- 한 Case가 여러 Asset을 낳을 수 있고, 한 Asset이 여러 Case에 의해 지지될 수 있다.
- Application은 Asset 버전과 프로젝트 맥락을 연결한다.
- Evaluation은 Application의 결과를 기록하며 Asset의 신뢰·범위·상태를 바꿀 수 있다.
- Counterexample은 Claim이나 Asset을 자동 폐기하지 않고 적용 경계를 좁히거나 경쟁 선례를 만든다.
- Deletion 또는 Withdrawal은 파생 관계를 따라 전달·검색·브랜드 표현에 영향을 준다.

### 10.3 고정 수명주기를 거부하는 이유

`사실 → 경험 → 교훈 → 교리 → 자산` 한 줄 사다리는 설명이 단순하지만 다음을 잃는다.

- 중요한 결정이 규칙이 되지 않아도 보존할 가치
- 성공 원인이 불분명한 사례의 보류 상태
- 한 사건에서 여러 경쟁 가설이 생기는 경우
- 한 자산이 여러 사례와 반례에 의해 계속 수정되는 관계
- 프로젝트 전용 선례가 공통화되지 않고도 다른 프로젝트의 참고가 되는 경우

따라서 주설계는 **분기형 계보**를 사용한다. 경험은 사례로만 남을 수도 있고, 평가법·테스트·프롬프트·금지 규칙 등 서로 다른 자산으로 분기할 수도 있다.

**[핵심 결정 D5]** 분기형 생명주기를 채택한다.  
**재검토 조건:** 사용자가 상태와 관계를 이해하기 어렵고 AI 자동화도 일관된 판정을 못하며, 단순 사다리와 비교해 오류·비용 감소가 없을 때 단순화한다.

## 11. 프로젝트·작업·실행·모델·도구 계보

### 11.1 실행을 해석하는 기본 단위

과거 결과를 모델 하나의 성능으로 해석하지 않기 위해 각 Run은 최소한 다음 구성의 영향을 받은 것으로 본다.

- 사람의 역할과 사전 판단
- 모델·버전과 시스템 지침
- 사용한 Skill·프롬프트·기억 판본
- 도구·실행 환경·외부 데이터
- 오케스트레이션 정책과 AI 역할 관계
- 평가자·테스트·승인 정책
- 예산·시간·위험·고객 제약

이는 모든 세부를 완벽히 고정해야 한다는 뜻이 아니다. 함께 바뀐 요소를 숨기지 않아 인과 주장 강도를 낮출 수 있게 하는 것이 목적이다.

### 11.2 방향 변경과 시도 연결

- 같은 Task의 반복 시도는 선후 관계와 변경 요소를 연결한다.
- 방향 전환은 이전 시도를 실패로 덮지 않고 당시 정보에서 왜 합리적이었는지 보존한다.
- 중단된 시도도 비용·불확실성 감소·후속 선택권을 남겼는지 기록한다.
- 결과물 판본과 이를 만든 Run을 연결한다.
- 사람 수정은 ‘최종 결과’에 흡수하지 않고 어떤 AI 출력의 어떤 한계를 보완했는지 남긴다.

### 11.3 독립 증거 판정

같은 원자료를 여러 AI가 요약하거나 같은 모델·프롬프트로 반복 생성한 결과는 독립 증거 수를 늘리지 않는다. 중앙은 최소한 다음 상관 가능성을 표시한다.

- 동일 원자료
- 동일 모델 계열 또는 동일 평가자
- 동일 프롬프트·Skill·검색 결과
- 서로의 답을 본 후 작성한 합성 결과
- 동일 사람의 승인 편향

**[설계자의 추론]** 독립성은 개수보다 오류 상관의 차이로 판단해야 한다.

## 12. 성공·실패·결정·실험·반례 처리

### 12.1 과정과 결과의 2×2

| 과정 | 결과 | 기본 처리 |
|---|---|---|
| 좋음 | 좋음 | 재현 후보, 원인·조건 확인 |
| 좋음 | 나쁨 | 환경 변화, 평가 오류, 운, 제약 조사 |
| 나쁨 | 좋음 | 운 좋은 성공 또는 근접 실패, 승격 보류 |
| 나쁨 | 나쁨 | 교정 후보, 기여 요인과 방어책 검토 |

### 12.2 성공

성공은 재현 가능한 Skill의 증거일 수 있지만 자동 승격 대상은 아니다.

- 사전 기대와 실제 결과를 분리한다.
- 어떤 과정이 성공에 기여했다는 근거를 확인한다.
- 같은 결과를 다른 경로로 얻었는지 비교한다.
- 외부 평가와 내부 자기평가를 구분한다.
- 원인이 불명확하면 ‘성공 사례·원인 미확인’ 상태로 남긴다.

### 12.3 실패와 근접 실패

- 개인 비난보다 당시 선택을 합리적으로 보이게 한 조건을 기록한다.
- 단일 root cause를 강제하지 않고 기여 요인을 보존한다.
- 중대한 보안·비밀·품질 문제는 정기 회고를 기다리지 않고 즉시 격리한다.
- 고의적 위반이나 법적 책임 판단은 학습 분석과 별도 절차로 둔다.

### 12.4 결정

결정은 결과의 정답 보증이 아니라 당시 맥락의 기억이다.

- 문제와 제약
- 고려한 대안
- 선택과 이유
- 반대 의견과 불확실성
- 재검토 조건
- 이후 결과와 대체 결정

### 12.5 실험

중요한 실험은 결과 전에 가설, 비교 조건, 주 지표, 중단 조건, 비용 예산, 허용 결론 범위를 정한다. 결과 뒤에 만든 설명은 사후 가설로 표시하고 다음 시험 대상으로 남긴다.

### 12.6 반례

반례는 기존 공통 원칙을 즉시 삭제하거나 최신 결과로 덮는 신호가 아니다. 다음 중 하나로 처리한다.

- 적용 조건을 좁힌다.
- 프로젝트 종류별로 분기한다.
- 모델·도구별 어댑터 문제로 본다.
- 경쟁 선례를 병존시킨다.
- 중대한 위험이면 임시 중지 후 검토한다.
- 기존 원칙의 핵심 가설이 무너졌으면 대체·폐기한다.

## 13. 프로젝트 전용·종류 공통·전체 공통의 관계

### 13.1 세 범위

1. **프로젝트 전용**: 고객·도메인·코드베이스·팀·비밀·특정 제약에 묶인 기억과 자산
2. **프로젝트 종류 공통**: 비슷한 작업군, 위험, 산출물, 도구 환경을 공유하는 프로젝트군의 조건부 자산
3. **전체 공통**: 도메인이 달라도 적용 가능하다고 시험된 품질·검증·보안·인계 방식의 핵심

### 13.2 범위는 권위가 아니다

전체 공통은 프로젝트 전용보다 ‘더 참’이거나 자동 우선이라는 뜻이 아니다. 범위는 적용 가능성의 주장이고, 권고 강도와 증거 확실성은 별도 축이다.

예를 들어:

- 전체 공통이지만 증거가 약한 저비용 경고가 있을 수 있다.
- 프로젝트 전용이지만 강한 native test로 검증된 필수 절차가 있을 수 있다.
- 전체 공통 자산이 프로젝트 native 절차와 충돌하면 자동으로 덮지 않는다.

### 13.3 범위 이동

- 프로젝트 전용 자산은 다른 프로젝트에서 우선 ‘참고 선례’로만 전달된다.
- 실제 전이가 일어나면 프로젝트 종류 공통 후보가 된다.
- 서로 다른 조건·모델에서 반복되고 반례 검토를 통과한 뒤에만 전체 공통 후보가 된다.
- 구체 횟수나 임계값은 현재 정하지 않는다.
- 음의 전이나 조건 차이가 나타나면 다시 범위를 축소한다.

### 13.4 프로젝트 자율성 보호

- 프로젝트는 중앙 자산을 거부할 수 있다.
- 중앙은 거부를 비준수로 자동 해석하지 않는다.
- 프로젝트가 중앙 자산을 변형하면 핵심 기능과 변경 이유를 구분한다.
- 탐색 프로젝트에는 일부 공통 자산을 의도적으로 적용하지 않는 안전한 샌드박스가 허용될 수 있다.

**[핵심 결정 D4]** 범위와 권위를 분리한다.  
**재검토 조건:** 사용자와 AI가 두 축을 지속적으로 혼동해 잘못된 적용이 반복되면 표현을 단순화하거나 범위 명칭을 바꾼다.

## 14. 여러 프로젝트 비교와 공통화·분기·모순 처리

### 14.1 비교 단위

비슷함은 제목이나 키워드만으로 판단하지 않는다. 최소한 다음 차원을 비교한다.

- 작업 유형과 산출물
- 실패·성공의 위험 수준
- 모델·도구·오케스트레이션 구성
- 데이터·고객·법적 제약
- 시간·예산·사람 숙련
- 검증 방식과 피드백 지연
- 적용한 자산과 변형 정도
- 결과와 최악 사례

### 14.2 공통화 절차

1. 유사 사건 또는 성공 패턴 후보를 발견한다.
2. 동일 원자료·모델·평가자에 따른 상관을 제거한다.
3. 공통 핵심과 프로젝트별 차이를 분리한다.
4. 경쟁 인과 가설과 반례를 함께 둔다.
5. 공통화의 이득과 선택 부담을 비교한다.
6. 프로젝트 종류 공통 후보로 제한 시험한다.
7. 다른 모델·조건에서 전이 결과를 회수한다.
8. 유지·분기·범위 축소·폐기를 결정한다.

### 14.3 모순 처리

모순은 투표, 최신순, 더 강한 모델의 의견으로 제거하지 않는다.

- 사실관계가 다른지 확인한다.
- 평가 기준과 성공 정의가 다른지 확인한다.
- 모델·도구·시점·위험 수준의 차이를 찾는다.
- 같은 조건에서도 결과가 갈리면 불확실성을 유지한다.
- 조건부 경쟁 선례를 병존시키고 선택 시 차이를 노출한다.

### 14.4 중앙집중과 탐색 감소 방지

- 공통 자산의 적용은 기본 제안이지 절대 명령이 아니다.
- 복잡·창의·고위험 과제에서는 중앙 자산을 보기 전 독립 초안을 허용한다.
- 중앙 자산이 없는 탐색 결과도 가치 있는 사례로 수집한다.
- 사용률이 높다는 이유만으로 자산의 권위를 올리지 않는다.
- 모든 프로젝트가 같은 자산을 사용해 오류 상관이 커지는지 정기적으로 본다.
- 경쟁 자산이나 소수 선례를 보존할 수 있다.

**[설계자의 추론]** 중앙 시스템은 다양성을 제거하는 표준화 엔진이 아니라, 다양성의 비용과 위험을 관찰하면서 검증된 부분만 제한적으로 재사용하는 포트폴리오여야 한다.

## 15. Skill·프롬프트·체크리스트·테스트·템플릿·행동 규칙의 생명주기

### 15.1 자산 유형

- **Skill**: 목적·입력·행동·완료 기준을 묶은 실행 절차
- **프롬프트**: 특정 모델·역할에 전달하는 표현 또는 지시
- **체크리스트**: 중요한 누락을 막는 확인 목록
- **테스트**: 결과 또는 행동의 합격·회귀를 판정하는 장치
- **템플릿**: 반복 산출물의 구조와 필수 정보를 보존하는 틀
- **행동 규칙**: 특정 조건에서 수행·금지·검토를 요구하는 규칙
- **판단 기준**: 선택이나 검토 때 비교할 기준

### 15.2 자산 구조의 핵심

각 자산은 최소한 다음 의미를 가져야 한다.

- 해결하려는 문제와 핵심 기능
- 적용 조건과 금지 조건
- 대상 범위
- 근거와 반례
- 모델·도구 의존성
- 기대 이익과 예상 부작용
- 사용 전후 검증 방법
- 현재 상태와 판본
- 대체·축소·폐기 이력

### 15.3 분기형 생명주기

1. **후보 생성**: 사건·성공·결정·실험에서 하나 이상의 자산 후보가 생성될 수 있다.
2. **격리 초안**: AI가 만들었거나 신뢰되지 않은 입력에서 파생된 자산은 활성화되지 않는다.
3. **프로젝트 한정 파일럿**: 안전한 조건에서 제한적으로 사용한다.
4. **평가**: 검색, 채택, 정확한 실행, 효과, 비용, 부작용을 분리한다.
5. **범위 결정**: 프로젝트 전용 유지, 종류 공통 후보, 전체 공통 후보 중 하나를 선택한다.
6. **이주 시험**: 모델·도구 변경 시 핵심 기능과 표현을 다시 검증한다.
7. **유지·적응·중지·폐기**: 결과에 따라 상태와 범위를 바꾼다.

모든 경험이 이 경로를 끝까지 지나야 하는 것은 아니다. 사례나 결정으로만 남는 것도 정상이다.

### 15.4 핵심 기능과 어댑터

모델 중립적으로 유지할 수 있는 핵심 기능과 모델·도구별 표현을 분리한다.

예:

- 핵심 기능: 중요한 가정을 실행 전에 명시하고 반증 기준을 둔다.
- 모델별 어댑터: 특정 모델이 이를 잘 수행하도록 하는 프롬프트 형식.

새 모델이 프롬프트 없이도 핵심 기능을 잘 수행하면 어댑터는 폐기할 수 있지만 핵심 검증 기준은 남을 수 있다.

### 15.5 native 자산 우선

프로젝트에 이미 더 강한 테스트·체크리스트·절차가 있으면 중앙은 중복 자산을 만들지 않는다. 중앙은 다음 중 하나를 한다.

- native 자산을 프로젝트 전용으로 참조한다.
- 공통 핵심만 추출하고 프로젝트 구현은 그대로 둔다.
- 중앙 자산이 더 약하면 전달하지 않는다.

## 16. 검색·선택·전달·거부·변형·결과 회수 흐름

### 16.1 의미상 요청

프로젝트 또는 Project Brain은 실제 API가 아니라 다음 의미를 중앙에 전달한다고 가정한다.

- 현재 목표와 작업 유형
- 중요한 제약과 위험
- 모델·도구·오케스트레이션 상태
- 필요한 기억의 종류: 사례, 금지조건, Skill, 테스트, 결정 근거 등
- 공개 가능한 프로젝트 정보 범위

### 16.2 중앙 선택

1. 접근권한과 프로젝트 경계를 적용한다.
2. 중지·폐기·삭제된 자산을 기본 검색에서 제외한다.
3. 현재 조건과 유사한 사례와 자산을 찾는다.
4. 반례·경쟁 선례·금지 조건을 함께 찾는다.
5. 프로젝트 native 자산과 충돌·중복을 확인한다.
6. 자산 수를 제한하고 선택 이유를 만든다.

### 16.3 전통 전달 묶음

정확한 파일·메시지 형식은 정하지 않지만 의미상 다음을 포함한다.

- 현재 과제에 왜 관련 있는지
- 추천 자산 또는 참고 사례
- 적용 조건과 사용 금지 조건
- 핵심 근거와 반례
- 필요한 사람 승인
- 실행 후 확인할 테스트·관찰
- 오래됨·불확실성·모델 의존 경고

### 16.4 프로젝트 응답

프로젝트는 다음 중 하나를 선택한다.

- 채택
- 거부
- 일부 채택
- 변형 적용
- 잘못 이해하거나 오적용
- 적용하지 못함

거부와 변형은 실패가 아니라 중요한 피드백이다. 이유를 가능한 범위에서 회수한다.

### 16.5 결과 회수

검색 실패, 채택 실패, 실행 실패, 자산 실패를 구분한다.

| 실패 위치 | 의미 |
|---|---|
| 검색 실패 | 필요한 자산이 있었지만 찾지 못함 |
| 선택 실패 | 관련 없는 자산을 추천하거나 더 나은 후보를 제외함 |
| 채택 실패 | 적절한 자산이었지만 전달·비용·신뢰 문제로 선택되지 않음 |
| 실행 실패 | 핵심 기능대로 사용되지 않음 |
| 자산 실패 | 정확히 사용했지만 결과가 나쁨 |
| 평가 실패 | 성공 기준이나 측정이 부적절함 |

**[핵심 결정 D6]** 자산만 전달하지 않고 근거·반례·금지조건·검증을 포함한 작은 묶음을 전달한다.  
**재검토 조건:** 묶음의 길이와 복잡성 때문에 채택률·정확한 실행이 낮아지고, 더 짧은 전달 방식보다 성과가 나쁘면 위험 기반으로 축약한다.

**[핵심 결정 D7]** 사용·거부·변형·오적용을 별도 결과로 회수한다.  
**재검토 조건:** 이 구분이 자산 선택·개선·비용 판단에 실제 차이를 만들지 않으면 필드를 합친다.

## 17. 모델·도구·오케스트레이션 변경과 계승

### 17.1 교체가 아니라 이주

새 모델은 단순 업그레이드가 아니다. 기존 Skill, 프롬프트, 오류 감지 방식, 도구 사용, 사람의 기대와 상호작용이 바뀔 수 있다. 따라서 변경은 다음을 포함하는 이주로 다룬다.

1. 바뀐 구성 요소를 식별한다.
2. 영향을 받을 자산과 평가를 계보로 찾는다.
3. 대표 과제와 최악 사례를 선택한다.
4. 기존 자산 없음·기존 자산 사용·변형 자산 사용을 가능한 범위에서 비교한다.
5. 핵심 기능과 모델별 표현을 분리한다.
6. 유지, 어댑터 수정, 범위 축소, 폐기를 결정한다.

### 17.2 능력 경계 원장

영구적인 ‘AI가 잘하는 일’ 목록 대신 다음 조건별 관찰을 유지한다.

- 과제 유형
- 모델·버전
- 도구·환경
- 사용 자산
- 사람 숙련과 승인 방식
- 평가 시점
- 성공·실패·최악 사례

### 17.3 인과 주장 강도

모델, 도구, 사용자 숙련, 데이터, 자산이 동시에 바뀌면 전통 단독 효과를 주장하지 않는다. ‘구성 전체의 성과가 변했다’고 보고하고, 분리가 가능한 후속 시험을 제안한다.

### 17.4 오케스트레이터 변화

중앙은 특정 Brain 메시지나 역할 수에 의존하지 않는다. 오케스트레이션이 바뀌어도 다음 의미만 유지되면 된다.

- 프로젝트 상황을 설명할 수 있음
- 중앙 자산 요청과 수신이 가능함
- 사용·변형·결과를 반환할 수 있음
- 사람 승인과 책임 위치를 구분할 수 있음

## 18. 자동화와 사람 승인

### 18.1 자동화 원칙

자동화는 기본값이지만 권한과 위험에 비례한다. 목표는 사람이 모든 기록을 읽는 체계도, AI가 자기 교리를 자동 승인하는 체계도 아니다.

### 18.2 자동화하기 적합한 작업

- 구조화 후보 추출
- 중복·유사 사례 군집화
- 사실·해석·제안 혼합 경고
- 근거 링크와 파생 관계 후보 생성
- 반례·모순·오래됨 탐지
- 접근권한에 따른 후보 필터
- 검색 후보 순위화
- 사용·거부·변형 결과 집계
- 비용·재사용·미사용 자산 요약
- 삭제·철회 영향 범위 후보 계산

### 18.3 사람 승인 없이는 활성화하지 않을 것

- 전체 공통 자산의 효력 발생
- 고위험 프로젝트에 적용하는 금지·필수 규칙
- 프로젝트 간 비밀 또는 민감 정보 공유
- 외부 브랜드 주장과 사례 공개
- 중요한 범위 확대·폐기·철회
- 삭제 의무와 보존 의무가 충돌하는 판단
- 고객 품질에 영향을 줄 수 있는 실험 조건 배정

### 18.4 조건부 자동화 가능 영역

저위험·가역적·프로젝트 내부 자산은 사용자가 미리 승인한 정책과 테스트를 충족하면 제한 자동 적용을 실험할 수 있다. 그러나 현재는 미검증 제안이며 기본값으로 확정하지 않는다.

### 18.5 승인 부하 관리

- 모든 원자료가 아니라 변화·위험·모순 중심으로 사람에게 보여준다.
- 승인 요청에는 선택지, 근거, 반례, 되돌리기 비용을 함께 제공한다.
- 반복 저위험 판단은 사전 승인 정책으로 위임할 수 있다.
- 인간 능동시간을 시스템 비용으로 측정한다.

**[핵심 결정 D8]** 공통 규칙·고위험 적용·외부 공개는 사람 승인 없이는 활성화하지 않는다.  
**재검토 조건:** 충분한 운영 증거가 쌓인 저위험 영역에서 사람 승인 비용이 실질 이득을 지속적으로 압도하면 제한 위임 범위를 확대할 수 있다. 고위험·비밀·외부 책임 영역은 별도 판단한다.

## 19. 개인정보·비밀·삭제·권한·기억 오염

### 19.1 기본 원칙

- 프로젝트 정보는 기본적으로 프로젝트 전용이다.
- 중앙 비교는 가능한 한 비식별·추상화된 특성으로 수행한다.
- 원비밀을 공통 자산에 복사하기보다 제한된 근거 포인터 또는 비식별 파생만 사용한다.
- 외부 문서와 AI 생성 회고는 신뢰되지 않은 입력에서 시작한다.

### 19.2 신뢰 영역

의미상 최소한 다음 영역을 구분한다.

1. 프로젝트 비밀 원자료
2. 프로젝트 내부 정제 기억
3. 프로젝트 간 공유 가능한 비식별 사례
4. 공통 자산 후보 격리 영역
5. 사람 승인된 활성 공통 자산
6. 외부 공개 승인 뷰

정확한 저장 위치나 기술은 미정이다.

### 19.3 명령과 데이터 분리

외부 문서, 코드 주석, 이메일, 로그에 포함된 명령형 문장은 중앙 시스템의 운영 명령이 아니라 분석 대상 데이터로 취급한다. 자산 후보로 승격하려면 출처·권한·검토·시험을 거쳐야 한다.

### 19.4 삭제와 철회

- 삭제 요청 또는 법적 의무가 원근거에 적용되면 파생 자산과 브랜드 표현을 추적한다.
- 삭제해야 할 내용은 역사 보존 원칙보다 우선한다.
- 가능한 경우 내용은 삭제하고 ‘삭제로 인해 근거가 더 이상 사용 불가’라는 비식별 상태만 남긴다.
- 근거가 철회되면 해당 자산을 즉시 중지하거나 근거 수준을 낮춘다.
- 삭제가 다른 근거로 독립적으로 지지되는 자산까지 자동 폐기하는지는 별도 판단한다.

### 19.5 기억 오염 대응

- 신뢰되지 않은 입력은 격리한다.
- 출처 없는 교훈은 권위를 갖지 않는다.
- 비밀 제거와 프롬프트 주입 검사를 하나의 AI 판단에만 의존하지 않는다.
- 중대한 오염이 의심되면 관련 검색·전달을 중지한다.
- 파생 관계를 따라 영향받은 자산과 외부 표현을 찾는다.

**[핵심 결정 D9]** 프로젝트 기본 격리와 파생 삭제 추적을 채택한다.  
**재검토 조건:** 실제 법적·기술적 환경에서 파생 추적이 불가능하거나 유지비가 과도하면 중앙이 보관하는 원자료 범위를 더 줄이고 프로젝트 포인터 중심으로 축소한다.

## 20. 사건 기반 갱신과 월간 종합

### 20.1 사건 기반 빠른 순환

다음은 월간 종합을 기다리지 않는다.

- 비밀·개인정보 노출
- 프롬프트 주입 또는 기억 오염
- 중대한 품질·안전 회귀
- 공통 자산의 명백한 음의 전이
- 근거 삭제·철회
- 모델·도구 변경으로 기존 검증이 무효화됨

흐름은 `탐지 → 전달 중지 또는 격리 → 사람 판단 → 임시 방어 → 영향 범위 확인 → 회귀시험 → 유지·수정·폐기`다.

### 20.2 월간 또는 정기 종합의 책임

- 여러 프로젝트의 반복 패턴과 모순 확인
- 실제 재사용과 미사용 자산 확인
- 검색 실패·거부·변형·오적용 원인 확인
- 비용·사람 능동시간·재작업 변화 확인
- 범위 확대·축소 후보 검토
- 경쟁 선례와 탐색 다양성 확인
- 시스템 자체의 기준과 자동화가 왜곡을 만드는지 검토
- 브랜드 주장과 내부 근거의 일치 확인

### 20.3 변경 없음

근거가 부족하면 `변경 없음`이 정상 결과다. 월간 산출물 수, 교훈 승격 수, 자산 생성 수를 성과 할당량으로 두지 않는다.

### 20.4 메타 순환

모델 교체, 프로젝트 종류 확대, 반복적 검색 실패, 운영비 악화가 있을 때는 검색·평가·승격 기준 자체를 재검토한다. 이는 현재 규칙 안에서 오류를 고치는 것뿐 아니라 규칙과 목표가 맞는지 묻는 순환이다.

**[핵심 결정 D10]** 사건 fast loop와 정기 slow loop를 분리한다.  
**재검토 조건:** 두 순환의 산출물과 판단이 대부분 중복되거나 정기 종합이 실제 공통화·폐기에 기여하지 않으면 빈도와 범위를 줄인다.

## 21. 공동 브랜드의 내부 근거와 외부 표현

### 21.1 내부 브랜드 근거

브랜드의 실체는 다음의 장기 계보다.

- 반복되는 품질 기준
- 사실·추론·제안 구분
- AI 기여와 사람 수정·승인 구분
- 성공·실패·반례·폐기 이력
- 모델 교체 뒤 검증과 이주
- 비용·재작업·중단의 투명성
- 비밀·책임·사용자 가치 우선

### 21.2 외부 표현

외부 사례, 포트폴리오 설명, 제안서, 브랜드 문구는 내부 근거에서 승인된 제한 뷰로 만든다.

- 공개 가능한 근거만 사용한다.
- AI가 한 기여와 사람이 검토·수정·승인한 범위를 과장하지 않는다.
- 성공 사례만 골라 장기 효과를 주장하지 않는다.
- 폐기와 수정 능력을 실패 은폐가 아니라 품질 특징으로 표현할 수 있다.
- 인과가 불분명하면 구성 전체의 관찰 결과로만 말한다.

### 21.3 브랜드 주장 상태

- 내부 근거 충분·외부 공개 승인
- 내부 근거 있으나 비밀로 공개 불가
- 관찰은 있으나 인과 미확인
- 과거에는 유효했으나 현재 철회
- 서사 후보이나 근거 부족

**[핵심 결정 D12]** 외부 브랜드는 내부 근거의 승인된 투영으로만 만든다.  
**재검토 조건:** 외부 이해관계자에게 실질 가치가 없거나 공개 준비 비용·비밀 위험이 크면 브랜드 기능을 후순위로 축소한다. 내부 작업 계보는 유지한다.

## 22. 비용·품질·재사용·전이·위험 평가

### 22.1 평가 범주

| 범주 | 예시 질문 |
|---|---|
| 품질 | 합격 조건, 결함, 외부 평가, 최악 사례가 개선됐는가? |
| 시간 | 벽시계 시간과 사람 능동시간이 어떻게 변했는가? |
| 비용 | 토큰, 구독, 현금, 재작업, 대기, 기회비용은 얼마인가? |
| 검색 | 필요한 자산을 찾았는가, 오검색은 없었는가? |
| 채택 | 제안된 자산을 왜 채택·거부했는가? |
| 실행 충실도 | 핵심 기능대로 사용했는가, 무엇을 변형했는가? |
| 효과 | 사용했을 때 결과가 실제로 좋아졌는가? |
| 유지 | 시간이 지나거나 모델이 바뀌어도 이득이 남는가? |
| 전이 | 동일 작업, 가까운 과제, 다른 프로젝트, 다른 모델 중 어디까지 유효한가? |
| 위험 | 음의 전이, 비밀, 보안, 오류 상관, 탐색 감소가 생겼는가? |
| 운영비 | 중앙 관리 시간이 실제 프로젝트를 방해하는가? |

### 22.2 증거 확실성과 행동 강도 분리

- **증거 확실성**: 근거와 재현·전이 결과를 얼마나 믿는가
- **행동 강도**: 비용·위험·가역성을 고려할 때 얼마나 강하게 적용할 것인가

약한 증거라도 저비용 보안 차단은 임시 강한 조치가 될 수 있고, 강한 평균 효과가 있어도 비싼 자산은 선택 옵션일 수 있다.

### 22.3 반사실과 비교

가능한 범위에서 다음을 구분한다.

- 전통 없음
- 원로그 또는 원사례만 제공
- 정제된 선례·자산 제공
- 모델 자체 변경
- 사람 숙련 또는 도구 변경

완전한 실험이 불가능하면 함께 바뀐 요소를 기록하고 인과 주장을 낮춘다.

### 22.4 지표 게임 방지

- 문서 수, 자산 수, 사용률을 최종 성과로 두지 않는다.
- 사용률이 높아도 효과가 없으면 성공이 아니다.
- 평균 향상과 함께 최악 오류·재작업·중대 위험을 본다.
- AI 평가자끼리의 합의를 독립 검증으로 세지 않는다.
- 평가 기준 자체의 오염과 포화를 점검한다.

## 23. 필수 사용 상황 10개의 처음부터 끝까지 흐름

### 23.1 프로젝트 하나가 완료되고 성공·실패·결정·비용·AI 기여가 들어온다

- **입력:** 프로젝트 범위, 주요 Task와 Run, 결과물, 성공·실패, 결정, 비용, 사람 수정, AI·도구 기여, 접근 제한
- **중앙 판단:** 원근거와 해석을 분리하고 누락·비밀·중복 파생을 확인한다. 모든 항목을 교훈으로 만들지 않는다.
- **AI 역할:** 구조화 후보, 결정·사건·비용·기여 연결, 잠재 사례와 자산 후보 제안
- **사람 승인:** 공유 범위, 민감 정보 처리, 중요한 해석과 자산 파일럿 여부
- **결과:** 프로젝트 계보, 보존할 사례, 보류된 가설, 제한 자산 후보, 비용 원장
- **실패·복구:** 원자료가 불완전하면 확인되지 않은 보고로 남기고 확정 사실로 승격하지 않는다. 비밀 제거가 불가능하면 중앙에는 제한 포인터와 최소 메타정보만 둔다.

### 23.2 성공했지만 원인이 불분명하다

- **입력:** 좋은 결과, 사용 구성, 과정 관찰, 비교 기준 부족
- **중앙 판단:** ‘성공 사례·원인 미확인’으로 보존하고 행동 규칙 자동 생성은 보류한다.
- **AI 역할:** 가능한 인과 가설과 대체 설명, 재현 시험 후보, 운 좋은 성공 위험 제시
- **사람 승인:** 재시험 비용이 가치 있는지, 안전한 내부 조건에서 시험할지 결정
- **결과:** 사례는 브랜드·비교 계보에 남지만 활성 자산은 생성되지 않거나 프로젝트 한정 실험 후보만 생성
- **실패·복구:** 나중에 반례가 나오면 성공을 삭제하지 않고 원인 가설과 범위를 수정한다.

### 23.3 세 프로젝트에서 비슷한 실패가 나타나지만 모델·도구·조건이 다르다

- **입력:** 각 프로젝트의 실패 사례, 구성, 제약, 검증 결과
- **중앙 판단:** 표면 유사성과 공통 기여 요인을 분리한다. 같은 원자료 또는 같은 평가자의 상관을 제거한다.
- **AI 역할:** 공통 핵심 후보, 조건 차이, 경쟁 가설, 기존 반례 탐색
- **사람 승인:** 프로젝트 종류 공통 후보로 제한 시험할지 결정
- **결과:** 하나의 범용 교리 대신 공통 핵심과 조건별 분기 자산 또는 ‘공통 원인 미확인’ 상태
- **실패·복구:** 공통화 자산이 한 프로젝트에서 악화시키면 즉시 범위를 축소하고 경쟁 선례를 복원한다.

### 23.4 기존 공통 원칙과 반대되는 결과가 한 프로젝트에서 나온다

- **입력:** 공통 원칙, 반대 결과, 프로젝트 조건, 사용 충실도, 평가 근거
- **중앙 판단:** 오적용·측정 오류·환경 차이·실제 반례를 구분한다.
- **AI 역할:** 원칙의 적용 조건과 이번 조건 비교, 반례 강도와 영향 범위 제안
- **사람 승인:** 임시 중지, 범위 축소, 경쟁 선례 병존, 폐기 중 선택
- **결과:** 원칙이 유지되더라도 반례와 금지 조건이 함께 전달됨
- **실패·복구:** 중대한 위험이면 판정 전에도 전달을 중지한다. 반례가 약하면 보류 상태로 남기되 삭제하지 않는다.

### 23.5 새 모델로 교체되며 기존 Skill과 프롬프트가 필요한지 모른다

- **입력:** 이전·새 Team Configuration, 영향받는 자산, 대표 과제, 과거 실패·최악 사례
- **중앙 판단:** 모델 중립 핵심 기능과 모델별 표현을 분리한다.
- **AI 역할:** 이주 시험 후보, 불필요해진 프롬프트, 새 오류 가능성 제안
- **사람 승인:** 시험 범위·비용·중단 조건과 새 기본 자산 판본
- **결과:** 유지, 어댑터 수정, 핵심만 유지, 범위 축소, 폐기 중 하나
- **실패·복구:** 모델과 도구가 동시에 바뀌면 전통 효과를 분리해 주장하지 않고 구성 전체 변화로 보고한다.

### 23.6 프로젝트 전용 지식을 다른 프로젝트가 요청한다

- **입력:** 요청 프로젝트 맥락, 원 프로젝트 지식, 접근권한·비밀 제한
- **중앙 판단:** 원문 전달 가능 여부와 추상화·비식별 가능성을 확인한다. 범위가 넓어진다고 권위가 높아지는 것은 아니다.
- **AI 역할:** 공유 가능한 핵심, 제외해야 할 비밀, 적용 차이와 재시험 항목 제안
- **사람 승인:** 프로젝트 간 공유와 변형된 전달 내용
- **결과:** 원자료가 아니라 제한된 참고 선례 또는 프로젝트 종류 공통 후보가 전달될 수 있음
- **실패·복구:** 안전한 추상화가 불가능하면 거부하고 존재 여부와 이유만 반환한다.

### 23.7 근거가 삭제·철회되거나 비밀정보 문제가 발견된다

- **입력:** 삭제·철회 대상, 법적·계약상 의무, 파생 관계
- **중앙 판단:** 영향받은 사례·Claim·Asset·Application·Brand Claim을 추적한다.
- **AI 역할:** 파급 후보 계산, 검색·전달 중지 대상, 대체 근거 존재 여부 제안
- **사람 승인:** 삭제 방식, 비식별 상태 보존, 자산 중지·폐기, 외부 정정
- **결과:** 원내용 삭제 또는 접근 차단, 파생 자산 상태 변경, 외부 표현 정정
- **실패·복구:** 파생 관계가 불완전하면 관련 범위를 넓게 임시 중지하고 수동 감사한다.

### 23.8 중앙 자산을 프로젝트가 거부·변형·오적용한다

- **입력:** 전달 자산, 선택 결과, 변경 내용, 실행 결과, 프로젝트 이유
- **중앙 판단:** 검색·채택·충실도·자산 자체 실패를 분리한다.
- **AI 역할:** 거부 이유 군집화, 핵심 기능 보존 여부, 전달 방식 문제와 자산 문제 구분
- **사람 승인:** 자산 수정·범위 변경·전달 축약·사용자 교육·폐기
- **결과:** 변형판이 새 프로젝트 전용 자산이 되거나 원자산의 금지 조건이 갱신됨
- **실패·복구:** 오적용이 중대 위험을 만들면 자산 전달을 즉시 중지하고 사용 전 확인 절차를 강화한다.

### 23.9 사용자가 지난 기간의 반복 패턴·실제 재사용·비용 변화·작업방식 변화를 묻는다

- **입력:** 기간, 프로젝트 범위, 비용·품질·자산 사용·모델 변화 기록
- **중앙 판단:** 모델·도구·사용자 숙련 변화와 전통 효과를 구분 가능한 범위에서 분리한다.
- **AI 역할:** 반복 패턴, 실제 사용된 자산, 미사용·폐기, 비용 변화, 반례, 인과 불확실성 요약
- **사람 승인:** 외부 공개 여부와 해석 강도
- **결과:** 문서량이 아니라 행동 변화·재사용·전이·비용·위험 중심의 기간 보고
- **실패·복구:** 기준선이 없거나 구성 변화가 너무 크면 인과 주장을 하지 않고 관찰된 변화만 보고한다.

### 23.10 월간 종합 시 변경할 충분한 근거가 없다

- **입력:** 기간 내 사건·성공·결정·자산 적용·비용·반례
- **중앙 판단:** 표본 부족, 모순 미해결, 효과 없음, 새로운 정보 없음 중 이유를 구분한다.
- **AI 역할:** ‘변경 없음’ 근거와 다음 관찰 포인트 제안
- **사람 승인:** 기존 상태 유지, 추가 실험 여부, 종합 빈도 조정
- **결과:** 승격·자산 생성 없이 상태 유지가 정식 결과로 기록됨
- **실패·복구:** 변화 할당량 때문에 억지 자산이 생성되지 않도록 승인 화면과 지표에서 ‘변경 없음’을 정상 처리한다.

## 24. 목표 제품과 첫 구현 범위의 분리

### 24.1 목표 제품

목표 제품은 다음 전체 순환을 책임진다.

`여러 프로젝트의 근거 수집·분리 → 계보 연결 → 사례·결정·실험·반례 해석 → 조건부 선례·자산 관리 → 현재 맥락 검색·선택 → 안전한 전달 → 프로젝트의 채택·거부·변형 → 적용 결과 평가 → 범위·상태·신뢰 변경 → 모델 이주·정기 종합·브랜드 근거`

### 24.2 단계적 구축

단계적 구축은 목표 능력을 위험과 가설 순서대로 검증하는 과정이다. 각 단계에서 전체 개념을 별도 구현하지 않는다. 필요한 관계만 최소 표현하고, 가치가 확인될 때 확장한다.

### 24.3 첫 구현 범위

첫 구현은 전체 제품의 축소판 데이터베이스가 아니라, 가장 중요한 가설을 시험하는 **작은 세로 왕복**이어야 한다.

- 원근거와 해석을 구분할 수 있는가?
- 프로젝트 경계를 지킬 수 있는가?
- 한 조건부 자산을 근거와 연결할 수 있는가?
- 다른 가상 프로젝트 요청에 적절히 전달·거부할 수 있는가?
- 사용·변형·반례 결과가 자산 상태를 바꿀 수 있는가?
- 삭제·철회가 파생 전달을 막을 수 있는가?

### 24.4 축소할 때 잃는 목적

| 축소 | 얻는 단순성 | 잃는 사용자 목적 |
|---|---|---|
| 자산 레지스트리만 유지 | 사용이 쉬움 | 성공·결정·실험·반례와 이유의 장기 계보 |
| 원로그만 저장 | 정제 비용 감소 | 다음 AI의 빠른 선택과 행동 변화 |
| 프로젝트별 완전 분리 | 비밀·자율성 강화 | 프로젝트 간 비교·공통화·공동 브랜드 |
| 전체 공통 규칙만 유지 | 전달 단순화 | 프로젝트별 조건·다양성·탐색 |
| 사람 승인 제거 | 속도 향상 | 비밀·위험·가치·책임 통제 |
| 모든 판단 사람 수동 | 자동 오승격 감소 | AI 측 계승 능력과 1인 지속 가능성 |
| 적용 결과 회수 생략 | 운영비 감소 | 잘못된 자산 수정·폐기와 실질 학습 |
| 브랜드 기능 제거 | 공개 위험 감소 | 공동 작업 방식의 장기 외부 표현 |

## 25. 오케스트레이터 없이 가능한 첫 독립 구현 조각

### 25.1 이름

**계보–적용–회수 왕복 커널**

### 25.2 목적

Project Brain의 실제 통신 형식 없이도 중립적 가상 프로젝트 입력을 사용해 중앙 시스템의 핵심 주장인 ‘근거가 자산으로 연결되고, 현재 맥락에 선택되어 전달되며, 적용 결과가 다시 자산을 바꾼다’를 한 바퀴 시험한다.

### 25.3 포함 범위

1. 소수의 사전 작성된 중립 가상 프로젝트 사례 입력
2. 프로젝트 식별과 접근 범위
3. 원근거·관찰·해석·자산 후보의 최소 구분
4. 한 개 이상의 조건부 자산과 근거·반례 연결
5. 다른 가상 프로젝트의 의미상 요청
6. 권한·상태·적용 조건에 따른 전달 또는 거부
7. 채택·거부·변형·오적용 중 하나의 결과 회수
8. 평가 결과에 따른 유지·범위 축소·중지
9. 근거 철회 시 후속 전달 차단 확인

### 25.4 제외 범위

- 실제 Project Brain 연결
- 실시간 이벤트 처리
- 벡터 검색·RAG·특정 DB 선택
- 대시보드와 외부 브랜드 페이지
- 자동 공통화와 자동 승인
- 실제 고객·프로젝트 데이터
- 장기 효과 또는 비용 우위 주장
- 멀티 AI 오케스트레이션 성능 평가

### 25.5 이 조각이 증명하려는 것

- 핵심 개념 관계가 모순 없이 왕복 가능한가?
- 프로젝트 경계와 철회가 전달보다 우선하는가?
- 자산 상태가 적용 결과에 의해 실제로 바뀌는가?
- 고정 승격 사다리 없이도 사실에서 행동까지 계보가 유지되는가?
- 같은 입력에 대한 판정이 설명 가능하고 재현 가능한가?

### 25.6 증명하지 못하는 것

- 실제 프로젝트에서 품질·시간·비용이 개선되는가
- AI 자동 추출과 검색이 정확한가
- Project Brain과의 통신이 안정적인가
- 월간 종합이 장기 복리 효과를 만드는가
- 공동 브랜드가 고객 신뢰를 높이는가
- 한 사람 규모에서 운영비가 감당 가능한가

**[핵심 결정 D11]** 첫 조각을 계보–적용–회수 왕복 커널로 정한다.  
**재검토 조건:** 설계 검토 결과 이 조각이 단순 스키마 검증에 머물러 핵심 전이·철회 가설을 시험하지 못하거나, 반대로 너무 많은 개념을 요구해 독립적으로 완성하기 어렵다면 범위를 다시 잘라야 한다.

## 26. 단위 시험·가상 흐름 시험·향후 효과 시험

### 26.1 단위 시험

**증명하려는 것**

- 상태 전이와 권한 규칙의 일관성
- 근거 없는 자산 활성화 방지
- 폐기·중지 자산의 기본 검색 제외
- 파생 관계와 철회 영향 추적
- 범위와 권위의 분리
- 사용·거부·변형·오적용 결과의 구분
- 같은 원자료에서 나온 AI 요약을 독립 증거로 중복 계산하지 않음

**증명하지 못하는 것**

- 실제 검색 적중률
- AI 추출 정확도
- 인간 승인 부담
- 실제 품질·비용·전이 효과

### 26.2 가상 프로젝트 흐름 시험

사전 작성된 서로 다른 조건의 가상 프로젝트를 사용해 필수 사용 상황 일부와 전체 왕복을 시험한다.

**증명하려는 것**

- 한 프로젝트의 자산이 다른 프로젝트에 자동 유출되지 않음
- 비식별·제한 전달과 거부가 가능함
- 반례가 자산의 범위·상태를 바꿈
- 모델 변경 상황에서 핵심 기능과 어댑터를 구분할 수 있음
- ‘변경 없음’이 정상 종료가 됨
- 사용자의 승인 지점이 지나치게 많거나 빠진 곳이 없는지 발견

**증명하지 못하는 것**

- 실제 AI와 사람이 같은 방식으로 행동함
- 가상 데이터의 난이도가 현실을 대표함
- 장기적인 반복 사용과 기억 오염
- 운영비 대비 가치

### 26.3 향후 실제 효과 시험

안정된 실제 과제군과 기준선이 생긴 뒤에만 수행한다.

가능한 비교는 다음과 같다.

- 전통 없음 vs 원로그 검색 vs 정제 선례·자산
- 현재 모델 vs 다른 모델, 각각 전통 있음·없음
- 동일 프로젝트 재사용 vs 가까운 전이 vs 다른 프로젝트 전이 vs 모델 이주

**증명하려는 것**

- 중앙 전통이 모델·도구 자체 변화 외에 추가 이득을 주는가
- 품질·시간·사람 수정·비용·최악 오류가 개선되는가
- 정제 비용이 원로그 검색보다 정당화되는가
- 음의 전이와 오류 상관이 통제 가능한가

**증명하지 못할 수 있는 것**

- 표본이 적으면 장기 일반 법칙
- 사용자 숙련과 전통 효과의 완전한 인과 분리
- 모든 프로젝트 종류에 대한 범용성
- 수년 단위 복리 성장과 브랜드 효과

## 27. 단계별 로드맵과 단계별 중단 조건

### 단계 0. 설계 동결과 결정 감사

- **시작 조건:** 독립 제안서 작성 완료
- **산출물:** 핵심 결정, 미정 사항, 첫 조각 경계, 반증 조건
- **중단 조건:** 최초 목적을 충족하지 못하거나 Project Brain 규격을 암묵적으로 고정함
- **다음 조건:** 사용자 가치 판단과 주설계 승인

### 단계 1. 계보–적용–회수 왕복 커널

- **시작 조건:** 최소 개념과 상태 전이 합의
- **산출물:** 중립 가상 입력으로 작동하는 작은 중앙 코어
- **중단 조건:** 핵심 관계가 모순되거나 프로젝트 경계·철회가 보장되지 않음
- **다음 조건:** 단위 시험과 설명 가능성 통과

### 단계 2. 필수 사용 상황 가상 흐름

- **시작 조건:** 커널 안정
- **산출물:** 10개 상황의 가상 시나리오 판정 기록과 실패 복구
- **중단 조건:** 사람 승인점 과다, 상태 폭증, 같은 상황에 비일관 판정
- **다음 조건:** 핵심 흐름을 단순화해도 목적 유지

### 단계 3. 오케스트레이터 없는 수동 실제 프로젝트 파일럿

- **시작 조건:** 비밀 없는 자체 개발·연습 프로젝트, 기준선, 사용자 승인
- **산출물:** 실제 프로젝트 1개 이상의 수동 입력·검색·적용·회수 경험
- **중단 조건:** 중앙 관리시간이 가치보다 크거나 원로그 대비 이득 가능성이 없음
- **다음 조건:** 반복 과제와 신선한 비교 사례 확보

### 단계 4. 프로젝트 종류 간 제한 전이 시험

- **시작 조건:** 최소 두 조건에서 비교 가능한 자산과 평가
- **산출물:** 프로젝트 전용 유지·종류 공통화·분기 판단 근거
- **중단 조건:** 음의 전이, 비밀 위험, 선택 부담이 개선보다 큼
- **다음 조건:** 제한된 공통 자산의 반복 이득

### 단계 5. Project Brain 의미 어댑터 설계·연결

- **시작 조건:** 원천 오케스트레이터의 Brain 책임과 통신 경계가 안정됨
- **산출물:** 중앙 내부와 분리된 교환 어댑터 및 실패 격리
- **중단 조건:** 중앙 핵심이 오케스트레이터 내부 형식에 종속됨
- **다음 조건:** 수동 경로와 자동 경로의 동등성·감사 가능성

### 단계 6. 모델 이주와 자동화 확대

- **시작 조건:** 대표 과제·최악 사례·비용 기준선 존재
- **산출물:** 모델 교체 이주 시험, 제한 자동 분류·검색·회수
- **중단 조건:** 새 모델에서 자산이 음의 전이를 만들거나 자동화가 오승격을 늘림
- **다음 조건:** 사람 능동시간 감소와 품질·위험 비악화

### 단계 7. 정기 종합과 내부 브랜드 계보

- **시작 조건:** 여러 프로젝트·자산 적용 이력과 철회 사례 존재
- **산출물:** 반복 패턴·비용·전이·폐기 보고, 내부 브랜드 근거
- **중단 조건:** 정기 종합이 문서 할당량이 되거나 인과 과장 발생
- **다음 조건:** 실제 외부 표현 가치와 공개 가능 근거 존재

### 단계 8. 제한된 외부 브랜드 표현

- **시작 조건:** 사용자 승인, 비밀 제거, 반복 가능한 내부 근거
- **산출물:** 정직한 외부 사례와 작업 방식 설명
- **중단 조건:** 홍보 압력이 내부 근거·불확실성·폐기 이력을 왜곡

## 28. 시스템 전체의 축소·폐기 조건

### 28.1 기능 축소 조건

- **검색 효과 부족:** 자산 포트폴리오를 줄이고 프로젝트별 핵심 사례 색인만 유지
- **정제 가치 부족:** 복잡한 선례 정제를 중단하고 원로그+최소 메타정보와 테스트만 유지
- **공통화 음의 전이:** 전체 공통 범위를 중지하고 프로젝트 종류별 또는 프로젝트 전용으로 축소
- **승인 부하 과다:** 저위험 자동화와 변화 중심 승인으로 단순화하거나 수집 범위를 축소
- **비밀·삭제 위험:** 중앙 원자료 보관을 중단하고 프로젝트 측 포인터와 비식별 파생만 유지
- **정기 종합 무가치:** 사건 기반 처리와 모델 이주 검토만 남김
- **브랜드 가치 부족:** 외부 표현 기능을 폐기하고 내부 계보만 유지

### 28.2 전체 폐기 조건

다음이 반복 시험에서도 지속되면 중앙 시스템 전체를 폐기하거나 단순 기록 체계로 되돌린다.

1. 원로그 또는 기존 프로젝트 문서보다 다음 행동을 더 잘 바꾸지 못한다.
2. 사람 능동시간과 운영비가 절감한 재작업·위험보다 크다.
3. 음의 전이와 중앙 단일문화 위험을 통제할 수 없다.
4. 프로젝트 비밀·삭제 의무를 안전하게 지키지 못한다.
5. 모델 교체 시 자산 이주가 거의 항상 무가치하다.
6. 사용·거부·변형 결과가 자산 개선으로 이어지지 않는다.
7. 시스템 유지가 실제 프로젝트 수행을 지속적으로 방해한다.

### 28.3 폐기 시 보존

법적·비밀 의무를 침해하지 않는 범위에서 다음만 남길 수 있다.

- 왜 폐기했는지
- 어떤 가설이 반증됐는지
- 어떤 범위에서만 유효했는지
- 다시 시도하려면 무엇이 달라져야 하는지

현재 근거로는 다음을 확정하지 않는다.

- 월간 종합의 고정 빈도와 시간
- 공통화·승격·폐기의 수치 임계값
- 첫 실제 실험의 과제 수와 통계 기준
- 사용할 모델·평가자·도구 조합
- 자동 비식별·비밀 탐지의 신뢰 수준
- 저위험 자동 적용 범위
- 장기 보존 기간과 백업 정책
- 브랜드 공개 채널과 정량 약속
- 월 손실 허용액이 학습 투자로 인정되는 자동 기준
- 오케스트레이터의 현재 개발 incident를 전통 효과 증거로 사용하는 것

이 사항들은 구현 편의가 아니라 실제 기준선·위험·비용·운영 결과를 본 뒤 결정해야 한다.

## 30. 사용자 승인과 가치 판단이 필요한 사항

1. 프로젝트 간 기본 공유 정책: 완전 격리, 비식별 공유 허용, 종류별 허용 범위
2. 어떤 정보를 절대 중앙화하지 않을지
3. 비밀 제거 후에도 남는 재식별 위험 허용 수준
4. 전체 공통 자산의 승인 기준과 사용자 승인 부담 한도
5. 고위험 작업의 정의와 필수 인간 검토 범위
6. 자동화가 틀렸을 때 허용 가능한 손실과 되돌리기 시간
7. 사람 능동시간·토큰·현금 중 어떤 비용을 더 중시할지
8. 탐색 다양성을 위해 중앙 자산을 일부러 보지 않는 조건을 허용할지
9. 실제 고객·공모전 프로젝트에서 관찰만 허용할지, 안전한 내부 비교를 어디까지 허용할지
10. 외부 브랜드에 AI 기여·사람 수정·실패·폐기를 어느 수준까지 공개할지
11. 근거 부족 상태에서 임시 보안 규칙을 얼마나 강하게 적용할지
12. 어떤 결과가 나오면 시스템을 축소·중단할지
13. 공동 브랜드가 실제 수익·고객 가치보다 낮은 우선순위임을 유지할지
14. 헌장의 목적과 가치 순서를 변경할 사유가 생겼을 때 변경 절차

본 설계는 현재 헌장에 대한 이의를 제기하지 않는다. 목적·철학은 주설계와 양립한다. 다만 실제 운영에서 1인 승인 비용이 과도하게 나타나면 하위 승인 구조를 먼저 단순화해야 하며, 그것만으로 해결되지 않을 때 사용자와 헌장 변경 여부를 별도로 검토해야 한다.

## 32. 이 설계의 가장 큰 위험과 반증 조건

### 32.1 가장 큰 위험

가장 큰 위험은 **계보와 조건을 정교하게 관리한다는 명분 아래 중앙 시스템이 사실상 권위 있는 표준화 관료제가 되어, 여러 프로젝트의 탐색을 줄이고 같은 오류를 넓게 퍼뜨리면서도 문서·관계·승인 수가 많아 이를 ‘성장’으로 오인하는 것**이다.

이 위험은 두 방향에서 동시에 발생한다.

- **인지적 위험:** 중앙의 정제된 설명이 원사례의 불확실성과 소수 반례를 지우고, 여러 AI가 같은 자산을 사용해 오류 상관을 높인다.
- **운영 위험:** 사용자는 계보·승인·월간 종합을 관리하느라 실제 프로젝트보다 개선 체계를 더 많이 운영하게 된다.

### 32.2 방어 원칙

- 공통화는 권위가 아니라 범위 주장으로 취급한다.
- 프로젝트는 거부·변형할 수 있다.
- 중앙 자산을 보기 전 독립 탐색이 필요한 과제군을 둔다.
- 반례와 경쟁 선례를 기본 검색 후보에 포함한다.
- 문서 수 대신 실제 적용·효과·폐기·비용을 본다.
- ‘변경 없음’과 시스템 축소를 정상 선택으로 둔다.
- 원로그·단순 검색·정제 자산을 실제로 비교한다.

### 32.3 핵심 반증 조건

다음 중 하나가 반복되면 주설계를 축소하거나 기각한다.

1. 정제 선례·자산이 원로그 검색보다 신선한 과제에서 낫지 않다.
2. 프로젝트의 거부·변형 이력이 다음 검색과 자산 개선에 유의미한 차이를 만들지 않는다.
3. 공통 자산 사용 프로젝트에서 오류 상관과 음의 전이가 증가한다.
4. 모델 이주 시험에서 핵심 자산의 추가 효과가 지속적으로 사라진다.
5. 중앙 관리에 쓰는 사람 능동시간과 비용이 실제 재작업·위험 감소보다 크다.
6. 비밀·삭제·오염 파급을 신뢰성 있게 통제하지 못한다.
7. 문서·자산·승인 수는 늘지만 품질·시간·비용·위험이 개선되지 않는다.
8. 프로젝트 탐색 다양성과 native 자산이 중앙 규칙 때문에 지속적으로 약화된다.

이 설계는 여러 프로젝트·여러 AI 세대의 공동 경험과 작업 전통을 출처·맥락·결정·구성·반례·적용 결과가 끊기지 않는 계보형 증거와 조건부 선례·실행 자산으로 보존하고, 다음 프로젝트에는 현재 조건에 맞는 소수의 자산과 검증 기준만 선택해 전달한 뒤 그 사용·변형·거부·성과를 다시 계보에 회수함으로써 더 나은 행동으로 되돌린다.
