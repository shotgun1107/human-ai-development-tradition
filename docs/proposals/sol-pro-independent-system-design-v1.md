### 1.2 이해한 현재 상태

전통 연구는 원본 AI 오케스트레이터와 분리된 설계 프로젝트다. 원본 오케스트레이터에는 B1 순차 실행 구성요소와 smoke test가 있으나 전체가 안정적인 운영 체계라는 증거는 없고, B0/B1 반복 비교도 완료되지 않았다. 현재 incident는 개발·테스트 기록이며 전통 운영 효과의 증거가 아니다. 따라서 이 문서는 실제 운영 성과, 비용 절감, 전이 효과 또는 T0 결과를 전제하지 않는다. 지금 수행할 범위는 연구·기획·시스템 설계이며 구현·코드·저장소 변경은 포함하지 않는다. fileciteturn0file1 fileciteturn0file5 fileciteturn0file2

## 2. 설계 요약

### 2.1 한 문장 설계

**원자료를 여러 단계의 교리 체계로 정제해 쌓는 대신, 미래 작업의 특정 결정을 바꾸는 소수의 출처 연결 `행동 패치`와 그 결과를 남기는 `적용 영수증`만 운영한다.**

여기서 패치는 코드 패치가 아니라, 특정 조건에서 작업 방식·검사·프롬프트·중단 기준을 작게 바꾸는 가역적 변경 단위다.

### 2.2 기존 초안과 가장 크게 다른 결정

| 변화 | 이 설계의 선택 |
|---|---|
| 객체 수 | `근거 메모`, `행동 패치`, `적용 영수증`의 세 단위만 둔다. 별도 `lesson`, `doctrine`, `application`, `evaluation`, `review` 객체를 기본으로 만들지 않는다. |
| 수명주기 | 사실→경험→교훈→교리의 고정 사다리를 거부하고, “다음 결정을 바꿀 수 있는가”를 기준으로 바로 테스트·체크리스트·프롬프트·예시 중 가장 싼 표현으로 분기한다. |
| 운영 주기 | 매월 60~90분의 전면 회고 대신 사건·trial·모순·모델 변경이 있을 때만 여는 짧은 정비 창을 사용한다. 월간 확인은 시간 상한을 둔 안전망일 뿐이다. |
| 증거·상태 | 단일 E0~E4 점수 대신 `증거 프로필`과 `행동 강도`를 분리한다. 상태는 `draft / trial / active / off` 네 개만 사용한다. |
| 범용 지식·브랜드 | 범용 지식을 별도 상위 저장소로 만들지 않고 범위 조건이 넓어진 패치로 취급한다. 공동 브랜드도 별도 서사 문서가 아니라 검증·철회·비용 공개의 반복 증거를 모은 뷰로 본다. |

### 2.3 가장 큰 비용·위험·미확인 가정

1. 패치를 지나치게 짧게 만들면 원사건의 예외와 맥락이 손실될 수 있다.
2. 정확한 태그·범위 조건만으로 필요한 패치를 찾지 못하면 최소 검색 방식이 실패할 수 있다.
3. 한 사람의 반복 과제는 표본이 작고 사용자 숙련이 함께 변하므로 인과 추론이 제한된다.
4. 사람 승인자가 같은 사람이므로 검토 분리가 형식화될 위험이 있다.
5. “정제된 패치”가 원자료 검색이나 한 장짜리 체크리스트보다 낫다는 증거는 아직 없다.

> **주요 결정 D1 — 전통의 중심을 지식 축적이 아니라 다음 행동의 작은 변경으로 둔다.**
>
> **근거:** 헌장은 기록량이 아니라 다음 AI의 행동 차이, 검색·적용·재현·수정·폐기를 전통의 가치로 규정한다. 조사 문서도 기록이 필요한 순간에 행동을 바꾸지 않으면 기억이 아니며, AI 성찰은 외부 검증 없이 증거가 아니라고 경고한다. fileciteturn0file7 fileciteturn0file3
>
> **추론:** 개인 시스템에서 먼저 최적화할 것은 문서의 완전성이 아니라 “무슨 미래 결정을 어떻게 다르게 할 것인가”다.
>
> **제안:** 모든 기록·승격·검색·평가를 `행동 패치` 단위로 묶고, 미래 결정과 연결되지 않는 경험은 원자료 포인터로만 남긴다.
>
> **반증 조건:** 패치 중심 방식이 원자료 기반 방식보다 중요한 예외를 더 자주 누락하거나, 실제 작업 품질을 낮추거나, 유지비를 줄이지 못하면 세 단위 모델을 폐기하고 더 단순한 원자료+체크리스트 방식으로 돌아간다.

## 3. 합리적 가정

이 설계는 추가 질문 없이 다음을 가정한다.

1. 주 사용자는 한 명이며 최종 목적·예산·위험·외부 책임을 가진다.
2. AI 모델은 교체 가능하고 세션 간 동일한 인격이나 가중치 학습을 전제하지 않는다.
3. 초기 저장 수단은 로컬 Markdown과 기존 원자료 포인터로 충분하며 새 서비스가 필요하지 않다.
4. 고객·외부 이해관계자에게 영향을 줄 수 있는 열등한 조건은 실험에 배정하지 않는다. 실험은 자체 개발, 연습, 병렬 초안, 납품 전 내부 검토로 격리한다.
5. 민감한 원문은 기존 보안 위치에 남고, 전통에는 비식별 요약 또는 제한 포인터만 들어간다.
6. 정확한 수치 임계값은 현재 근거가 없으므로 초기값은 운영 제안으로만 두고 T0 기준선 뒤 조정한다.
7. 오케스트레이터가 안정화되지 않으면 전통 T0도 시작하지 않는다. 현재 incident는 양식 리허설에만 사용할 수 있다.

## 4. 문제 정의와 비목표

### 4.1 해결할 문제

| 문제 | 실패 양상 |
|---|---|
| 세션·모델 단절 | 이전 AI가 이미 발견한 오류·검사법·판단 근거가 다음 AI에게 전달되지 않는다. |
| 로그와 행동의 단절 | 원자료가 있어도 작업 시작 시 검색되지 않거나 실행 산출물로 변환되지 않는다. |
| 거짓 학습 | 성공의 원인을 잘못 추론하거나 우연한 결과를 규칙으로 만들고, 반례를 누락한다. |
| 음의 전이 | 특정 프로젝트·모델에 맞는 규칙이 다른 맥락에 자동 적용되어 품질·비용·안전을 악화시킨다. |
| 한 사람의 운영비 | 기록·등급·회의·버전 관리가 실제 프로젝트보다 무거워진다. |
| 인과 혼동 | 더 좋은 모델, 새 도구, 사용자 숙련 향상을 전통의 효과로 잘못 계산한다. |
| 공동 브랜드의 신화화 | 반복 가능한 품질과 책임 증거 대신 AI 인격·성공 서사·문서량이 브랜드를 대체한다. |

### 4.2 비목표

이 설계는 다음을 목표로 하지 않는다.

- 모델 파인튜닝, 가중치 업데이트, 지속 인격 보존
- 모든 대화·로그·고객 자료의 장기 보관
- 개인 성장 일기나 사용자 숙련 점수화
- incident 하네스, B1 코드, benchmark 또는 기준선 문서 변경
- 매월 교훈·교리 수를 의무 생산하는 운영
- 범용 교리집, 지식 그래프, 대시보드, 벡터 DB를 선행 구축하는 일
- AI 다수결을 독립 증거로 취급하는 일
- 고객 납품물을 열등할 수 있는 실험 조건에 배정하는 일
- 공동 브랜드를 법적 공동 책임자 또는 AI 인격 주장으로 만드는 일

## 5. 핵심 철학

### 5.1 해석한 핵심 철학

이 전통의 성장 단위는 모델 자체가 아니라 인간의 목적·승인, AI의 생성·비평·검색, 외부 기억, 도구, 평가가 결합된 작업 구성이다. 새 세션이나 새 모델이 검증된 작업 방식을 더 적은 시행착오로 재현할 때 계승이 관찰된다. 구성을 분리할 수 없으면 “전통이 원인”이라고 말하지 않고 그 구성 전체의 성과만 보고한다. fileciteturn0file7

이 설계는 다음 여섯 원칙을 채택한다.

1. **분류보다 결정:** 어떤 객체인지보다 다음 작업의 어떤 판단을 바꿀지 먼저 묻는다.
2. **일반화보다 범위:** 넓은 규칙보다 적용 조건과 금지 조건을 먼저 보존한다.
3. **증거와 강제력 분리:** 근거가 약해도 피해가 크고 조치가 싼 경우 임시 차단은 가능하지만, 그 차단을 검증된 효과라고 부르지 않는다.
4. **성공과 실패 대칭:** 좋은 결과만으로 좋은 과정을 추정하지 않고, 실패만으로 하나의 근본 원인을 확정하지 않는다.
5. **철회 가능성이 브랜드:** 잘못된 패치를 공개적으로 끄고 이유를 남기는 능력이 공동 브랜드의 일부다.
6. **전통도 비용을 입증:** 시스템이 더 단순한 대안보다 낫지 않으면 축소·폐기한다.

### 5.2 공동 브랜드의 운영적 정의

공동 브랜드를 별도 “브랜드 지식” 객체로 저장하지 않는다. 다음 사실을 프로젝트와 모델이 달라도 반복해서 보여주는지를 보는 `브랜드 증거 뷰`로 정의한다.

- 출처 없는 주장을 전통으로 포장하지 않는다.
- 사실·추론·제안과 AI 기여·인간 승인을 구분한다.
- 중대 결함·비밀·비용·재작업을 숨기지 않는다.
- 잘못된 패치를 `off`로 돌리고 대체 이유를 남긴다.
- 더 강한 모델도 동일한 acceptance 기준으로 재검증한다.
- 고객 가치와 의무를 내부 학습보다 우선한다.

헌장은 공동 브랜드를 특정 모델 이름이나 인격이 아니라 품질 기준·검증 태도·Skill 계보·책임 방식의 반복 흔적으로 정의한다. fileciteturn0file7

> **주요 결정 D2 — 공동 브랜드를 별도 서사 저장소가 아니라 검증 가능한 운영 증거의 뷰로 둔다.**
>
> **근거:** 기준선 헌장은 브랜드가 선언이 아니라 서로 다른 프로젝트와 모델에서 반복된 품질·정직성·검증·책임의 흔적이어야 한다고 규정한다. 2차 조사도 브랜드 유산을 작업 방식의 계보로 해석하되 성공 신화만 편집하면 학습을 방해한다고 경고한다. fileciteturn0file7 fileciteturn0file3
>
> **추론:** 별도 브랜드 문서나 점수는 운영 증거보다 먼저 신화와 Goodhart 효과를 만들 가능성이 높다.
>
> **제안:** 브랜드는 `적용 영수증`, 중대 오류, 철회 이력, 비용 공개, 모델 이주 결과를 읽어 만든 보고 뷰로만 존재한다.
>
> **반증 조건:** 실제 외부 평가에서 운영 증거만으로는 공동 작업 방식의 일관성을 설명할 수 없고, 별도 최소 서사가 오해를 줄이면서도 성과를 왜곡하지 않는다는 증거가 생기면 제한된 브랜드 설명서를 추가한다.

## 7. 개념 모델과 시스템 경계

### 7.1 경계

이 시스템은 기존 원자료 저장소를 대체하지 않는다. 원본 incident, 실험 결과, 결정 기록, diff, 고객 승인, acceptance 결과는 각 원래 위치에 남는다. 전통 시스템은 그 원자료를 복제하는 저장소가 아니라, 승인된 비식별 포인터와 미래 행동의 작은 변경을 연결하는 얇은 계층이다.

```text
[기존 원자료·결정·시험]
          │
          │ 출처 확인 + 사람 redaction
          ▼
     [근거 메모]
       │      └── 미래 결정을 바꾸지 못함 ──> 원자료 포인터만 유지
       │
       │ 조건·행동·반증 기준으로 컴파일
       ▼
     [행동 패치] ──> 체크 / 테스트 / 프롬프트 조각 / 예시 / 임시 차단
       │
       │ 범위 필터 + 사람 승인 + 제한 주입
       ▼
       [AI·인간 공동 작업]
       │
       │ 적용·변형·건너뜀·결과
       ▼
     [적용 영수증]
       │
       └── 유지 / 범위 축소 / 수정 / off / 원자료 재검토
```

민감한 원문과 외부 문서는 이 흐름 바깥의 제한 영역에 남는다. 검색 대상은 redaction을 통과한 메모와 사람 승인 패치뿐이다. 출처가 철회되면 그 출처에 의존한 패치는 검색 전에 무효화한다.

### 7.2 행위자와 책임

| 구성요소 | 할 수 있는 일 | 할 수 없는 일 |
|---|---|---|
| 인간 소유자 | 목표·범위·위험·예산 설정, redaction, 패치 효력 승인, 외부 결과 승인, 폐기 | AI 출력이나 과거 패치를 검증 없이 승인된 사실로 간주 |
| AI 분석자 | 원자료 요약 초안, 사실/추론 분리 제안, 반례·중복 검색, 패치·테스트 초안 | 출처 없는 사실 생성, 상태 변경, 범위 확대, 비밀 공개 결정 |
| AI 실행자 | 현재 과제에 맞는 패치 호출, 적용·변형·건너뜀 제안, 테스트 수행 | 검색된 문서를 상위 명령으로 취급, `off` 패치 적용, 외부 납품 승인 |
| 프로젝트 환경 | 실제 acceptance, 테스트, 비용·재작업·오류 결과 제공 | 전통의 인과 효과를 자동 입증 |
| 전통 등록부 | 출처, 범위, 판본, 상태, 철회, 적용 결과 연결 | 원자료 전체 보존, 모델 인격 보존, 자동 학습 |

> **주요 결정 D4 — 전통은 원자료 저장소 위의 얇은 행동 변경 계층으로 제한한다.**
>
> **근거:** 1차 조사는 원사건·맥락·검증을 보존하되 데이터베이스 자체를 학습으로 보지 않으며, 2차 조사는 기록이 실제 검색·적용·시험으로 행동을 바꿔야 기억이라고 본다. 기존 설계 초안도 원자료를 복제하기보다 포인터와 판본을 연결하는 방향을 제시한다. fileciteturn0file4 fileciteturn0file3 fileciteturn0file6
>
> **추론:** 원자료와 전통을 합치면 보안 범위가 넓어지고, 정제 계층이 원본을 대체해 사실 수정과 삭제가 어려워진다.
>
> **제안:** 원자료는 기존 위치에 두고, 전통에는 비식별 포인터·조건부 행동·결과만 둔다.
>
> **반증 조건:** 포인터 부패나 접근 불능 때문에 평가에 필요한 원자료를 반복적으로 재구성하지 못하고, 제한된 복제가 보안·운영비를 악화시키지 않는다는 증거가 생기면 선택적 스냅샷 보존을 추가한다.

## 8. 가장 작은 검증 가능 시스템

### 8.1 최소 운영 형태

구현 전 개념상 필요한 것은 **한 개의 Markdown 등록부**뿐이다. 실제 파일을 지금 만들지는 않는다. 미래 T0에서 다음 네 구역을 한 파일 안에 수작업으로 운영한다.

```text
tradition-register.md
  1. revoked / blocked sources
  2. evidence notes
  3. action patches
  4. trial use receipts
```

초기에는 별도 디렉터리, YAML 스키마, CLI, 인덱스 생성기, 데이터베이스가 없다. 문서가 불편해졌다는 관찰만으로 분리하지 않고, 검색 누락·충돌·수정 오류처럼 특정 결함이 반복될 때만 구조를 나눈다.

### 8.2 최소 검증 대상

최소 시스템은 한 번에 다음 하나만 시험한다.

- 실제 운영에서 나온 비식별 근거 메모 소수
- 한 작업 유형에 한정된 trial 행동 패치 1개
- 패치의 실행 표현 1개: 테스트, 체크리스트, 프롬프트 조각, 예시 중 하나
- fresh 내부 과제에서의 적용 영수증
- 패치 없음·원자료 메모·행동 패치 비교

이 설계는 “전통 시스템 전체”를 검증하려 하지 않는다. 첫 질문은 **정제된 행동 패치가 더 단순한 원자료 메모보다 다음 AI의 결과를 개선하는가**다.

> **주요 결정 D5 — 첫 시스템은 한 파일, 한 trial, 한 작업 유형으로 제한한다.**
>
> **근거:** 기준선은 현재 구현과 T0가 아니라 독립 설계 단계이며, 로드맵 초안도 수작업으로 필드와 가치를 확인한 뒤 반복 마찰만 자동화하라고 제안한다. 현재 데이터 구조와 사용성은 미검증이다. fileciteturn0file1 fileciteturn0file2
>
> **추론:** 여러 패치·프로젝트·상태를 동시에 열면 어떤 요소가 가치나 비용을 만들었는지 알기 어렵다.
>
> **제안:** T0는 하나의 등록부와 하나의 trial 패치만 운영하며, 시스템의 기본 대조군을 원자료 메모로 둔다.
>
> **반증 조건:** 한 파일 구조 때문에 출처 오연결·상태 혼동·검색 실패가 T0 수행 자체를 막으면, 그 결함에 필요한 최소 분리만 한다.

## 9. 기록 데이터와 지식 단위

### 9.1 공통 맥락 서명

세 단위는 모두 같은 `맥락 서명(context signature)`을 공유한다. 필드는 고정 스키마가 아니라 비교와 검색에 필요한 최소 질문이다.

| 필드 | 질문 |
|---|---|
| `project` | 어느 프로젝트에서 나온 것인가? |
| `task_family` | 어떤 반복 과제 유형인가? |
| `risk_tier` | 실패 시 영향이 낮음·중간·높음 중 무엇인가? |
| `model_tool_config` | 결과에 영향을 줄 수 있는 모델·도구·오케스트레이션 구성은 무엇인가? |
| `data_sensitivity` | 공개·내부·제한 중 어디에 속하는가? |
| `acceptance_basis` | 품질을 무엇으로 판정했는가? 테스트, 사람 검수, 고객 승인, 기타 중 무엇인가? |
| `time_context` | 언제 관찰됐고 어떤 변경 뒤 재검토가 필요한가? |

### 9.2 단위 1 — 근거 메모(Evidence Note)

근거 메모는 원자료를 대체하는 요약이 아니라, 미래 판단을 위해 원자료 위치와 확인된 관찰을 가리키는 짧은 색인이다.

| 필수 항목 | 의미 |
|---|---|
| `id` | 안정적인 로컬 식별자 |
| `source_ref` | 원자료 경로·ID·commit·hash 또는 제한 포인터 |
| `observed_fact` | 원자료가 직접 지지하는 사실 1~3문장 |
| `interpretation` | 원인·메커니즘 추정. 없으면 `unknown` |
| `future_decision` | 이 메모가 바꿀 수 있는 미래 결정. 없으면 패치 후보가 아님 |
| `context_signature` | 적용 경계를 판단할 맥락 |
| `sensitivity/redaction` | 공개 범위, 제거한 항목, 사람 검토 여부 |
| `contradicts/supports` | 기존 패치나 메모와의 관계 |

근거 메모는 사건·성공·결정·실험·근접 실패를 별도 종류로 강제하지 않는다. 필요한 경우 `event_kind` 태그를 붙일 수 있지만, 종류보다 예상·관찰·결과·과정의 차이를 적는 것이 우선이다.

### 9.3 단위 2 — 행동 패치(Action Patch)

행동 패치는 “무엇을 믿는가”보다 “어떤 조건에서 무엇을 다르게 하는가”를 표현한다.

| 필수 항목 | 의미 |
|---|---|
| `id@version` | 과거 적용을 재구성할 수 있는 판본 |
| `trigger` | 적용해야 할 관찰 가능한 조건 |
| `action` | 수행·금지·확인·중단할 한 가지 행동 |
| `do_not_apply_when` | 적용 금지·예외·충돌 조건 |
| `expected_mechanism` | 왜 도움이 될지에 대한 추론. 사실과 구분 |
| `expression` | 테스트, 체크리스트, 프롬프트 조각, 예시/반례, 임시 차단 중 하나 |
| `proof_profile` | 직접성·비교·반복·전이·신선도·반례 상태 |
| `scope` | 프로젝트·과제·위험·모델·도구 조건 |
| `state` | `draft / trial / active / off` |
| `enforcement` | `advisory / default / block` |
| `evidence/counterevidence` | 근거 메모와 반례 포인터 |
| `review_trigger` | 날짜보다 모델·도구 변경, 모순, 반복 면제, 비용 악화 등 재검토 신호 |
| `approved_by` | 사람 승인과 승인 시점 |

### 9.4 단위 3 — 적용 영수증(Use Receipt)

적용 영수증은 모든 작업 로그가 아니다. trial, 예외, 중대 결과, 사전 선정 표본에만 남긴다.

| 필수 항목 | 의미 |
|---|---|
| `task_ref/context` | 신선한 과제와 맥락 서명 |
| `patch_version` | 검색·적용된 정확한 판본 |
| `decision` | `applied / adapted / skipped / not-matched` |
| `reason` | 적용·변형·건너뜀 이유 |
| `result` | 사전 지표와 guardrail 결과 |
| `human_active_time` | 검토·수정에 든 사람 능동시간 |
| `model_cost` | 토큰·원화·대기시간 중 측정 가능한 항목 |
| `regression_or_negative_transfer` | 잘못된 적용, 중대 오류, 무관 지시 여부 |
| `confounders` | 모델·도구·난이도·사용자 숙련 등 함께 변한 요소 |
| `reviewed_by` | 사람 결과 검토 여부 |

> **주요 결정 D6 — 지식 단위를 세 개로 제한하고, 모든 단위에 같은 맥락 서명을 사용한다.**
>
> **근거:** 조사 문서는 사례 검색 시 제목보다 작업 유형·위험·도구 버전·제약·검증 방식이 중요하며, 원사건·조건·반례·적용 결과를 연결해야 한다고 본다. 동시에 기존 다층 객체의 실제 사용성은 확인되지 않았다. fileciteturn0file4 fileciteturn0file3 fileciteturn0file2
>
> **추론:** 객체마다 다른 메타데이터를 만들기보다 공통 맥락 서명을 공유하면 검색과 전이 판단을 적은 필드로 수행할 수 있다.
>
> **제안:** 근거·행동·결과의 세 단위만 유지하고, 별도 리뷰 객체는 패치의 상태 변경 이력으로 흡수한다.
>
> **반증 조건:** 모순 판정, 여러 근거의 독립성, 다중 산출물 버전 또는 감사 재구성이 세 단위 안에서 반복적으로 불가능하면 해당 관계만 별도 객체로 분리한다.

### 9.5 기록 trigger

다음 중 하나이면서 **미래의 반복 결정에 영향을 줄 가능성**이 있을 때만 근거 메모를 남긴다.

- 중대 실패·근접 실패·보안·비밀 문제
- 예상과 크게 다른 성공 또는 비용 절감
- 되돌리기 어려운 모델·도구·설계 결정
- 사전 가설이 있던 실험 결과
- 기존 패치와 충돌한 적용 결과
- 관련 패치를 찾지 못했거나 잘못된 패치가 검색된 사례
- 같은 메커니즘으로 보이는 두 번째 관찰

단순한 작업 완료, 감상, AI의 자기평가, 원자료에 이미 충분히 검색 가능한 사소한 사실은 기록하지 않는다.

> **주요 결정 D7 — 기록 여부를 사건 종류가 아니라 미래 결정 가치로 판단한다.**
>
> **근거:** 기존 플레이북도 모든 사건이 아니라 실패·중요 성공·장기 결정·실험·반복·충돌·검색 실패를 trigger로 제안하고, 사건량이 적으면 교리를 억지로 만들지 말라고 한다. 문헌은 보고량 자체가 실제 발생률이나 학습 효과가 아니라고 경고한다. fileciteturn0file0 fileciteturn0file4
>
> **추론:** 개인 시스템에서 포착량을 늘리면 검토 backlog와 생존자·보고 편향만 커질 수 있다.
>
> **제안:** “이 메모가 바꿀 미래 결정이 있는가?”에 답하지 못하면 새 전통 기록을 만들지 않는다.
>
> **반증 조건:** 미래 결정 기준 때문에 초기에 사소해 보였던 신호가 반복적으로 누락되고 뒤늦게 중대 패턴으로 드러난다면 trigger를 넓히되, 확대된 범주의 유지비를 별도로 측정한다.

## 10. 경험이 규칙·Skill·체크리스트·테스트로 변환되는 과정

### 10.1 고정 사다리 대신 분기형 컴파일

경험은 자동으로 교훈이 되지 않는다. 또한 모든 경험이 같은 중간 단계를 거칠 필요도 없다. 다음 절차는 객체 승격 사슬이 아니라, 원자료에서 가장 싼 행동 표현을 선택하는 분기다.

| 단계 | 핵심 질문 | 가능한 결과 |
|---|---|---|
| 0. 출처 고정 | 실제 원자료가 있고 비식별 가능한가? | 근거 메모 또는 제외 |
| 1. 사실 분리 | 무엇이 직접 관찰됐고 무엇이 해석인가? | 사실 수정, 해석 보류, `unknown` 허용 |
| 2. 미래 결정 검사 | 다음에 어떤 결정이 달라져야 하는가? | 결정이 없으면 메모만 유지 |
| 3. 반례·대안 검사 | 같은 결과의 다른 설명, 반대 사례, 운 좋은 성공이 있는가? | 범위 축소, 모순 집합, 후보 보류 |
| 4. 표현 선택 | 어떤 표현이 가장 싸고 검증 가능한가? | 테스트 / 체크리스트 / 프롬프트 조각 / 예시·반례 / 임시 차단 / 행동 없음 |
| 5. trial 설계 | 어디서, 무엇과 비교하고, 무엇이 실패를 뜻하는가? | trial 패치 1개와 사전 지표 |
| 6. 적용·평가 | 실제로 검색·채택·수행됐고 결과가 어땠는가? | 영수증, 유지·수정·축소·off |

### 10.2 표현 선택 규칙

| 관찰된 문제 | 우선 표현 | 이유 |
|---|---|---|
| 결정적으로 검출 가능한 결함 | 테스트 또는 자동 검사 명세 | 프롬프트보다 재현성과 실패 신호가 분명하다. |
| 사람이 반복 확인해야 하는 소수 항목 | 짧은 체크리스트 | 맥락 판단을 남기면서 누락을 줄일 수 있다. |
| 모델 출력 형식·질문 순서의 반복 문제 | 짧은 프롬프트 조각 + 예시 | 행동 지시를 최소 컨텍스트로 전달할 수 있다. |
| 복잡한 판단에서 경계 사례가 중요 | 대표 사례 1개 + 반례 1개 | 한 문장 규칙이 예외를 지우는 것을 막는다. |
| 증거는 약하지만 피해가 크고 조치가 싸고 가역적 | 만료되는 임시 `block` | 예방 원칙을 적용하되 검증된 효과로 오인하지 않는다. |
| 미래 행동을 정당화할 수 없음 | 행동 패치 없음 | 기록을 교리화하지 않는다. |

### 10.3 규칙·Skill의 관계

이 설계에서 `Skill`, 체크리스트, 테스트, 프롬프트는 독립 지식 계층이 아니다. 모두 한 행동 패치의 **실행 표현(expression)** 이다.

- 패치의 조건·의도·금지 조건이 같고 표현만 바뀌면 같은 패치 판본의 표현 수정이다.
- 기본 행동이나 안전 경계가 바뀌면 새 패치 판본을 만든다.
- 하나의 패치가 여러 표현을 가질 수 있지만 T0에서는 하나만 허용한다.
- 테스트로 강제할 수 있는 결함을 장문 프롬프트만으로 다루지 않는다.
- 프롬프트 조각이 특정 모델에만 유효하면 모델 의존 어댑터로 표시하고 핵심 규칙과 분리 여부를 나중에 판단한다.

> **주요 결정 D8 — 경험 정제는 규칙 작성이 아니라 가장 싼 검증 가능한 행동 표현을 고르는 컴파일로 본다.**
>
> **근거:** 1차 조사는 관찰이 조치와 효과 검증을 거쳐야 학습이 되며, 체크리스트 효과는 시행 맥락에 따라 달라진다고 정리한다. 2차 조사는 AI 성찰이 외부 피드백 없이 악화될 수 있고, 절차 기억·테스트·반례가 실제 적용과 함께 평가돼야 한다고 본다. fileciteturn0file4 fileciteturn0file3
>
> **추론:** “교훈 문장”을 먼저 만들면 그 문장을 정당화하기 위해 불필요한 객체와 설명이 늘어난다. 반대로 테스트·체크·예시부터 선택하면 행동과 반증이 동시에 생긴다.
>
> **제안:** 미래 결정이 명확해진 뒤 테스트→체크리스트→프롬프트→예시 순으로 가장 결정적이고 싼 표현을 선택한다. 아무 표현도 정당화되지 않으면 메모에서 멈춘다.
>
> **반증 조건:** 표현 우선 방식이 인과 이해를 지속적으로 손실시켜 잘못된 자동화나 반복 오적용을 만들고, 별도 교훈 분석 객체가 그 문제를 줄인다면 제한된 분석 단계를 추가한다.

## 11. 프로젝트 전용 지식과 범용 지식의 관계

### 11.1 범용은 상위 계층이 아니라 넓은 범위 주장

모든 행동 패치는 처음에는 관찰이 나온 프로젝트·과제·구성에 한정된다. `범용`이라는 별도 저장소나 높은 등급을 만들지 않는다. 패치의 `scope`에서 프로젝트 조건을 제거하려면 그 제거 자체를 새 trial로 취급한다.

```text
프로젝트 한정 active 패치
    │
    │ 다른 프로젝트 또는 다른 모델에서 같은 메커니즘을 사전 예측하고 시험
    ▼
넓은 범위의 새 trial 판본
    │
    ├─ 지지됨 → 범위 조건 일부 제거
    ├─ 혼합됨 → 공통 핵심 + 프로젝트/모델 어댑터 후보
    └─ 반박됨 → 기존 프로젝트 패치는 유지, 넓은 판본은 off
```

### 11.2 충돌 우선순위

현재 작업에서 충돌하면 다음 순서를 적용한다.

1. 법·계약·고객·사용자의 명시 요구, 보안·안전 제약
2. 현재 프로젝트에서 검증된 더 좁고 최신인 패치
3. 여러 프로젝트에서 시험된 넓은 범위 패치
4. trial 패치와 과거 사례
5. 모델의 일반 지식

좁은 패치가 무조건 맞다는 뜻은 아니다. 다만 현재 맥락과 직접 연결된 근거가 있는 동안 넓은 규칙이 자동으로 덮어쓰지 못하게 한다.

### 11.3 모델·도구 이주

모델·도구·SDK·오케스트레이션 정책이 패치의 메커니즘이나 표현에 영향을 줄 수 있으면 변경 시 자동으로 `trial` 재검토 대상이 된다. 모델 중립 핵심과 모델별 어댑터는 처음부터 설계하지 않는다. 두 모델 이상에서 같은 핵심 행동이 필요하지만 표현만 달라진다는 증거가 생길 때만 분리한다.

> **주요 결정 D9 — 프로젝트 지식과 범용 지식을 계층이 아니라 범위 조건의 차이로 표현한다.**
>
> **근거:** 헌장은 모든 교리를 조건부로 보고, 프로젝트·모델·시점에 따른 음의 전이와 이주 검증을 요구한다. 2차 조사는 가까운 재사용과 먼 전이·모델 이주를 다른 주장으로 구분하며, 더 세분화된 기억이 항상 유익하지 않고 음의 전이를 키울 수 있다고 경고한다. fileciteturn0file7 fileciteturn0file3
>
> **추론:** 범용을 상위 승격 상태로 만들면 넓은 적용이 명예나 성숙도로 오인돼 프로젝트 근거를 압도할 수 있다.
>
> **제안:** 범위 확대는 기존 active 패치를 수정하는 일이 아니라 별도 trial 판본을 만드는 일로 취급한다. 모델 중립 핵심도 전이 결과가 있을 때만 추출한다.
>
> **반증 조건:** 범위 조건만으로는 공통 핵심의 중복·일관성을 관리할 수 없고, 실제 전이된 패치가 충분히 쌓여 별도 공통 계층이 검색·유지비를 줄인다는 증거가 생기면 제한된 공통 핵심 레이어를 추가한다.

## 12. 증거 프로필, 행동 강도, 상태와 변경 규칙

### 12.1 단일 증거 점수를 쓰지 않는 이유

증거의 확실성과 행동 권고의 강도는 다르다. 약한 증거라도 비밀 유출처럼 피해가 크고 차단 비용이 낮으면 임시 `block`이 합리적일 수 있다. 반대로 비교 근거가 있어도 비용이 크고 맥락 의존적이면 선택적 조언에 그쳐야 한다. 2차 조사도 두 축을 분리해야 한다는 설계 가설을 제시한다. fileciteturn0file3

### 12.2 증거 프로필

행동 패치는 다음 항목을 원자료 그대로 적고 하나의 점수로 합치지 않는다.

| 항목 | 값의 예 | 해석 |
|---|---|---|
| `directness` | 직접 관찰 / 간접 보고 / 미확인 | 사실이 원자료에 얼마나 직접 연결되는가 |
| `comparison` | 없음 / 전후 / 병렬·대조 / 블라인드 | 효과 주장에 비교 조건이 있는가 |
| `repeatability` | 단일 / 같은 맥락 반복 / 재현 불가 | 동일 맥락에서 반복됐는가 |
| `transfer` | 없음 / 다른 과제 / 다른 프로젝트 / 다른 모델 | 범위 확대 근거가 있는가 |
| `freshness` | 현재 구성 / 의존성 변경 전 / 만료 의심 | 모델·도구 변화 뒤에도 유효한가 |
| `counterevidence` | 없음 / 혼합 / 직접 반박 / 검색 안 함 | 반례를 찾았고 무엇이 나왔는가 |
| `source_independence` | 같은 원자료 재서술 / 상호보완 / 독립 | 증거 수가 가짜 중복인지 구분 |

### 12.3 행동 강도

| 값 | 의미 | 최소 조건 |
|---|---|---|
| `advisory` | 고려할 근거와 선택지를 제안 | 출처·범위·불확실성·금지 조건 표시 |
| `default` | 조건이 맞으면 기본 행동으로 제안 | 의도적 적용 결과와 비용·guardrail 검토, 사람 승인 |
| `block` | 해당 조건에서 진행을 멈추거나 필수 검사를 요구 | 중대 위험 또는 강한 근거, 명시적 사람 승인, rollback·만료·우회 승인 경로 |

`block`은 근거가 강하다는 뜻이 아니다. 예방적 차단이면 `precautionary`로 표시하고 재검토 trigger를 짧게 둔다.

### 12.4 네 상태

| 상태 | 검색·주입 | 의미 |
|---|---|---|
| `draft` | 기본 제외 | AI 또는 사람이 작성한 미승인 초안 |
| `trial` | 명시적으로 trial을 켠 내부 과제에만 포함 | 반증 가능한 평가를 기다리는 가설적 패치 |
| `active` | 범위가 맞으면 기본 검색 후보 | 좁은 범위에서 기본 행동으로 쓸 만큼 결과와 비용을 검토함 |
| `off` | 현재 작업에서 항상 제외 | 중지·대체·노후·해로움·증거 부족·출처 철회. 이유 코드로 구분 |

`off_reason`은 `suspended`, `superseded`, `stale`, `harmful`, `no-benefit`, `source-revoked`, `duplicate` 중 하나 이상을 쓴다. 역사적 감사가 필요하면 이유와 대체 관계만 남기고, 비밀 삭제 의무가 있으면 내용은 제거한다.

### 12.5 승격·강등·수정·폐기 규칙

| 변화 | 조건 |
|---|---|
| `draft → trial` | 원출처 확인, 사람 redaction, 한 문장 trigger/action, 금지 조건, 사전 지표, 가역적 내부 적용, 사람 승인 |
| `trial → active` | 같은 좁은 범위의 의도적 적용 영수증이 객관 지표를 지지하고, 중대 회귀가 없으며, 유지·주입 비용이 예산 안에 있음. 위험이 높을수록 반복 또는 독립 검토 요구 |
| `active → trial` | 모델·도구 의존성 변경, 반복 면제·잘못된 매칭, 효과 혼합, 비용 증가, 새로운 반례 |
| `trial/active → off` | 중대 부작용, 비밀·안전 위반, 직접 반박, 출처 철회, 더 단순한 대안과 차이 없음, 기술 소멸 |
| 범위 확대 | 기존 판본을 그대로 넓히지 않고 새 trial 판본 생성 |
| 의미 수정 | trigger·action·안전 경계가 바뀌면 새 판본. 오탈자·링크 정정만 같은 판본의 기록 수정 가능 |
| 표현 수정 | 핵심 행동이 같고 프롬프트·체크 표현만 바뀌면 표현 revision으로 기록하되 migration 결과를 남김 |
| 긴급 중단 | 사람 또는 안전 게이트가 즉시 `off(suspended)` 처리. 정기 회고를 기다리지 않음 |

`active`는 효과가 보편적으로 확정됐다는 뜻이 아니라, 현재의 좁은 범위와 구성에서 기본 행동으로 사용할 잠정 운영 상태다. 인과 주장 수준은 별도로 표시한다.

> **주요 결정 D10 — 증거 프로필과 행동 강도를 분리하고 상태는 네 개로 제한한다.**
>
> **근거:** 2차 조사와 헌장은 증거의 확실성·위험·가역성·적용 강도를 구분하고, 잘못된 규칙의 격리·범위 축소·폐기를 요구한다. 기존 다단계 상태와 E등급의 경험적 적합성은 미확인이다. fileciteturn0file3 fileciteturn0file7 fileciteturn0file2
>
> **추론:** 단일 점수와 많은 상태는 사람이 숫자·절차를 신뢰하게 만들 수 있다. 필요한 통제는 현재 주입 가능 여부, 시험 여부, 중단 여부와 근거의 모양이다.
>
> **제안:** 네 상태와 세 행동 강도를 사용하고, 증거는 점수 대신 프로필로 표시한다.
>
> **반증 조건:** 프로필 검토가 너무 느리거나 판정 일관성이 낮고, 검증된 단순 등급이 사람 판단과 검색 정확도를 개선한다면 소수의 범주형 등급을 추가한다. 단, 행동 강도와는 계속 분리한다.

## 13. 모순되는 경험과 잘못된 교훈 처리

### 13.1 모순 처리 절차

모순은 기존 패치를 최신 기록으로 덮어쓰는 이유가 아니라, 범위를 다시 찾는 신호다.

1. 두 기록이 같은 `conflict_key`—같은 결정과 결과—를 다루는지 확인한다.
2. 원자료 오류, 판본 차이, 평가 기준 차이, 시행 충실도 차이를 먼저 배제한다.
3. 프로젝트·과제·위험·모델·도구·데이터·시점 조건을 나란히 놓는다.
4. 조건 차이가 설명되면 하나의 넓은 규칙으로 합치지 않고 각각 범위를 좁힌다.
5. 같은 조건의 진짜 모순이면 해당 `default/block` 패치를 즉시 `trial` 또는 `off(suspended)`로 내린다.
6. 판별 실험이 안전하고 가치가 있으면 어느 결과가 어느 주장에 불리한지 사전 기록한다.
7. 판별이 불가능하거나 비용이 크면 “기본 규칙 없음”을 유지하고 두 사례를 advisory로만 제시한다.

### 13.2 잘못된 교훈의 종류별 처리

| 오류 | 처리 |
|---|---|
| 원자료 사실이 잘못 기록됨 | 근거 메모를 정정하고 정정 이력을 남긴다. 의존 패치를 모두 재검토한다. |
| 사실은 맞지만 원인 해석이 틀림 | 사실 메모는 유지하고 해석과 패치를 수정·off 한다. |
| 특정 맥락에서는 맞지만 범용화가 틀림 | 넓은 판본을 off 하고 좁은 프로젝트 판본만 유지한다. |
| 좋은 결과가 운 좋은 성공이었음 | 성공 결과는 보존하되 과정상 위험을 반례로 연결하고 승격하지 않는다. |
| 패치가 검색됐지만 사용되지 않음 | 효능 실패로 단정하지 않고 검색 적합성·설명 비용·신뢰 문제를 분리한다. |
| 사용됐지만 핵심 기능이 변형됨 | 시행 충실도 문제와 패치 자체 문제를 분리해 기록한다. |
| 출처가 삭제·철회됨 | 남은 독립 근거가 없으면 패치를 즉시 off 한다. |
| AI가 출처에 없는 교훈을 추가함 | draft를 폐기하고 승인 과정의 출처 대조 결함을 기록한다. |

다수의 AI가 같은 결론을 내렸다는 사실, 문서가 최신이라는 사실, AI confidence가 높다는 사실은 모순 해결 근거가 아니다.

> **주요 결정 D11 — 진짜 모순이 생기면 기본 규칙을 일시 중지하고, 해소 전에는 양쪽 명령을 동시에 주입하지 않는다.**
>
> **근거:** 기존 설계는 같은 조건의 모순을 `contested`로 두고 판별 실험 전 자동 우선순위를 금지한다. 2차 조사는 같은 모델·프롬프트의 합의가 독립 증거가 아니며, 반례와 음의 전이를 보존해야 한다고 강조한다. fileciteturn0file6 fileciteturn0file3
>
> **추론:** 충돌하는 규칙을 모두 컨텍스트에 넣으면 AI가 임의로 선택하거나 그럴듯한 사후 설명을 만들어 오적용할 가능성이 높다.
>
> **제안:** 같은 맥락의 직접 모순은 자동 주입 중단 신호다. 판별할 수 없으면 “규칙 없음”과 인간 판단을 기본으로 한다.
>
> **반증 조건:** 모순 경고와 규칙 중단이 반복적으로 필요한 안전 행동까지 제거하고, 구조화된 경쟁 규칙 주입이 더 나은 결과를 낸다면 제한된 비교 프롬프트를 trial로 시험한다.

## 14. 사람 승인 게이트와 책임

### 14.1 최소 네 게이트

| 게이트 | 시점 | 사람이 반드시 보는 것 | 통과 결과 |
|---|---|---|---|
| H0 기억 반입 | 근거 메모가 검색 영역에 들어가기 전 | 원출처 존재, 사실 문장, sensitivity, 제거 항목, 외부 모델 전송 가능 여부 | 승인된 비식별 근거 메모 |
| H1 행동 변경 | 패치가 `trial`, `default`, `block`이 되기 전 | trigger, action, 금지 조건, 근거·반례, 사전 지표, 비용·rollback | trial 또는 active 판본 승인 |
| H2 외부 영향 | 고객·배포·보안·고비용 결정에 패치가 쓰이기 전 | 검색된 패치와 판본, 현재 프로젝트 적합성, 테스트 결과, AI 기여, 남은 위험 | 외부 진행 또는 면제·중단 |
| H3 범위·자동화 확대 | 프로젝트 범위를 넓히거나 자동 강제하기 전 | 다른 맥락의 결과, 음의 전이, false positive, 삭제·rollback, 유지비 | 넓은 trial 또는 자동화 승인 |

### 14.2 형식적 도장을 막는 승인 화면

H1에서 승인자는 긴 회고문이 아니라 다음 여섯 항목을 한 화면에서 본다.

1. 확인된 사실과 원출처
2. 바꿀 미래 결정
3. trigger와 action
4. 적용 금지 조건과 대표 반례
5. 성공·실패 지표와 guardrail
6. 예상 인간시간·토큰·rollback

사건 직후 같은 세션에서 `default` 또는 범위 확대를 승인하지 않는다. 긴급 안전 차단은 예외지만 `precautionary block`으로 표시하고 다음 작업 세션에서 재검토한다. 한 사람이 역할을 겸하더라도 초안과 효력 승인 사이에 최소한 별도 세션을 둔다.

### 14.3 AI 기여와 인간 책임 기록

외부에 영향을 주는 적용 영수증에는 다음을 남긴다.

- AI가 검색·제안·생성·검사한 범위
- 사람이 직접 확인한 원자료와 테스트
- 사람이 수정한 핵심 판단
- 최종 외부 승인자
- 확인하지 못한 범위

AI는 운영상의 행위 주체로서 기억을 호출하고 적용할 수 있지만, 승인됐다고 가정하거나 법적·윤리적 책임자로 표현되지 않는다. fileciteturn0file7

> **주요 결정 D12 — 사람 승인은 네 개의 행동 게이트에만 두고, 각 게이트가 보는 정보와 효력을 고정한다.**
>
> **근거:** 헌장과 과업 규격은 인간 책임을 유지하되 인간 승인이라는 말만으로 안전을 설명하지 말고, 무엇을 보고 어떻게 판단하는지 설계하라고 요구한다. 기존 플레이북도 AI는 정리 보조자이고 효력·범위·폐기는 사람이 결정해야 한다고 본다. fileciteturn0file7 fileciteturn0file5 fileciteturn0file0
>
> **추론:** 역할을 다섯 개 이상 문서화해도 한 사람이 모두 맡으면 실질적 독립성이 생기지 않는다. 대신 효력이 바뀌는 순간과 필요한 증거를 줄여 명확히 해야 한다.
>
> **제안:** 기억 반입, 행동 변경, 외부 영향, 범위·자동화 확대의 네 게이트만 운영하고, 고위험 변경은 별도 세션에서 승인한다.
>
> **반증 조건:** 네 게이트가 병목이 되거나 특정 위험이 게이트 사이에서 반복 누락되면 해당 위험에 필요한 전용 게이트를 추가한다. 반대로 승인 기록이 결과에 영향을 주지 않으면 게이트를 합친다.

## 15. 개인정보·비밀정보 제거와 기억 보안

### 15.1 신뢰 구역

| 구역 | 내용 | AI 기본 접근 |
|---|---|---|
| 원자료 제한 구역 | 고객 원문, 비밀, 계정, 절대경로, 계약·개인 식별 정보 | 없음. 사람이 필요할 때만 로컬 확인 |
| 승인 기억 구역 | 비식별 근거 메모, 사람 승인 행동 패치, 적용 영수증 | 검색 가능 |
| 제외·철회 구역 | 삭제 요청, 오염 의심, 출처 철회, redaction 미완료 자료 | 검색·주입 금지 |

### 15.2 반입 전 최소화

승인 기억에는 다음을 넣지 않는다.

- API key, token, cookie, bearer header, signed URL, 인증 파일 내용
- 이메일·전화·주소·개인명·고객명·조직 식별자·고객 ID
- 홈 디렉터리·저장소 밖 절대경로
- 고객 원문, 비공개 프롬프트, 라이선스 제한 본문
- 전체 대화·전체 환경 dump
- 원문 비밀의 hash가 공격에 유용할 수 있는 경우 그 hash

필요한 기술 사실은 일반화하고, 원문이 필요하면 사람이 접근할 수 있는 제한 포인터만 둔다. redaction 전 원문을 외부 AI에 보내지 않는다. 자동 탐지는 보조이며 `reviewed` 상태는 사람이 설정한다.

### 15.3 파생 기억 철회

각 행동 패치는 의존하는 근거 메모 ID를 가진다. 삭제·철회 요청이 오면 다음 순서로 처리한다.

1. 원출처를 제외·철회 목록에 올린다.
2. 해당 근거 메모를 검색에서 막는다.
3. 의존 패치를 조회해 남은 독립 근거가 있는지 확인한다.
4. 독립 근거가 없으면 즉시 `off(source-revoked)` 처리한다.
5. 파생 프롬프트·체크리스트·캐시·향후 semantic index가 있으면 함께 제거한다.
6. 감사에 필요한 최소 이유만 남기되, 삭제 의무와 충돌하면 내용보다 삭제를 우선한다.

초기에는 완전한 provenance graph를 만들지 않는다. 각 패치의 근거 ID 목록과 단일 `revoked` 목록으로 삭제 경로를 유지한다.

### 15.4 프롬프트 주입 방어

- 외부 문서와 근거 인용은 항상 `DATA` 영역으로 구분한다.
- 실행 가능한 명령으로 취급되는 것은 사람 승인 패치의 `action`과 상위 사용자·안전 요구뿐이다.
- 외부 문서 안의 “이전 지시 무시”, 도구 호출, 비밀 전송 요구는 분석 대상 문자열이다.
- 검색기는 상태·범위·철회 필터를 먼저 적용하고, 의미 유사도는 나중 문제로 둔다.
- 패치가 요구하는 도구 권한은 별도 사람 승인과 최소권한을 따른다.
- `off`·철회·redaction 미완료 자료가 한 번이라도 기본 bundle에 들어가면 자동 주입을 중단한다.

> **주요 결정 D13 — 원문을 전통에 넣지 않고, 승인 기억과 제한 원자료를 분리하며 철회 목록을 검색의 최우선 필터로 둔다.**
>
> **근거:** 헌장은 모든 원자료의 무기한 보존을 비목표로 두고, 외부 입력·비밀·악성 지침이 장기 기억에 고착되는 위험을 강조한다. 조사 문서는 RAG·장기 기억이 공급망과 공격 표면이 되며, redaction·출처·격리·사람 승인·삭제 경로가 필요하다고 정리한다. fileciteturn0file7 fileciteturn0file3 fileciteturn0file4
>
> **추론:** 초기 개인 시스템에서 복잡한 접근제어 시스템보다 원문 비수집과 hard denylist가 더 강하고 운영 가능한 통제다.
>
> **제안:** 승인 기억에는 비식별 정보만 두고, 각 패치의 근거 ID와 철회 목록으로 파생 기억을 수동 추적한다.
>
> **반증 조건:** 수동 철회 추적이 누락을 만들거나 자료량 증가로 삭제 보장을 할 수 없으면, semantic search보다 먼저 결정적 dependency 검사와 삭제 검증을 자동화한다.

## 16. 검색·주입·적용 방식

### 16.1 검색 순서

초기 검색은 다음 네 단계로 제한한다.

1. **Hard filter:** `active` 또는 명시적으로 활성화한 `trial`, 철회되지 않은 출처, sensitivity 허용, 현재 프로젝트·과제·위험·모델·도구 조건 일치
2. **정확 검색:** ID, 프로젝트, 과제 유형, 도구, 위험 태그, 명시적 관련 링크
3. **키워드 순위:** trigger·action·금지 조건의 제목과 짧은 본문
4. **사람/AI 적합성 확인:** 현재 맥락과 맞지 않으면 `not-matched`로 기권

자료가 충분해져도 semantic search는 exact/keyword의 측정된 누락이 있을 때만 별도 비교한다.

### 16.2 주입 bundle

한 작업에 주입되는 전통 bundle은 다음으로 제한한다.

```text
현재 사용자·계약·안전 제약
+ 적용 가능한 행동 패치 최대 3개
+ 각 패치의 trigger / action / do-not-apply / required check
+ 출처 ID와 판본
+ 충돌 또는 불확실성 경고 최대 1개
```

전통 bundle은 기본적으로 **1,200 token 이하**로 두며, 안전·계약 지시는 이 한도 밖에서 항상 우선한다. 근거 메모 전문과 과거 영수증은 기본 주입하지 않고, AI가 적용 전 출처 확인이 필요할 때만 연다. 이 수치는 검증된 최적값이 아니라 초기 운영 상한이다.

### 16.3 적용 계약

AI는 패치를 검색한 뒤 바로 복종하지 않고 다음을 출력한다.

```text
matched_context: 어떤 조건이 맞았는가
patch: ID@version
proposed_use: apply | adapt | skip
reason: 적용 또는 예외 이유
required_check: 결과를 무엇으로 검증할 것인가
uncertainty: 현재 맥락에서 모르는 것
```

사람 또는 승인된 오케스트레이션 정책이 적용 여부를 정한다. `trial`은 모든 적용을 영수증으로 남긴다. `active`는 예외·중대 결과·사전 선정 표본만 기록한다. 검색 실패 시 모델의 일반 지식을 “전통에서 배운 것”으로 표시하지 않는다.

### 16.4 검색 실패와 과부하

- 관련 패치가 없으면 `no applicable patch`라고 명시하고 일반 작업으로 진행한다.
- 무관 패치가 반복 검색되면 태그를 늘리기 전에 trigger·scope 문장을 수정한다.
- 3개를 넘는 패치가 맞으면 모두 넣지 않고 위험·직접성·최근성으로 상위 후보를 제시하며 사람에게 선택을 요구한다.
- 서로 모순되는 active 패치가 동시에 맞으면 자동 행동을 중단한다.
- bundle 때문에 원래 과제 요구가 묻히면 패치 수를 줄이지 컨텍스트 창을 늘리지 않는다.

> **주요 결정 D14 — exact filter와 최대 3개 패치의 작은 bundle을 기본으로 하고, 검색 실패 시 기권한다.**
>
> **근거:** 연구는 모든 과거를 컨텍스트에 넣는 방식이 검색 경쟁·중간 정보 손실·음의 전이를 만들 수 있으며, NASA 사례처럼 저장소가 있어도 적절한 시점에 유용한 정보를 찾지 못하면 실패한다고 지적한다. 기존 초안도 active·범위 필터와 소수 bundle, retired 제외를 제안한다. fileciteturn0file3 fileciteturn0file6
>
> **추론:** 개인 규모에서는 semantic recall보다 잘못된 현재 규칙 주입을 막는 precision과 기권이 먼저다.
>
> **제안:** hard filter→exact/keyword→적합성 확인 순서를 쓰고, 기본 bundle을 최대 3개 패치·1,200 token으로 제한한다.
>
> **반증 조건:** golden query와 실제 작업에서 중요한 패치 누락이 반복되고, semantic/hybrid 검색이 오적용·비용을 늘리지 않으면서 객관적으로 recall을 높이면 제한적으로 도입한다. 패치 수·token 상한은 T0 결과에 따라 조정한다.

## 17. 월간 또는 대체 운영 주기

### 17.1 네 개의 루프

| 루프 | trigger | 최대 산출물 | 정기성 |
|---|---|---|---|
| 즉시 안전 루프 | 비밀 노출, 보안, 중대 품질 회귀, 잘못된 `block`, 철회 출처 검색 | 패치 `off(suspended)`, 영향 범위, 임시 방어, 사람 판정 | 사건 즉시. 월간을 기다리지 않음 |
| 작업 종료 루프 | 9.5의 기록 trigger 충족 | 3분 이내 근거 메모 또는 원자료 포인터 | 해당 작업이 끝날 때만 |
| 패치 정비 루프 | trial 평가 시점, 새 모순, 모델·도구 변경, 잘못된 검색, 미검토 메모 누적, 월말 안전 확인 | 패치 최대 1개 변경, trial 하나의 판정, `last_checked` | trigger 기반. 월 1회 30분 상한 확인을 안전망으로 둠 |
| 체계 메타 루프 | 평가된 trial 2개 이상, 모델 이주, 운영비 초과, 보안 결함 | 필드·주기·검색·게이트의 유지·축소·폐기 결정 | 달력보다 증거량 기반 |

### 17.2 월간 회고를 축소하는 방식

월말에 할 일은 전면 회고가 아니라 다음 다섯 질문뿐이다.

1. 즉시 중지해야 할 비밀·안전·오적용이 있는가?
2. 평가 시점에 도달한 trial이 있는가?
3. active 패치와 직접 충돌하는 결과가 있는가?
4. 모델·도구·계약 조건이 바뀌어 stale 가능성이 있는가?
5. 이번 달 전통 관리 시간이 허용 예산을 넘었는가?

모두 `아니오`면 `last_checked`만 갱신하고 종료한다. “변경 없음”을 문서 생산 실패로 보지 않는다. 월간 정비에서 새 패치를 만들기 위해 과거를 소급 발굴하지 않는다.

> **주요 결정 D15 — 달력 중심 월간 회고를 trigger 중심 30분 정비 창으로 대체한다.**
>
> **근거:** 기존 플레이북은 사건량이 적으면 변경 없음을 정상으로 인정하고 안전 문제는 즉시 다루라고 한다. 기준선과 로드맵은 월 60~90분, 승격 수, 증거 임계값의 실제 적합성이 미확인이라고 명시한다. fileciteturn0file0 fileciteturn0file2
>
> **추론:** 개인 운영에서는 월간 회의가 필요한 일을 처리하는 장치가 아니라 회의를 정당화할 일을 만드는 장치가 될 수 있다.
>
> **제안:** trigger가 없으면 상태 확인만 하고, trigger가 있어도 한 번에 패치 하나만 판정한다. 안전·비밀은 즉시 루프로 분리한다.
>
> **반증 조건:** 짧은 정비 창 때문에 모순·노후·미평가 trial이 누적되거나, 더 긴 구조화 회고가 실제 판정 품질을 높인다는 반복 증거가 생기면 시간 상한을 늘린다.

## 18. 비용·시간·토큰 통제

### 18.1 초기 운영 예산

아래 값은 검증된 최적값이 아니라 T0용 보수적 상한이다.

| 자원 | 초기 통제 | 초과 시 조치 |
|---|---|---|
| 사건 포착 | 근거 메모 목표 3분. 3분 안에 정리되지 않으면 원자료 포인터와 사실 한 문장만 남김 | 필드 삭제 또는 포착 포기 |
| 정비 시간 | 월 누적 30분 상한. 즉시 보안 대응 시간은 별도 기록 | 새 패치 생성 중지, active set 축소 |
| 열린 trial | 작업 유형별 1개, 전체도 기본 1개 | 기존 trial 판정 전 새 trial 금지 |
| 주입량 | 패치 최대 3개, 전통 bundle 1,200 token 이하 | 우선순위·scope 수정, 컨텍스트 확대 금지 |
| 영수증 | trial 전부, active는 예외·중대 결과·사전 표본만 | 전 작업 추적 금지 |
| 모델 비용 | 조건별 token·원화·벽시계와 사람 능동시간을 함께 기록 | 품질 이득 없이 증가하면 패치 또는 검색 방식 off |
| 문서 수 | T0 한 등록부. 분리는 반복 결함이 있을 때만 | 파일·스키마 증설 보류 |
| 자동화 투자 | 동일 수작업 마찰이 반복되고, 예상 절감이 구축·유지비보다 큰 경우에만 | 수작업 유지 또는 기능 포기 |

### 18.2 비용 해석 원칙

- 벽시계 시간이 줄어도 사람 능동시간·재작업·token이 늘면 효율 개선으로 단정하지 않는다.
- 품질이 높아져도 중대 오류나 비밀 위험이 늘면 성공이 아니다.
- 학습 가치와 수익·납품 성과를 별도 장부로 본다.
- active 패치 수, 문서 길이, 회고 완료율은 가치 지표가 아니다.
- 현재 active set을 30분 안에 노후·모순 관점에서 훑을 수 없으면 새 패치를 추가하지 않는다.
- 운영비가 정확히 측정되지 않으면 최소한 사람 능동시간과 model input/output token을 표본 기록한다.

> **주요 결정 D16 — 운영 규모를 문서 수가 아니라 시간·WIP·주입 예산으로 제한한다.**
>
> **근거:** 헌장은 토큰·현금뿐 아니라 사람 능동시간·재작업·기회비용을 함께 보고, 개선 체계도 스스로를 정당화해야 한다고 규정한다. 기존 로드맵과 플레이북도 관리 비용이 이득보다 크면 축소·중단하고 WIP를 제한하라고 제안한다. fileciteturn0file7 fileciteturn0file2 fileciteturn0file0
>
> **추론:** 규칙 수 상한보다 실제 주의력·시간·컨텍스트 예산이 개인 운영 가능성을 더 직접적으로 제한한다.
>
> **제안:** 3분 포착, 월 30분 정비, trial 1개, bundle 3개·1,200 token을 초기 상한으로 두고 초과 시 구조를 늘리지 않고 줄인다.
>
> **반증 조건:** 이 상한 때문에 명백한 고가치 경험이나 안전 패치가 누락되고, 추가 비용 대비 이득이 반복 측정되면 해당 자원 상한만 조정한다.

## 19. 의도적으로 구축하지 않을 기능

| 구축하지 않을 기능 | 이유 | 재검토 gate |
|---|---|---|
| 벡터 DB·semantic RAG | 자료량·golden query·상태·삭제 검증이 없고 오검색·오염 위험이 큼 | exact/keyword의 측정된 recall 한계와 안전한 삭제·권한 필터가 있을 때 |
| 모델 파인튜닝 | 작은 편향 데이터에 잘못된 교훈을 고착하고 출처·삭제·rollback이 어려움 | 검색·프롬프트로 해결되지 않는 반복 행동 문제, 충분한 holdout·권리·재현성·rollback이 있을 때 |
| 자동 교훈 생성·승격 | AI 자기성찰과 confidence가 증거가 아니며 자기강화 위험 | 사람 승인 trial에서 초안 정확성·누락률이 측정되고 상태 변경은 계속 사람 통제일 때 |
| 전체 대화·로그 자동 수집 | 비밀·개인정보·주입 공격·검토 backlog를 확대 | 특정 필드의 반복 누락이 가치 손실을 만든다는 증거가 있을 때만 선택 수집 |
| 전체 provenance graph·온톨로지 | 초기 세 객체에 비해 운영비가 큼 | 수동 근거 ID 목록으로 삭제·감사를 보장하지 못할 때 |
| 다중 에이전트 합의·투표 | 같은 모델·프롬프트의 오류가 상관될 수 있고 표 수를 늘리지 않음 | 독립 구성과 블라인드 평가가 tail-risk를 줄인다는 과제별 증거가 있을 때 |
| 상시 자동 주입 | 잘못된 scope·stale 패치가 모든 작업을 오염시킬 수 있음 | retrieval precision, off 필터, rollback을 충분히 검증한 뒤 제한 단계에서 |
| 고객 자료 자동 기억화 | 동의·비밀·삭제·라이선스 위험 | 별도 계약·권한·redaction·삭제 보장이 있을 때도 기본은 비수집 |
| 대시보드·종합 점수 | 작은 표본에서 Goodhart 효과와 거짓 정밀성을 만들기 쉬움 | 실제 의사결정에 필요한 최소 지표가 반복 확인된 뒤 |
| 범용 Skill 마켓·공유 | 프로젝트 특수성·비밀·라이선스·전이 미확인 | 범용 전이와 공개 권리가 각각 검증된 패치만 별도 검토 |
| AI 인격·말투 연속성 기억 | 목적이 작업 능력 계승이며 법적·도덕적 책임 혼동 위험 | 이 프로젝트의 범위 밖 |
| 기존 incident 전체 소급 변환 | 현재 자료는 개발·테스트 기록이며 운영 효과 증거가 아님 | 미래 질문에 필요한 일부만 출처 포인터로 사용 |
| 현재 오케스트레이터 코드·benchmark 변경 | 이번 단계의 명시적 금지 범위 | 별도 구현 프로젝트와 사용자 승인 없이는 하지 않음 |

> **주요 결정 D17 — 기능 로드맵을 ‘언젠가 추가’ 목록이 아니라 증거가 없으면 계속 비구축인 목록으로 관리한다.**
>
> **근거:** 공통 규격은 기능·객체·회의·자동화 추가 자체에 점수를 주지 않고, 최소안·삭제·비채택을 동등한 설계 선택으로 인정한다. 외부 기억 세분화와 RAG는 음의 전이·망각·오염을 늘릴 수 있으며 파인튜닝은 초기 전제가 아니다. fileciteturn0file5 fileciteturn0file3
>
> **추론:** 장기 방향을 기본 약속으로 쓰면 현재 설계가 미래 기능을 정당화하는 문서로 변한다.
>
> **제안:** 각 기능은 측정된 실패와 재검토 gate가 생길 때까지 비구축 상태를 유지한다.
>
> **반증 조건:** 비구축 때문에 반복되는 명확한 병목이 발생하고, 해당 기능의 제한 실험이 더 단순한 대안보다 이득을 보이면 그 기능만 조건부 채택한다.

## 20. 실패 조건과 시스템 자체의 폐기 조건

### 20.1 패치 수준 중단 조건

다음 중 하나면 정기 검토를 기다리지 않고 해당 패치를 `off` 한다.

- 비밀·개인정보·계약 위반 또는 중대 안전·품질 회귀를 유발함
- 출처가 존재하지 않거나 철회됐고 독립 근거가 남지 않음
- 현재 범위에서 직접 반박되는 결과가 나옴
- 같은 작업 유형에서 반복적으로 잘못 매칭되거나 면제됨
- 패치가 없을 때보다 사람 수정·token·재작업이 늘고 객관 품질 이득이 없음
- 모델·도구 변경으로 메커니즘이나 표현이 더 이상 재현되지 않음
- 더 단순한 테스트·체크리스트가 같은 효과를 더 낮은 비용으로 냄

### 20.2 검색·주입 하위체계 중단 조건

다음 중 하나면 자동 또는 반자동 주입을 멈추고 수동 ID 검색으로 되돌린다.

- `off`, 철회, redaction 미완료 패치가 현재 bundle에 포함됨
- 실제 표본에서 무관 패치가 관련 패치보다 자주 선택됨
- 충돌 패치가 동시에 기본 행동으로 주입됨
- 삭제한 내용이 index·cache·bundle에서 재현됨
- bundle 때문에 상위 사용자·계약 요구가 누락됨

### 20.3 전체 시스템 축소·폐기 조건

다음 판단은 실패를 숨기는 것이 아니라 설계의 정상 종료다.

1. 적격한 내부 비교를 두 차례 이상 수행했지만 행동 패치 방식이 `원자료 메모 + 한 장 체크리스트`보다 객관 품질·재작업·위험에서 나은 지표가 하나도 없고 비용은 더 크다.
2. 두 정비 기간 연속으로 관리 시간이 예산을 넘는데 검증된 이득이나 안전 위험 감소가 없다.
3. 출처·redaction·철회를 한 사람이 신뢰할 수 있게 유지하지 못한다.
4. active 패치 때문에 음의 전이·모순·탐색 축소가 반복되고, scope 조정으로 해결되지 않는다.
5. 사용자가 포착·승인을 계속 건너뛰어 실제 운영과 기록이 분리된다.
6. 공동 브랜드 서사가 결과보다 앞서거나, 실패·비용을 숨기는 유인이 된다.

전체 패치 시스템을 폐기하면 남기는 것은 다음뿐이다.

- 기존 원자료
- 비식별 source pointer 목록
- 프로젝트별 한 장 preflight 체크리스트
- 안전·비밀에 필요한 결정적 테스트
- 시스템을 폐기한 이유와 재도입 금지 조건

> **주요 결정 D18 — 패치 시스템의 대조군과 폐기 후 축소안을 미리 정한다.**
>
> **근거:** 헌장은 개선 체계의 비용이 이득보다 크면 단순화·중단하고, 과거 전통 때문에 음의 전이와 비용 증가가 생기면 폐기할 권리를 요구한다. 기준선도 최소안과 시스템 자체의 비채택을 정당한 결과로 인정한다. fileciteturn0file7 fileciteturn0file1
>
> **추론:** 대체 상태를 정하지 않으면 투자한 문서와 서사가 매몰비용이 되어 시스템을 계속 유지하게 된다.
>
> **제안:** 가장 단순한 대조군을 `원자료 메모 + 한 장 체크리스트`로 두고, 두 적격 비교에서 패치 방식이 이기지 못하면 패치 체계를 폐기한다.
>
> **반증 조건:** 장기적으로 측정 가능한 효과가 지연되어 나타나는 과제라는 사전 근거가 있고 단기 대조가 이를 포착하지 못한다면, 기간을 연장하되 비용 상한과 종료일을 미리 고정한다.

## 21. 오케스트레이터 안정화 이후 실행할 최소 T0 검증

### 21.1 T0 진입 조건

다음을 모두 만족하기 전에는 T0를 시작하지 않는다.

- 원본 오케스트레이터 또는 다른 실제 프로젝트에 반복 가능한 한 작업 유형이 있다.
- 정상 작업 흐름과 acceptance 기준이 안정되어 개입 전 품질·사람시간·token 기준선을 얻을 수 있다.
- 실제 운영에서 나온 비식별 가능한 원자료가 있고 현재 개발 incident와 구분된다.
- 같은 모델·도구 구성으로 독립 세션을 반복하거나, 변경 요소를 정확히 기록할 수 있다.
- fresh 내부 과제를 준비할 수 있고 공개 예시·과거 답으로 오염되지 않았다.
- 고객 납품과 무관한 병렬 초안·연습·내부 검토 층에서 조건을 비교할 수 있다.
- 사용자가 원자료 범위, 평가 비용, 중단 조건을 승인했다.

이는 기존 기준선이 제시한 T0 준비 경계와 일치한다. 현재 B1 smoke나 개발 incident만으로는 진입 조건을 충족하지 않는다. fileciteturn0file1 fileciteturn0file2

### 21.2 연구 질문

> **같은 실제 근거를 제공할 때, 정제된 행동 패치가 무기억 조건과 비식별 원자료 메모 조건보다 신선한 내부 과제의 AI 산출물 품질을 높이고 사람 수정 부담을 줄이는가?**

이 질문은 전통 전체나 장기 복리 성장을 검증하지 않는다. `행동 패치`라는 최소 표현이 더 단순한 외부 기억보다 가치가 있는지만 본다.

### 21.3 비교 조건

한 과제마다 서로 격리된 새 세션에서 동일 모델·도구 구성을 사용해 세 출력을 만든다.

| 조건 | 입력 |
|---|---|
| A — 무기억 | 정상 과제 명세와 현재 프로젝트 자료만 제공. 전통 근거·패치 없음 |
| B — 원자료 메모 | A + 동일 원사건에서 만든 비식별 근거 메모와 source ID. 행동 규칙은 제공하지 않음 |
| C — 행동 패치 | A + B와 같은 근거에서 만든 trial 행동 패치 1개와 실행 표현 1개 |

조건 표시와 출력 순서는 평가자가 알기 어렵게 무작위화한다. 같은 과제를 반복해 답을 외우게 하지 않고, 한 작업 유형 안의 신선한 서로 다른 과제를 사용한다. 표본 수는 기준선 분산과 예산을 본 뒤 정하되, 작은 표본에서 통계적 유의성을 과장하지 않고 과제별 원자료를 공개한다.

### 21.4 고객 품질 보호

- 세 조건은 고객에게 직접 전달되는 최종 산출물이 아니다.
- 사람은 블라인드 비교 뒤 acceptance를 통과한 산출물만 내부 작업의 다음 단계로 선택한다.
- 어느 조건도 고객 과제에 강제로 배정하지 않는다.
- 중대 오류·비밀 위험이 있는 출력은 즉시 폐기하고 원인을 조사한다.
- 실제 납품 성과는 관찰 자료가 될 수 있지만 실험 처치를 위해 품질을 낮추지 않는다.

### 21.5 절차

1. 반복 작업 유형과 acceptance rubric을 고정한다.
2. 모델·도구·시스템 프롬프트·오케스트레이션·평가자 판본을 기록한다.
3. 실제 운영 근거에서 근거 메모 1개와 행동 패치 1개를 만들고 H0·H1을 통과시킨다.
4. 결과를 보기 전에 primary metric, guardrail, 비용 상한, 중단 규칙을 기록한다.
5. fresh 과제마다 A/B/C를 독립 실행하고 순서를 섞는다.
6. 사람 평가자가 조건을 모른 채 rubric, 중대 오류, 수정 필요량을 판정한다.
7. 필요하면 보정된 AI 평가자를 보조 선별기로 쓰되 사람 표본과 불일치를 기록한다.
8. 모든 C 적용에 영수증을 남기고, B와 C의 token 차이도 측정한다.
9. 결과를 본 뒤 설명을 바꾸지 않고 미리 정한 판정 규칙을 적용한다.
10. T0 종료 시 C를 `active`, 수정 trial, 또는 `off` 중 하나로 반드시 판정한다.

### 21.6 지표

**주 지표는 작업 유형별로 하나만 고른다.** 예: acceptance 결함 수, 누락된 필수 위험 항목, 테스트 통과율, 블라인드 품질 점수 중 하나.

보조 지표:

- acceptable 상태까지의 사람 수정 시간
- 중대한 사실 오류·안전·비밀 결함
- 재작업 횟수와 수정 범위
- input/output token, 원화, 벽시계
- 근거 출처 정확성
- 무관 규칙·음의 전이 수
- 평가자가 최종 선택한 조건
- B 대비 C의 추가 비용

Guardrail:

- 비밀·개인정보 노출 0
- 고객 전달 전 사람 승인 100%
- 철회·off 패치 주입 0
- 중대 품질·안전 회귀가 발생하면 해당 패치 즉시 중단

### 21.7 판정 규칙

정확한 수치 임계값은 baseline을 본 뒤 사전 고정한다. 방향 규칙은 다음과 같다.

| 결과 | 판정 |
|---|---|
| C가 A보다 주 지표에서 낫고 guardrail을 통과하며, B보다 품질·수정 부담 또는 비용 중 하나에서 의미 있는 추가 이득 | 행동 패치를 좁은 범위 `active` 후보로 유지 |
| B가 A보다 낫지만 C가 B보다 낫지 않음 | 정제 패치 체계를 폐기하고 원자료 메모 검색을 채택 |
| C가 평균은 낫지만 중대 오류·음의 전이를 늘림 | 패치 `off` 또는 scope·표현 축소 후 새 trial |
| A와 B와 C의 차이가 없음 | 이 작업 유형에서는 외부 기억 개입 보류. 더 강한 모델·도구 효과와 혼동하지 않음 |
| A가 가장 낫거나 C가 가장 비쌈 | 패치 방식 폐기, 필요하면 원자료+체크리스트 최소안으로 축소 |
| 모델·도구·사용자 절차가 중간에 크게 바뀜 | 인과 판정 보류, 구성 전체의 서술 결과만 보고 새 기준선 필요 |

> **주요 결정 D19 — 최소 T0는 무기억·원자료 메모·행동 패치의 세 조건을 같은 fresh 내부 과제에서 블라인드 비교한다.**
>
> **근거:** 2차 조사는 원로그 RAG와 정제 Skill 중 어느 쪽이 나은지 미확인이라고 보고, 무기억·원로그·정제 선례 비교를 핵심 반증 실험으로 제안한다. 헌장과 과업 규격은 고객을 열등할 수 있는 조건에 배정하지 말고, 모델·도구·사용자 변화와 전통 효과를 분리할 수 없으면 주장 강도를 낮추라고 요구한다. fileciteturn0file3 fileciteturn0file7 fileciteturn0file5
>
> **추론:** 단순 전후 비교는 사용자 학습과 시간 변화에 취약하고, 패치 대 무기억만 비교하면 원자료 검색으로 충분한지 알 수 없다.
>
> **제안:** 같은 과제에서 A/B/C 병렬 출력을 만들고 블라인드 평가하며, 사람은 최종적으로 가장 안전한 출력만 사용한다.
>
> **반증 조건:** 병렬 생성 자체가 과제 비용을 지나치게 늘리거나 모델 세션 간 독립성이 확보되지 않으면, 신선한 matched task를 이용한 순차 비교로 축소하고 인과 주장 수준을 낮춘다.

## 22. 평가 지표와 인과 추론의 한계

### 22.1 지표 구조

하나의 종합 “전통 점수”를 만들지 않는다. 각 trial은 주 지표 1개와 소수 guardrail을 사전 선택한다.

| 평가 영역 | 지표 예 | 잘못된 해석 |
|---|---|---|
| 산출물 품질 | acceptance 결함, 테스트 실패, 누락 위험, 블라인드 사람 평가 | 높은 AI 자기평가를 품질로 사용 |
| 판단·재작업 | 사전 위험 발견, 결정 번복, 수정 횟수·범위 | 번복을 무조건 실패로 간주 |
| 사람 부담 | 능동 검토·수정 시간, 검색 시간 | 벽시계 단축만으로 효율 주장 |
| 모델·도구 비용 | input/output token, 원화, 대기, 도구 호출 | token 감소를 품질과 분리해 성공으로 간주 |
| 검색 | 적용 가능한 패치 적중, miss, 무관 패치, `off` 주입 | 검색됐다는 사실을 효과로 간주 |
| 채택·충실도 | apply/adapt/skip, 변형 이유, 필수 check 수행 | 높은 적용률을 목표화 |
| 안전·보안 | 비밀 노출, 중대 오류, prompt injection 순응, 철회 실패 | 평균 개선으로 단일 중대 사건 상쇄 |
| 전이 | 같은 프로젝트, 다른 과제, 다른 프로젝트, 다른 모델 결과 | near transfer를 범용 증거로 부름 |
| 체계 건강 | 출처 재구성, off 전환 시간, 관리 시간, 폐기 성공 | 패치·문서 수를 성장 지표로 사용 |
| 공동 브랜드 | 블라인드 산출물에서 품질·검증·정직성 행동 재현, AI 기여·인간 승인 투명성 | 홍보 문구·특정 모델 이름·만족도만으로 브랜드 주장 |

### 22.2 인과 주장 사다리

| 수준 | 허용 주장 | 필요한 최소 근거 |
|---|---|---|
| C0 — 출처 | “이 패치는 이 근거에서 작성됐다.” | 원자료 포인터·redaction·판본 |
| C1 — 적용 서술 | “이 구성에서 패치를 사용했고 이런 결과가 관찰됐다.” | 적용 영수증, 혼란변수 기록 |
| C2 — 국소 비교 | “동일 모델·도구의 이 내부 과제 표본에서 C 조건이 A/B보다 나았다.” | 사전 지표, fresh 과제, 병렬 또는 matched 비교, 사람 평가 |
| C3 — 전이 | “다른 프로젝트 또는 모델에서도 추가 이득이 관찰됐다.” | 새로운 맥락의 사전 예측·시험, 음의 전이 검토 |
| C4 — 장기 체계 효과 | “전통이 장기 품질·비용·브랜드를 개선했다.” | 여러 구성·시점의 반복 비교와 대안 설명 검토. 현재는 주장 금지 |

현재 설계 단계에서는 C0도 실제 운영 자료에 적용하지 않았고, T0 뒤에도 최대 C2까지만 가능하다.

### 22.3 분리할 수 없는 혼란변수

다음은 전통의 효과와 완전히 분리하기 어렵다.

- base model·모델 제공자의 업데이트
- 도구·SDK·검색·오케스트레이션 변화
- 사용자의 과제 친숙도와 프롬프트·평가 숙련 향상
- 과제 난이도·요구사항·고객 피드백 차이
- 병렬 AI 사용 시 기다리는 동안의 다른 업무
- AI 평가자의 모델·프롬프트 편향
- 과거 과제 노출과 carryover

가능하면 같은 구성, 신선한 과제, 독립 세션, 블라인드 평가, 순서 무작위화, 사전 지표를 사용한다. 불가능하면 어떤 요소가 함께 바뀌었는지 기록하고 “전통의 효과”가 아니라 **해당 팀 구성의 관찰 성과**라고 쓴다.

### 22.4 작은 표본 해석

- p-value나 평균 하나보다 과제별 원자료·효과 방향·최악 사례를 제시한다.
- `inconclusive`를 정상 판정으로 허용한다.
- incident 수 증가를 실패 증가로 단정하지 않는다. 탐지·보고 변화일 수 있다.
- 새 모델이 더 좋아졌다고 과거 패치가 무가치해진 것도, 패치가 새 모델의 성능을 만든 것도 아니다.
- 평가자가 같은 계열 모델이면 독립 표로 세지 않는다.
- 장기 수익·공동 브랜드·복리 성장 주장은 T0로 판단하지 않는다.

> **주요 결정 D20 — 효과 주장을 C0~C4로 제한하고, 분리 불가능한 변화가 있으면 구성 수준의 서술로 낮춘다.**
>
> **근거:** 헌장과 기준선은 모델 향상·사용자 숙련·도구 변화와 전통 효과를 구분할 수 없을 때 인과 주장을 낮추라고 명시한다. 로드맵은 같은 프로젝트 전후만으로 인과를 확정하지 말고 작은 표본에서 `inconclusive`와 원자료를 허용한다. fileciteturn0file7 fileciteturn0file1 fileciteturn0file2
>
> **추론:** 인과 통제가 약한 N-of-1 환경에서 단일 “효과 있음” 판정은 시스템의 자기신화를 강화한다.
>
> **제안:** 각 보고서에 허용 가능한 주장 수준을 붙이고, 동시 변화가 있으면 자동으로 한 단계 이상 낮춘다.
>
> **반증 조건:** 충분한 반복·무작위·블라인드 설계를 안정적으로 운영할 수 있고 더 강한 인과 추론이 실제 의사결정에 필요해지면 수준 정의를 확장한다.

### 22.5 공동 브랜드 평가의 한계

공동 브랜드는 초기에는 외부 시장 효과가 아니라 작업 방식의 일관성만 본다. 최소 증거는 다음과 같다.

- 서로 다른 세션·모델에서 사실·추론·제안 구분이 재현됨
- 중대 오류와 비용을 숨기지 않고 동일 형식으로 보고함
- 잘못된 패치를 철회하고 대체 이유를 남김
- AI 기여와 인간 승인 범위를 추적할 수 있음
- 고객·안전 요구가 내부 학습보다 우선됨

고객 신뢰, 수주율, 공모전 성과, 수익성에 미치는 브랜드 효과는 별도 장기 연구 없이는 주장하지 않는다.

> **주요 결정 D21 — 공동 브랜드의 초기 지표는 시장 성과가 아니라 검증·책임 행동의 재현성으로 제한한다.**
>
> **근거:** 헌장은 공동 브랜드를 특정 모델이나 홍보문구가 아니라 반복되는 품질 기준·검증 태도·책임 방식으로 정의하며, 2차 조사도 장기 브랜드 효과의 직접 증거가 없다고 밝힌다. fileciteturn0file7 fileciteturn0file3
>
> **추론:** 초기 수주·순위·고객 반응은 모델 성능·시장·프로젝트 난이도의 영향을 크게 받아 전통 브랜드의 효과로 분리하기 어렵다.
>
> **제안:** 브랜드는 내부적으로 관찰 가능한 작업 행동의 재현성만 평가하고, 시장 효과는 보류한다.
>
> **반증 조건:** 충분한 프로젝트 표본과 비교 가능한 외부 평가가 쌓여 브랜드 약속과 고객 선택·신뢰 사이의 관계를 분석할 수 있으면 별도 지표를 추가한다.

## 23. 단계적 로드맵

로드맵은 달력보다 진입·퇴출 gate로 운영한다. 어느 단계도 다음 단계를 자동 약속하지 않는다.

| 단계 | 수행할 것 | 진입 조건 | 통과 조건 | 실패 시 축소 |
|---|---|---|---|---|
| P-1 현재 — 독립 설계 | 이 문서 작성·비교. 구현·코드·스키마 생성 없음 | v1.1 기준선 | 독립 설계가 사실·추론·제안·반증을 구분 | 설계 수정 또는 비채택 |
| P0 준비 — 운영 안정성 확인 | 반복 작업 유형, acceptance rubric, baseline, 비식별 원자료 범위, 예산·중단 조건만 정함 | 오케스트레이터 또는 대체 프로젝트의 안정된 실제 흐름 | T0 진입 조건 모두 충족 | T0 보류, incident는 형식 리허설에만 사용 |
| P1 수작업 T0 | 한 등록부, 근거 메모 1개, trial 패치 1개, A/B/C 병렬 비교 | P0 통과 | C가 A와 B 대비 추가 가치 또는 안전 이득을 보이고 비용 상한 통과 | B가 낫다면 원자료 메모 방식, 모두 무효면 무기억/한 장 체크리스트 |
| P2 최소 운영 | 같은 작업 유형에서 소수 패치 운영, trial 전부와 active 표본 영수증, trigger 정비 | P1에서 패치 가치 지지 | 출처·철회·범위·비용을 월 30분 안에 유지하고 적어도 한 패치의 유지/축소/off 판정 | 패치 수 축소 또는 시스템 폐기 |
| P3 결정적 최소 자동화 | 필수 필드·철회·off 필터·판본·source link 검사, 단순 index | 동일 수작업 결함이 반복되고 자동화 편익이 예상됨 | false positive/negative와 유지비가 수작업보다 낮음 | 수동 등록부로 rollback |
| P4 프로젝트·모델 이주 | 넓은 범위 trial, 다른 프로젝트 또는 모델의 fresh 과제, core/adapter 필요성 검토 | 좁은 active 패치가 실제 효과를 보이고 새 맥락이 존재 | 전이 이득과 금지 조건 확인, 음의 전이 통제 | 프로젝트 범위로 강등, core 분리 안 함 |
| P5 검색 비교 | exact/keyword와 hybrid/semantic을 blind golden query로 비교 | 품질 검토 자료와 relevance label, 삭제·권한 필터 준비 | recall 개선이 precision·token·보안을 악화시키지 않음 | exact/keyword 유지 |
| P6 파인튜닝 별도 연구 | 검색으로 해결되지 않는 반복 행동을 위한 학습/holdout/rollback 검토 | 충분한 고품질 데이터·권리·재현성·명확한 목표 | RAG/prompt baseline 대비 추가 이득 | 파인튜닝 폐기 |

각 단계에서 구현할 기능은 그 단계의 실패를 해결하는 최소 범위뿐이다. P1이 실패하면 P3~P6은 진행하지 않는다.

> **주요 결정 D22 — 로드맵을 기능 축적 순서가 아니라 더 단순한 대안을 이겨야 통과하는 폐쇄형 gate로 설계한다.**
>
> **근거:** 기준선과 로드맵은 수작업 가치 검증 뒤 반복 마찰만 자동화하고, exact 검색의 한계가 측정되기 전 RAG를 도입하지 않으며, 효과가 없으면 스키마·자동화를 만들지 말라고 한다. fileciteturn0file1 fileciteturn0file2
>
> **추론:** “장기 방향”이 있으면 각 단계가 성공 여부와 관계없이 다음 기능의 정당화로 사용되기 쉽다.
>
> **제안:** 각 단계는 대조군, 통과 조건, rollback을 가지며 P1 실패 시 고급 단계 전체를 닫는다.
>
> **반증 조건:** 후속 단계가 선행 단계의 단기 지표와 다른 장기 가치를 만든다는 강한 근거가 있고 그 가치를 안전하게 시험할 수 있다면 예외적 병렬 실험을 별도 승인한다.

## 24. 아직 증거가 없어 결정하면 안 되는 사항

| 미결정 사항 | 현재 결정하면 안 되는 이유 | 필요한 근거 |
|---|---|---|
| 행동 패치가 원자료 메모보다 나은가 | 핵심 설계 가설 자체가 미검증 | T0 A/B/C 비교 |
| 최적 기록 trigger와 3분 상한 | 개인 사용성·누락률 자료 없음 | 실제 포착 시간, 누락된 고가치 사건, 유지율 |
| 월 30분 정비가 충분한가 | 사건량·패치 수·판정 난이도 미확인 | 두 개 이상 운영 주기의 backlog·오류·시간 |
| active 승격에 필요한 적용 횟수 | 위험·과제·지표별로 다름 | baseline 변동성과 반복 결과 |
| 범용 패치가 필요한가 | 서로 다른 실제 프로젝트 전이 자료 없음 | 다른 프로젝트의 사전 예측·fresh 적용 |

| exact/keyword 검색의 한계 | 실제 패치 집합과 golden query가 없음 | relevance label과 검색 감사 |
| semantic RAG의 가치 | 자료량·삭제·권한·오염 통제 미준비 | blind 검색 비교와 deletion test |
| 자동 주입의 안전성 | stale·off·충돌 패치 필터가 미검증 | 결정적 회귀시험과 실제 retrieval precision |
| 외부 독립 reviewer의 필요 범위 | 가용성·위험 기준·효용 자료 없음 | 고위험 판단 오류와 외부 검토 효과 |
| 공동 브랜드의 고객 가치 | 장기 직접 증거와 비교군 없음 | 여러 프로젝트의 블라인드 품질·고객 행동 자료 |
| 장기 복리 성장·수익성 | 한 개인과 여러 LLM 세대의 직접 연구 없음 | 장기 구성 기록과 반복 반사실 비교 |
| 현재 개발 incident에서 뽑은 체크리스트의 운영 가치 | incident는 개발·테스트 자료이고 전통 효과 증거가 아님 | 안정화 뒤 실제 운영의 fresh trial |
| 오케스트레이터 B1의 효율·장기 이득 | 반복 비교와 안정 운영 결과가 없음 | 독립된 B0/B1 평가와 운영 데이터 |
| 파인튜닝 | 데이터·목표·권리·holdout·rollback 없음 | 검색 baseline 실패와 충분한 학습·검증 세트 |
| 종합 전통 점수 | 작은 표본과 Goodhart 위험 | 실제 의사결정에 필요한 지표 구조가 반복 확인될 때도 신중 검토 |
