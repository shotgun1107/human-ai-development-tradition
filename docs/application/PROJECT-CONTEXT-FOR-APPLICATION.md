# 인간–AI 공동 개발 전통 — 삼성전기 AI 솔루션 지원서용 프로젝트 맥락

> **지원서·CONTROL용 2차 자료 — 독립 실험 입력으로 자동 사용 금지.** 이 문서는 과거 설계 선택과 감사 결과를 요약한다. 다른 지원서 프로젝트에서 맥락 자료로 쓰는 용도와, 새 독립 검토자·실행자에게 허용되는 연구 입력은 다르다. 연구 역할에는 이 파일이나 원 대화를 자동 첨부하지 말고, 해당 역할의 동결된 입력 목록을 따른다.

> 문서 목적: 다른 AI가 이 프로젝트를 이해하고 지원서 문항에 맞는 경험 소재를 선택하도록 돕는 내부 작성 자료다. 제출용 자기소개서나 제품 성과 인증서가 아니다.
>
> 작성일: 2026-09-15 · 프로젝트의 최근 종합 감사 결과: 2026-09-09
>
> 핵심 상태: **중앙 시스템 설계와 공개 시험 준비 구성요소가 있는 연구·개발 프로젝트다. 중앙 시스템 전체, 실제 공개 리허설, S0, 운영 효과를 완성·검증했다고 쓰면 안 된다.**

## 0. 이 파일을 사용하는 AI에게

- 먼저 §1의 요약을 읽고, 문항에 맞춰 §8의 역량 연결과 §9의 경험 카드를 선택한다.
- 프로젝트 사실은 §2–6, 지원자의 기여 범위는 §7, 표현 한계는 §10, 확인 질문은 §11을 따른다.
- 이 파일 하나로 기본 맥락을 이해할 수 있도록 작성했다. §12의 원문 경로는 추가 확인용이며, 다른 PC나 프로젝트에서 열리지 않을 수 있다.
- **프로젝트에 존재하는 산출물과 지원자가 직접 작성·구현한 산출물은 다르다.** AI가 수행한 구현·테스트·감사를 지원자의 단독 성과로 바꾸지 않는다.
- 지원 공고 원문, 실제 문항, 글자 수, 지원자의 상세 이력은 아직 제공되지 않았다. 직무 연결은 해석 후보이지 삼성전기의 공식 직무기술서 요약이 아니다.
- 누락된 기간·인원·개발 비중·사업 성과·개선율은 추정하지 않는다. 필요한 사실만 지원자에게 확인한다.
- 기록된 테스트 통과 수를 정확도, 생산성 향상률, 사업적 효과로 변환하지 않는다.
- 지원서에는 내부 버전·파일명보다 문제, 선택 이유, 지원자의 행동, 관찰 결과, 한계를 우선한다.
- 이 자료는 지원서 작성용이다. 원 프로젝트의 실행·수정·비공개 자료 접근·게시를 허가하거나, 원 저장소의 운영 규칙을 지원서 프로젝트에 그대로 적용하는 문서가 아니다.

### 바로 이해할 수 있는 짧은 소개

이 프로젝트는 AI와 개발하면서 얻은 경험이 세션과 모델 교체 때 단절되는 문제를 다룬다. 과거 기록을 그대로 주입하는 대신, 출처와 적용 조건이 있는 작업 자산으로 정리하고 현재 과제에서 다시 검증하는 체계를 목표로 한다. 중앙 기억·자산 관리 구조를 설계하고 공개 시험 도구를 준비했으며, 별도 감사를 통해 구성요소의 검증 결과와 전체 실행 가능성을 구분했다. 현재는 준비 단계로, 실제 운영 효과와 모델 간 전이는 아직 검증하지 않았다.

## 2. 출발점과 문제 정의

### 2.1 해결하려던 불편

목적 헌장과 설계 브리프에 다음 문제가 기록돼 있다. [S1, S2]

1. 새 세션이 이전 판단과 실패 이유를 모른다.
2. 잘된 결과가 있어도 성공 조건과 원인이 남지 않아 재사용하기 어렵다.
3. 프롬프트·Skill·체크리스트가 특정 모델이나 프로젝트에 묶인다.
4. AI가 더 빨라진 느낌과 실제 품질·시간·비용 개선이 혼동된다.
5. 문서와 규칙이 계속 늘어도 잘못된 규칙을 수정·폐기할 기준이 부족하다.
6. 여러 AI의 동의가 같은 자료에서 나온 반복 주장일 수 있는데도 독립적인 검증으로 오인되기 쉽다.

이것은 프로젝트의 문제 정의다. 반복 오류 발생률이나 손실액을 실제로 측정했다는 뜻은 아니다.

### 2.2 목적을 오해하면 안 되는 부분

- 개인 성장 일기나 개발 회고 저장소만 만드는 것이 목적은 아니다.
- 초기 접근은 모델의 가중치를 학습시키는 파인튜닝이 아니다.
- 여러 에이전트를 많이 실행하는 것 자체가 성과가 아니다.
- 중앙에 모든 원문을 복사하거나, 모든 프로젝트에 하나의 규칙을 강제하려는 것도 아니다.
- 원문에 나오는 ‘전통’은 **출처·맥락·반례·판본이 연결되고, 틀리면 수정하거나 폐기할 수 있는 작업 기억**을 뜻한다.
- 장기적인 ‘공동 브랜드’는 반복되는 품질과 책임의 계보라는 목표다. 대외 신뢰나 브랜드 가치가 이미 확보됐다는 실적은 없다.

### 2.3 중요한 요구사항 정정

설계 브리프는 이전 안이 작은 행동 규칙 엔진으로 좁아진 문제를 지적하고, 다음 두 원칙을 함께 요구했다. [S2 §0–5]

- **목표 시스템 전체의 책임은 충분히 정의한다.** 여러 프로젝트, 경험, 자산, 적용 결과, 모델 교체, 철회를 포함한다.
- **첫 구현과 시험은 작고 검증 가능하게 제한한다.** 전체 설계를 곧바로 대규모 서비스 구현으로 연결하지 않는다.

지원서에서는 이를 ‘큰 목표를 유지하면서 검증 가능한 개발 단위로 나눈 과정’으로 설명할 수 있다. 구체적으로 어느 요구사항을 지원자가 직접 수정했는지는 확인 후 서술한다.

## 3. 목표 시스템의 구조와 작동 방식

이 절은 **설계 설명**이다. 아래 기능이 모두 운영되는 완성 시스템이라는 뜻이 아니다. [S3 §3–6]

### 3.1 전체 흐름

1. 프로젝트의 성공·실패·결정·실험·비용·사람 수정 등에서 원근거를 확보한다.
2. 프로젝트 경계와 권한을 확인하고, 사실과 AI의 해석·요약을 구분한다.
3. 유사 사례와 반례를 비교해 조건부 경험으로 정리한다.
4. 필요할 때만 Skill·프롬프트·체크리스트·테스트 등의 작업 자산 후보를 만든다.
5. 현재 과제의 권한·상태·적용 조건에 맞는 소수의 자산을 제공한다.
6. 실제 채택·거부·변형·적용 결과를 회수해 자산의 범위를 조정하거나 중지·폐기한다.

### 3.2 주요 구성 책임

| 구성 | 설계상 책임 | 중요한 제약 |
|---|---|---|
| 경계·신뢰 확인 | 프로젝트 식별, 접근권한, 공개 범위, 입력의 신뢰 수준 확인 | 외부 자료의 명령형 문장을 운영 지시로 취급하지 않음 |
| 증거·실행 계보 | 프로젝트·작업·실행·모델·도구·기여·결정의 관계 보존 | 같은 원근거를 요약한 여러 결과를 독립 근거로 세지 않음 |
| 경험 해석·비교 | 사실, 해석, 가설, 반례, 조건 차이 분리 | 성공 하나를 곧바로 범용 규칙으로 만들지 않음 |
| 조건부 자산 관리 | 자산의 판본, 근거, 적용·금지 조건, 효력 관리 | 후보·제한 시험·활성·중지·폐기를 구분 |
| 선택·전달 | 현재 문제에 필요한 소수의 근거와 행동 지침 제공 | 관련성이 높아도 권한이 없거나 중지된 자료는 전달하지 않음 |
| 평가·철회 | 적용 결과, 오적용, 비용, 반례에 따라 수정·철회 | 사용량이나 문서 수만으로 효과를 판단하지 않음 |

이 구성은 논리적 책임 구분이지, 각각 별도 서버·DB·마이크로서비스로 구현했다는 뜻이 아니다.

### 3.3 다른 오케스트레이션 프로젝트와의 관계

별도로 구상·개발되는 프로젝트별 `Project Brain`은 현재 작업의 분해·실행·판단을 대표한다. 이 프로젝트의 중앙 시스템은 장기 기억·재사용·철회를 담당하는 방향이다. [S2 §2–3, S3 §4.4]

- 다른 멀티 AI 오케스트레이션 프로젝트의 성과를 이 프로젝트의 성과로 합치지 않는다.
- Project Brain과의 실제 API, 메시지 형식, 실행 순서, 통합 운영은 확정·검증된 실적이 아니다.
- RAG나 검색 기반 전달은 가능한 접근이다. 현재 벡터 DB·검색 서비스가 구현됐다고 추정하지 않는다.

### 3.4 구조 선택의 논리

설계는 중앙 저장소를 만드는 것을 당연한 정답으로 두지 않았다. 새 공통 계층 없음, 프로젝트 내부 정리, 최소 공통 목록, 최소 증거 계보를 비교 조건으로 유지했다. [S3 §2.6, §10.2]

채택한 방향은 최소 계보를 통해 출처·파생·적용·철회를 잇는 것이다. 다만 더 단순한 대안보다 오류를 줄이지 못하거나 관리비만 늘리면 목록이나 로컬 방식으로 축소하도록 했다. **이는 설계 가설과 포기 조건이지, 중앙화의 우수성을 실험으로 입증한 결과가 아니다.**

## 4. 실제 진행 범위와 검증 수준

### 4.1 단계별 상태

| 영역 | 확인되는 진행 내용 | 지원서에서 유지할 한계 |
|---|---|---|
| 목적·요구사항 | 목적 헌장, 독립 설계용 브리프, 여러 사용 상황과 책임 경계가 문서화됨 | 요구사항을 정의한 것과 기능을 구현한 것을 구분 |
| 중앙 시스템 v2.1 | 통합 설계와 제한 수정·재심사를 거쳐 S0 준비 기준선으로 채택됨 | 승인 범위는 준비 설계이며 운영 승인이나 제품 완성이 아님 |
| S0 | 합성 입력에서 중복 근거·권한·반례·상태·철회 등의 논리를 비교하기 위한 시험 설계·준비 | 실제 S0 실행·점수·성공은 주장하지 않음 |
| 공개 I0 도구 | 형식·무결성 검사, 결정적 입력 변환, 답안 형식 검사 코드와 검증 보고가 보존됨 | 공개 연습 입력용 기술 검사이며 AI 성능·운영 안전 검증이 아님 |
| 후속 공개 조립·adapter·runtime/native 작업 | 2026-09-09 감사에서 구성요소·빌드·생성물과 실행 차단을 확인한 이력이 있음 | 당시 임시 작업 자료는 현재 지정 경로에서 접근되지 않음. 현재 저장소에 모두 포함됐다고 쓰지 않음 |
| 종합 감사 | C01–C15의 조사·판정과 최소 수정 계획을 2026-09-09에 완료·전달함 | 오류 수정 완료나 전체 과거 실행의 재검증 완료가 아님 |
| 실제 운영·효과 | 아직 검증된 결과 없음 | 현장 적용, 고객 성과, 비용 절감, 모델 간 전이 성과를 만들지 않음 |

### 4.2 I0가 실제로 검사하는 것

보존된 I0 검증 보고서에 따르면 Python CLI와 테스트는 다음을 다룬다. [S5]

- 허용된 공개 입력의 파일 해시·목록 및 JSON 구조 확인.
- 하나의 기준 입력과 지정된 프로필로 예상 패키지를 바이트 단위로 재생성.
- 답안의 질문·선택지·인용·순서 등 형식 계약 확인.
- 잘못된 입력·경로에 대한 명시적 오류 반환과 기존 출력 덮어쓰기 방지.
- 일반 답안 검사에서 숨겨진 정답이나 점수 산정 경로를 사용하지 않는 경계.

여기서 ‘프로필’은 정해진 입력 표현·runtime 구성을 설명하는 내부 용어다. 사용자 프로파일링이나 개인 정보를 뜻하지 않는다.

### 4.3 기술 요소와 사용 수준

| 기술·방법 | 프로젝트 안의 용도 | 개인 역량 서술 시 주의 |
|---|---|---|
| Python | 공개 입력 변환, CLI, 검증·실행 준비 도구 | 지원자가 직접 구현한 함수와 이해 범위를 확인 |
| JSON / JSON Schema | 입력·답안·기록의 구조 계약과 오류 확인 | 업무 모델 정확도 검증과는 다름 |
| unittest / jsonschema | 단위·형식 검증 기록 | 과거 환경은 Python 3.12.10, jsonschema 4.26.0으로 기록됨. 현재 환경 재실행은 하지 않음 |
| SHA-256 / manifest | 검토·시험 대상의 정확한 바이트와 파일 집합 식별 | 해시 일치가 코드의 올바른 동작이나 성능을 증명하지 않음 |
| Git / Markdown | 버전·요구사항·검증·판단 기록 관리 | 커밋 상태와 임시 작업 상태를 구분 |
| PowerShell / Windows 도구 | 실행·검증·빌드 환경 관리 | 실제 직접 사용 범위는 지원자 확인 필요 |
| C++ / Win32 API | 후속 native runtime 준비·경계 구현 후보 | 9월 9일 감사로 확인한 후속 작업 이력. C++·시스템 프로그래밍 숙련도나 본인 단독 구현을 자동으로 주장하지 않음 |
| Codex 및 역할별 AI 작업 | 설계·구현·시험·문서·독립 검토 지원 | 인간 팀 협업 경력이나 사람 개발팀 인원으로 바꾸지 않음 |

## 5. 수치로 활용할 수 있는 근거와 그 의미

아래 수치는 **현재 보존된 I0 보고서에 기록된 과거 검증 결과**다. 이 문서를 만들면서 시험을 다시 실행하지 않았다. 최신 전체 시스템의 통과 수치로 사용하지 않는다. [S5]

| 기록 | 실제 의미 | 하면 안 되는 해석 |
|---|---|---|
| 테스트 36개 중 35개 통과, 1개 skip | 당시 Windows 호스트의 I0 후보 시험 결과. 심볼릭 링크 생성 시험 1개가 건너뛰어짐 | ‘전체 테스트 100% 통과’, ‘모든 경로 안전 검증’ |
| 패키지 8개 재생성 일치 | 지정된 공개 패키지 8개와 두 번 실행한 결과가 바이트 단위로 일치 | 새 입력·새 모델에 대한 일반화 성능 |
| 공개 manifest 90개 항목·JSON 56개 검사 | 해당 공개 입력 묶음의 형식·무결성 검사 기록 | 제품 기능 90개, 실제 고객 데이터 56개, AI 정확도 |
| 적용 대상 schema instance 19개 오류 0 | 해당 형식 계약에 대한 유효성 검사 기록 | 업무 정답률 100%, 결함 0개인 제품 |

숫자보다 ‘무엇을 검증했고 무엇을 검증하지 않았는가’를 설명하는 편이 중요하다. 작은 지원서 문항에는 **35개 통과·1개 skip** 또는 **8개 패키지의 결정적 재생성** 정도만 필요한 맥락과 함께 선택한다.

### 실제로 수정된 공개 입력 불일치 사례

I0 보고서는 공개 패키지 식별자의 길이와 고정 schema 규칙이 맞지 않았던 문제를 기록한다. 승인된 범위에서 식별자·경로를 정정했고, 패키지 내용 바이트·해시는 유지됐으며 이후 관련 schema 검사가 오류 0으로 기록됐다. [S5, “Resolved upstream discrepancy”]

이 사례는 ‘명세와 실제 데이터 계약을 대조하고 영향 범위를 확인한 과정’의 소재가 된다. **지원자가 직접 결함을 발견하거나 패치를 작성했다는 근거는 별도로 확인해야 한다.**

## 6. 종합 감사에서 확인한 문제와 배움

### 6.1 당시 감사의 핵심 결과

다음은 2026-09-09에 이 대화에서 회수·전달한 독립 감사 결과다. 이번 작성 시 동일 검사를 다시 실행하지 않았다. [S6]

| 문제 | 당시 근거 수준 | 실질적인 의미 |
|---|---|---|
| native package 검사 목록 불일치 | 정적 확인 | 처음에는 파일 7개를 요구하고 재검사에서는 6개를 요구해, 정상 패키지가 뒤 단계에서 거부되는 경로가 있었음 |
| Python 파일 감시기의 os.open 해석 오류 | 격리 재현 | 실제 이벤트 `(path, None, flags)`를 잘못 해석해 허용된 파일 읽기도 거부했음. 전체 native 실행 재현과는 다름 |
| 과거 프로필과 새 runtime의 결합 충돌 | 정적 확인 | 서로 다른 runtime manifest를 동일 바이트로 묶는 규약 때문에 다음 실행이 막혔음 |
| 종료 결정과 현재 작업 원장 불일치 | 기록 대조 | 끝난 검토가 진행 중으로 남아 다음 작업 판단을 혼동시킬 수 있었음 |

감사는 오류·한계와 수정 계획을 정리한 것이며 위 문제가 수정됐다는 기록은 아니다. 지원서에서 ‘문제를 해결했다’고 쓰려면 실제 수정·재검증 근거를 추가해야 한다.

### 6.2 일반화할 수 있는 교훈

- 각 구성요소의 테스트가 통과해도 실제로 연결했을 때 정상 경로가 실패할 수 있다.
- 대역(mock) 중심 테스트와 실제 API 이벤트·파일 읽기의 조합은 별도 확인이 필요하다.
- 빌드 성공, 파일 생성 성공, 단위 검사 통과, 전체 실행 성공은 다른 증거 수준이다.
- 완료 보고와 다음 작업의 기준 문서가 연결돼야 중복 작업과 잘못된 재개 판단을 줄일 수 있다.
- 복잡한 검증 도구를 늘리는 것보다 현재 업무를 막는 직접 원인을 분리하는 것이 먼저다.

이는 프로젝트에서 얻을 수 있는 교훈이다. 반복 오류 감소율, 재작업 감소율, 운영 비용 절감액을 실제로 측정했다는 주장은 아니다.

### 6.3 현재 가용성에 관한 제한

2026-09-15 확인 시, 당시 감사 보고서와 최신 임시 작업 폴더의 지정 경로는 접근 가능한 파일로 확인되지 않았다. 원 저장소의 HEAD는 당시 확인값과 같지만, 그것만으로 과거 임시 작업의 모든 바이트가 보존됐다고 볼 수 없다.

따라서 핵심 소개는 현재 읽을 수 있는 목적·설계·I0 보고서를 기반으로 하고, 후속 native 작업과 종합 감사는 **날짜가 명시된 과거 확인 이력**으로 활용한다. 삭제 원인이나 모든 사본의 부재는 확인하지 않았다.

## 7. 지원자의 기여와 AI 기여 구분

### 7.1 현재 자료가 뒷받침하는 범위

| 구분 | 확인되는 내용 | 지원서 작성 방식 |
|---|---|---|
| 사용자 목적 | 개인 회고를 넘어 AI의 반복 오류와 경험 단절을 다루려는 목적이 헌장·브리프에 사용자 의도로 명시됨 | 본인이 이 문제를 발견한 실제 상황을 확인해 동기로 연결 |
| 목표·제약·승인 | 전체 목표와 작은 첫 시험의 구분, 인간 승인과 책임, 실제 가치 우선 등의 기준이 문서화됨 | 지원자가 직접 제안·검토·변경한 구체적 결정을 골라 서술 |

### 7.2 기여 표현 원칙

- ‘제가 모든 코드를 설계·구현·검증했습니다’보다 실제로 본인이 수행한 결정과 검토를 구체적으로 쓰는 것이 낫다.
- ‘AI로 만들었습니다’만으로 끝내지 말고, **무슨 문제를 주었고, 어떤 기준으로 결과를 수용·거부했으며, 무엇을 바꾸게 했는지**를 설명한다.
- AI 독립 검토와 인간 조직에서의 팀워크는 다른 경험이다. 사람 팀원과의 협업 사실이 없다면 팀 협업 문항의 핵심 사례로 억지로 사용하지 않는다.
- AI가 발견한 오류를 활용할 때는 ‘독립 감사에서 발견된 오류를 바탕으로 …’처럼 주체를 유지한다.
- 설계 이해도·코딩 숙련도는 면접에서 본인이 설명·수정할 수 있는 범위를 기준으로 표현한다.

## 8. AI 솔루션 직무와 연결할 수 있는 역량

아래는 **지원서 해석 후보**다. 삼성전기 공고의 실제 담당 업무·필수 역량과 대조해 관련 있는 항목만 사용한다. 회사의 내부 시스템이나 구체적인 현장 과제를 알고 있다는 식으로 쓰지 않는다.

| 역량 관점 | 프로젝트에서 연결할 근거 | 연결하기 좋은 문항 |
|---|---|---|
| 업무 문제를 기술 요구로 바꾸는 능력 | ‘기억을 많이 저장’하는 요구를 출처·적용 조건·검증·철회가 있는 자산 관리 문제로 구체화 | 직무 적합성, 문제 해결, 프로젝트 소개 |
| AI 기반 시스템 설계 | 장기 기억과 현재 프로젝트 실행의 책임을 분리하고, 목표 구조와 첫 검증 단위를 나눔 | 기술 경험, 설계 판단, 도전 경험 |
| 데이터·명세 품질 관리 | schema·manifest·결정적 변환으로 입력 계약과 시험 대상의 일관성을 다룸 | 꼼꼼함, 품질 개선, 오류 해결 |
| 검증 중심 AI 활용 | AI의 완료 보고를 실제 명세·코드·시험·후속 활용과 대조하는 감사를 요청함 | AI 활용 경험, 신뢰성, 책임감 |
| 실패 분석과 한계 관리 | 정상 경로 거부, 프로필 결합 충돌, 대역 시험의 한계를 구분함 | 실패 경험, 배운 점, 개선 방향 |
| 기술과 비용의 균형 | 새 체계가 단순한 대안보다 유용하지 않으면 축소·중단하도록 기준을 둠 | 의사결정, 효율, 우선순위 판단 |
| 지식 재사용 설계 | 프로젝트별 경험의 출처·조건·판본·적용 결과를 연결하려는 구조 | 지식 기반 업무 지원, 지속 개선 관련 문항 |

### 제조·업무 현장과 연결할 때의 경계

‘이와 같은 출처·조건·검증 관리 관점을 향후 현업 지식 재사용이나 AI 업무 지원 과제에도 적용하고 싶다’는 **향후 적용 의지**는 설명할 수 있다. 그러나 이 프로젝트로 제조 데이터를 분석했다거나, 공정 최적화·불량 검출·수율 개선·현장 배포를 수행했다고 쓰면 안 된다. 그런 경험은 별도 자료가 필요하다.
