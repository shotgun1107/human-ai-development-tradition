# 단계별 구축과 평가 계획

## 1. 전략

이 체계는 한 번에 완성하지 않는다. 먼저 수작업으로 가치와 필드를 검증하고, 반복되는 마찰만 자동화한다. 장기 방향은 검색 가능한 개인 조직 기억이지만 첫 성공 기준은 “문서가 많아짐”이 아니라 다음 프로젝트의 한 결정 또는 한 검증 단계가 더 좋아지는 것이다.

현재 경계와 확인된 기반:

- 전통 연구는 원천 오케스트레이터와 분리된 독립 프로젝트다.
- 원천 프로젝트에서 B1 순차 실행 구성요소와 실제 Codex smoke가 완료됐지만, 범용 오케스트레이터 전체는 아직 구축·테스트 단계이며 운영 체계로 보지 않는다.
- 비라이브 회귀시험과 구조화된 **개발·테스트 incident**가 존재하지만 실제 운영 경험과 전통 효과의 증거는 아니다.
- B0/B1 동결 manifest는 있으나 두 fixture × 각 3회 반복 비교는 미실행이다.

따라서 B1 효율 우위를 교리로 만들지 않고, 현재 incident로 전통의 효과를 검증했다고 주장하지 않는다. 지금 단계는 운영 실험이 아니라 연구 기반 기획·시스템 설계 경쟁이다. 수작업 T0는 원천 프로젝트 또는 다른 실제 프로젝트가 아래 진입 조건을 충족할 때까지 보류한다.

## 2. 단계별 로드맵

### Phase T-1 — 연구 기반 독립 설계와 기준선 확정(현재)

목표: 구현 없이 두 개의 독립 기획·시스템 설계를 비교할 수 있는 v1.1 기준선을 확정한다.

범위:

- 목적·철학, 문헌, 외부 비판 심사의 사실 오류와 공통 전제 교정
- 같은 v1.1을 입력으로 한 독립 설계안 A/B
- 현재 운영 데이터가 없다는 사실과 미래 T0 진입 조건 명시
- 코드·스키마·RAG·자동화 구현 금지

통과 조건:

- 두 설계가 같은 해시 기준선을 사용함
- 확인된 사실, 설계 가설, 미래 검증 계획이 분리됨
- 정제 수명주기를 채택하지 않는 최소안도 경쟁에서 탈락하지 않음
- 실제 운영 효과나 T0 결과를 꾸며내지 않음

### Phase T0 — 수작업 연결과 첫 회고(진입 조건 충족 뒤 1개월)

진입 조건:

- 원천 프로젝트 또는 다른 실제 프로젝트에 반복 가능한 과제군과 안정된 작업 흐름이 있다.
- 개입 전 품질·시간·비용 기준선을 측정할 수 있다.
- 실제 사용에서 나온 사건과 성공·결정·실험이 비식별 가능한 형태로 축적됐다.
- 고객 품질에 영향을 주지 않는 안전한 내부 trial을 설계할 수 있다.
- 사용자가 시간 예산, 중단 조건, 사용할 원자료 범위를 승인했다.

목표: 새 하네스 없이 기존 기록에서 한 번의 완전한 학습 순환을 수행한다.

범위:

- 실제 운영에서 나온 소수의 사건과 직접 관련 원자료만 입력으로 사용
- 구축·테스트 incident는 데이터 형식 점검에는 쓸 수 있지만 운영 효과 증거에서는 제외
- experience 표 4~8개 수작업 작성
- lesson candidate 최대 3개
- 프로젝트 trial doctrine 최대 1개
- 실행 산출물 1개와 평가 계획 1개
- 범용 active 교리 0개

개발 incident에서 도출한 preflight 체크리스트는 미래 후보 또는 형식 리허설일 뿐, 실제 운영 trial은 진입 시점의 과제와 기준선에 맞춰 새로 선택한다.

통과 조건:

- 모든 주장에 기존 원자료가 연결됨
- 사실·추론·제안 혼합 결함 0건
- 비밀 검토 완료
- 승인된 trial이 반증 가능한 사전 지표를 가짐
- 회고 총 수작업 시간이 기록됨

중단/축소 조건:

- 원자료 연결에 2시간 이상 걸리면 필드를 줄인다.
- 후보를 만들기 위해 근거 없는 과거 기억을 채워야 하면 그 후보를 버린다.
- 기존 benchmark 계획을 바꾸거나 결과를 미리 보게 되면 실험을 분리한다.

### Phase T1 — 두 번의 월간 순환과 최소 파일 계약(2~3개월)

목표: 실제 사용된 필드만으로 최소 데이터 계약을 확정한다.

범위:

- experience/lesson/doctrine/application/evaluation/review의 Markdown 또는 YAML 최소 형식
- ID, 상태, 출처, evidence grade, scope, review_due 검사
- 수작업 생성 인덱스
- active/trial/retired 필터
- 프로젝트 doctrine만 운영

통과 조건:

- 두 달 연속 회고 완료
- 적어도 한 trial이 실제 다음 작업에 적용 또는 명시적으로 면제됨
- 적용 판본과 결과를 재구성 가능
- 오래된/기각 문서가 현재 bundle에 들어가지 않음
- 유지 비용이 월 90분 안팎 또는 사용자 허용 범위

자동화 보류:

- 벡터 DB/RAG
- 자동 교리 생성·승격
- 전체 revision log 소급 이관
- 모델 파인튜닝

### Phase T2 — 결정적 검증과 검색 baseline(3~6개월)

목표: 반복 실수와 검색 누락을 작은 도구로 줄인다.

후보 기능:

- schema/필수 필드/상태 전이 검증
- unsafe path와 secret/PII 패턴 검사
- 원본 링크와 hash 존재 검사
- 교리 판본·대체 관계·review_due 검사
- 결정적 Markdown 인덱스
- exact filter + keyword 검색 baseline
- 프로젝트 시작 doctrine bundle 생성 전 사람 preview

통과 조건:

- golden query 10~20개에서 precision@3와 recall@5 기준 충족
- retired/rejected current retrieval 0건
- 누락 출처와 stale 교리 자동 탐지
- 도구 false positive/negative를 월간 검토에 기록
- 자동화 시간이 수작업 절약보다 크지 않음

### Phase T3 — 프로젝트 간 전이 실험(6~12개월)

목표: 개인 범용 교리의 가치와 오적용 위험을 검증한다.

전제:

- 서로 다른 AI 개발 프로젝트 또는 명시적으로 다른 작업 맥락 둘 이상
- 프로젝트 active 교리의 적용·평가 기록
- 동일 메커니즘의 반복 근거

범위:

- 범용 trial doctrine 1~3개
- 각 규칙에 금지 조건과 대표 반례
- 새 프로젝트 시작 시 적용/비적용 예측을 사전 기록
- 적용 프로젝트와 holdout/비적용 프로젝트 비교

통과 조건:

- 범용 bundle이 관련 규칙을 찾는 시간을 줄이거나 오류·재작업을 감소
- guardrail 비용·토큰·시간 악화가 허용 범위
- 프로젝트 예외가 너무 많지 않음
- 적어도 한 범용 후보를 강등·기각할 수 있을 정도로 반례 절차가 실제 작동

### Phase T4 — 제한적 RAG와 고급 검색(자료가 충분한 뒤)

목표: exact/keyword baseline보다 semantic retrieval이 실질적으로 나은지 검증한다.

전제:

- 수십~수백 개의 품질 검토된 경험과 교리
- golden query, relevance label, 상태 필터
- 삭제·재색인·접근 통제 절차

실험:

- keyword vs hybrid retrieval blind 비교
- active doctrine recall, 반례 recall, irrelevant context 비율
- citation correctness와 doctrine version 정확도
- prompt injection 문구가 있는 과거 문서를 데이터로 안전하게 처리하는지 시험
- 삭제된 민감 문서가 index/cache에서 사라지는지 확인

중단 조건:

- keyword baseline 대비 유의한 개선 없음
- 상태·권한 필터를 semantic layer가 우회
- 잘못된 유사 사례 주입으로 품질 악화
- 운영 비용이 개인 사용 가치를 넘음

### Phase T5 — 파인튜닝 검토(장기 선택 사항)

다음을 모두 충족할 때만 별도 연구한다.

- 검색·프롬프트 방식으로 해결되지 않는 반복 행동 문제가 명확함
- 충분한 고품질 학습/검증/holdout 데이터
- 개인정보·라이선스·삭제 권리 확인
- base model과 학습 recipe를 재현 가능
- RAG/prompt baseline 대비 사전 정의된 개선
- rollback과 회귀 평가가 가능

월간 문서 갱신만으로도 목표를 달성하면 파인튜닝은 하지 않는다.

## 3. 최소 실험 설계

### Experiment T0-1: benchmark preflight 교리의 효과

연구 질문:

> 출처·hash·placeholder 검사 체크리스트가 B0/B1 반복 비교의 잘못된 입력 또는 준비 재작업을 실행 전에 탐지하는가?

주의: 이미 placeholder incident를 경험했으므로 같은 결함을 다시 일부러 원본 benchmark에 넣지 않는다. 원본·동결 설계를 수정하지 않고 별도 복제 또는 합성 표본에서 체크리스트를 검증한다.

가설:

- H1: 체크리스트 적용 시 알려진 합성 결함의 사전 탐지율이 높다.
- H2: 실제 비교 준비 시간의 과도한 증가는 없다.
- H3: checklist completion만 하고 실질 검사를 하지 않는 형식적 준수는 탐지율을 높이지 못한다.

설계:

1. 실제 benchmark 파일을 변경하지 않는 별도 표본에 4~6개 결함을 만든다: placeholder, 잘못된 commit, tree mismatch, 누락 seed, 결과 경로 충돌 등.
2. 체크리스트 없이 기존 README만 사용하는 baseline 검토와 체크리스트 검토를 시간 분리해 수행한다.
3. 결함 위치를 미리 보지 않거나, 가능하면 다른 사람이 결함을 주입한다.
4. 탐지 수, false positive, 검토 시간, 수정 전 실행 진입 여부를 기록한다.
5. 실제 B0/B1 실행에서는 체크리스트 판본과 적용 결과만 기록하고 benchmark/동결 설계는 바꾸지 않는다.

주요 지표:

- defect detection rate before execution
- false positive count
- preflight duration
- execution aborted due to invalid input
- post-start rework count

guardrail:

- 체크리스트 10개 항목 이하
- 준비 시간 증가의 초기 허용 상한을 baseline의 20% 또는 절대 15분 중 큰 값으로 임시 설정
- 원본 fixture·manifest 변경 0건

판정:

- 탐지율 개선과 guardrail 통과: 프로젝트 trial 유지, 실제 적용 추가
- 탐지율 개선이나 비용 과다: 체크리스트 축소 후 재시험
- 개선 없음: 폐기 또는 자동 검사로 표현 변경
- 실제 비교에서 새 결함을 발견하더라도 B1 우위 증거와 교리 효과 증거를 구분

### Experiment T0-2: 검색 가능한 문서 bundle의 가치

T1 이후 선택 실험이다.

질문:

> 새 작업 시작 시 관련 active 교리와 대표 사례·반례를 1페이지 bundle로 제공하면, 전체 로그를 직접 읽는 것보다 올바른 preflight 선택이 빨라지는가?

비교:

- A: `codex-revision-log.md`와 incident index만 제공
- B: 상태·범위로 필터한 1페이지 doctrine bundle + 원본 링크 제공

과제:

- 새 SDK integration 사전 점검 계획
- 새 benchmark fixture 동결 계획
- timeout/approval 기본값 검토 계획

지표:

- 필수 안전 항목 recall
- 잘못 적용한 교리 수
- 출처 정확성
- 계획 시간과 입력 token
- retired/irrelevant 규칙 포함 수

AI가 평가자일 수 있지만 사람 정답표와 교차 검토한다.

## 4. 평가 체계

### 4.1 결과 지표

| 목표 | 핵심 지표 | 해석 주의 |
|---|---|---|
| 품질 향상 | 회귀 결함, acceptance 실패, 재작업 | 프로젝트 난이도 보정 필요 |
| 판단 개선 | 사전 위험 발견률, 결정 번복률 | 번복은 나쁜 것만은 아님 |
| 효율 | wall-clock, token, 회고·검색 시간 | 품질 희생 여부 함께 봄 |
| 재사용 | 관련 교리 적용률, 검색 성공률 | 높은 적용률 자체가 목표 아님 |
| 학습 완결 | verified action rate | action close와 효과 검증 분리 |
| 안전 | 비밀 노출, stale/retired 주입 | 한 건도 심각할 수 있음 |
| 적응 | 강등·폐기·범위 축소 | 0이면 경직 가능성 조사 |

### 4.2 선행 지표와 후행 지표

선행:

- provenance completeness
- redaction review rate
- doctrine bundle size
- review_due 준수
- 다음 실험의 사전 지표 등록률
- 체크리스트 실제 증거 첨부율

후행:

- 반복 incident 비율
- 같은 원인의 회귀시험 탐지율
- 다음 프로젝트의 acceptance 품질
- 비용·시간·token 변화
- 교리 적용 후 mixed/contradicts 비율

### 4.3 측정 설계 원칙

- 결과를 보기 전에 가설·주요 지표·guardrail을 기록한다.
- 같은 프로젝트의 전후 비교만으로 인과를 확정하지 않는다.
- 가능한 경우 동일 fixture, seed, 모델·도구 판본, 반복 실행을 사용한다.
- 모델 변동성 때문에 단일 turn의 승패를 일반화하지 않는다.
- 통계적 검정이 불가능한 작은 표본에서는 효과 크기와 원자료를 제시하고 `inconclusive`를 허용한다.
- AI judge는 사람 표본과 보정하고 judge prompt/model 판본을 기록한다.
- 품질 향상과 보고 증가를 구분한다. incident 건수 증가가 탐지 문화 개선일 수 있다.

## 5. 주요 실패 모드와 통제

| 실패 모드 | 조기 신호 | 통제 |
|---|---|---|
| 일화의 교리화 | 단일 성공에서 범용 주장 | E등급·trial·독립 반복 |
| 생존자 편향 | 성공만 capture | 실패·면제·비적용 trigger |
| 후견지명 편향 | 원인을 당연시 | 당시 정보·대안·timeline 보존 |
| root cause 단일화 | 사람 실수 한 줄 | 기여 요인·대안 가설·시스템 관점 |
| 형식적 체크리스트 | 완료율 높고 결함 지속 | 증거 첨부·결과 지표·시행 충실도 |
| action graveyard | 미완료 backlog 증가 | owner·기한·효과 판정, WIP 제한 |
| 교리 팽창 | bundle이 계속 커짐 | 월 1~3개 제한·중복 병합·폐기 |
| 규칙 충돌 | 모델이 상황마다 다른 지시 | scope·우선순위·contested 상태 |
| stale knowledge | SDK 변경 뒤 옛 규칙 적용 | dependency trigger·review_due |
| AI 권위 편향 | AI 요약이 원본보다 우선 | advisory 라벨·사람 승인·source ID |
| RAG 오검색 | 그럴듯한 무관 사례 주입 | exact filter·golden queries·abstain |
| prompt injection in memory | 과거 문서 명령 실행 | 문서를 데이터로 격리·허용목록 |
| 비밀 확산 | 요약·embedding에 token 잔존 | 수집 최소화·사전 redaction·삭제 시험 |
| Goodhart 효과 | 지표만 좋아지고 품질 악화 | primary+guardrail+원자료 감사 |
| 과도한 회고 비용 | 기록 시간이 개발을 잠식 | 필드 축소·비례 trigger·자동화 게이트 |
| 망각 불능 | 폐기 규칙이 계속 검색 | 상태 필터·대체 관계·retirement test |

## 6. 의사결정 게이트

### T0 → T1

- 첫 회고가 실제 한 개의 가역 trial을 만들었는가?
- 출처·redaction·평가 계획을 수작업으로 유지할 수 있는가?
- 사용자에게 다음 작업의 명확한 가치가 있었는가?

아니면 스키마 구현을 하지 않고 capture note만 유지한다.

### T1 → T2

- 같은 검증·인덱스 작업이 두 달 이상 반복됐는가?
- 자동화할 안정된 필드와 상태가 확인됐는가?
- 자동화가 기존 incident 하네스와 충돌하지 않는가?

아니면 수작업을 계속하고 필드를 바꾼다.

### T2 → T3

- 프로젝트 doctrine이 실제 효과 평가를 통과했는가?
- 다른 맥락이 생겼는가?
- 범용화가 해결할 반복 문제가 있는가?

아니면 범용 교리를 만들지 않는다.

### T3 → T4

- exact/keyword 검색의 측정된 한계가 있는가?
- 품질 검토된 자료량과 relevance set이 충분한가?
- 접근 통제·삭제·상태 필터를 보장할 수 있는가?

아니면 RAG를 도입하지 않는다.

## 7. 현재 설계 단계와 미래 T0 첫 30일

현재 수행할 일은 v1.1 기준선으로 독립 설계안 A/B를 만들고 비교하는 것이다. 아래 실행안은 앞의 T0 진입 조건을 충족한 뒤에만 시작한다.

1. 사용자가 승인한 실제 운영 사건의 범위와 개입 전 기준선을 고정한다.
2. 각 사건에서 사실·추론·제안을 다시 분리한다.
3. 반복 가능성이 있는 후보를 최대 3개만 쓴다.
4. 고객 품질과 원천 프로젝트의 기존 비교를 방해하지 않는 내부 trial 하나를 선택한다.
5. 체크리스트 초안, baseline, 결함 표본, 주요 지표, guardrail을 사전 고정한다.
6. 첫 월간 회고에서 프로젝트 trial 최대 1개만 승인한다.
7. 실제 다음 작업의 application/evaluation을 남긴다.
8. 두 번째 회고에서 유지·수정·폐기 중 하나를 반드시 판정한다.

## 8. 확인 범위와 미확인 범위

확인한 것:

- 원천 오케스트레이터 저장소의 incident schema·CLI·tests·초기 개발 entry·생성 index 구조
- 원천 `codex-revision-log.md`의 역할과 B1 구성요소 smoke/B0-B1 미완료 상태
- 공식·원자료 및 동료평가 문헌에서 관찰/교훈 분리, 행동 검증, 무과실, 비식별 보고, 사례 검색, CAPA/PDSA, 체크리스트 효과의 맥락 의존성

확인하지 않은 것:

- 전통 데이터 스키마의 실제 구현 가능성과 사용자 사용성
- 구축·테스트 incident가 아닌 실제 운영 경험에서 T0가 유용한 산출물을 만드는지
- 월 60~90분, 승격 1~3개, E등급 임계값의 경험적 적합성
- 검색/RAG의 실제 precision·recall과 token 비용
- 이 체계가 B0/B1 또는 향후 프로젝트 품질을 실제로 높이는지
- 외부 독립 reviewer의 가용성과 고위험 기준

이 미확인 항목을 설계 결함으로 숨기지 않고 T0~T4의 실험 대상으로 둔다.
