# 인간–AI 공동 전통 기획·시스템 설계 경쟁 공통 규격

> 규격 버전: 1.1.0  
> 상태: 독립 설계안 A/B 공통 과업  
> 기준일: 2026-08-05  
> 적용 대상: 서로의 결과를 보지 않고 작성하는 두 개의 독립 기획·시스템 설계  
> 금지: 구현, 기존 B1·benchmark·동결 문서 수정, 커밋·푸시, 상대 설계 열람

## 0. 이 문서의 역할

이 문서는 완성된 설계도, 특정 모델용 프롬프트, 구현 명세가 아니다. 서로 다른 두 설계자가 **동일한 문제·자료·제약·산출물 계약**을 받고 독립적인 해법을 만들도록 하는 공통 설계 규격이다.

두 제안은 같은 질문에 답해야 하지만 같은 구조나 결론을 낼 필요는 없다. 기존 초안을 개선해도 되고, 목적·철학 헌장을 지키는 범위에서 전혀 다른 개념 구조를 제시해도 된다. 차이를 인위적으로 만들기보다 각자 가장 일관되고 현실적인 설계를 선택한다.

최종 판단자는 두 문서를 기계적으로 합치지 않는다. 항목별로 채택·기각·실험 보류를 결정하며, 공통된 주장도 독립된 증거로 간주하지 않는다.

## 1. 설계 목표

다음 목적을 달성하는 인간–AI 공동 개발 전통의 **기획과 시스템 설계**를 작성한다.

> 실제 프로젝트에서 인간과 AI가 얻은 검증된 경험을 모델 밖에 보존하고, 세션과 모델 세대가 바뀌어도 다음 AI가 이를 이어받아 더 나은 작업을 재현하게 하며, 그 계보 있는 작업방식 자체를 인간–AI 공동 브랜드로 만든다.

설계는 단순 오류 로그, 개인 지식관리, 프롬프트 모음, 무제한 대화 보존, 모델 파인튜닝과 구별되어야 한다. 초기에는 검색 가능한 문서·외부 기억·Skill·테스트·프롬프트 주입과 사람 승인으로 운영하고, 효과가 입증된 부분만 장기적으로 자동화할 수 있어야 한다.

## 2. 권위와 입력의 우선순위

입력 사이에 충돌이 있으면 다음 순서를 적용한다.

1. 사용자가 직접 밝힌 목적과 명시적 제약
2. `purpose-and-philosophy.md` v1.1.0
3. 확인된 저장소 사실과 금지 범위
4. 1·2차 조사에서 `확인`으로 분류된 사실과 출처
5. 조사 문서의 설계 가설과 반증 조건
6. 기존 `system-design`, `monthly-review-playbook`, `roadmap-and-evaluation`

기존 설계 문서는 참고 초안이지 유지해야 할 정답이 아니다. 2차 조사와 헌장에 맞지 않는 부분은 채택하지 않거나 명시적으로 대체한다. 반대로 새로워 보인다는 이유만으로 검증된 기존 요소를 버리지 않는다.

## 3. 공통 입력 자료

두 설계자는 기준선 명세에 기록된 동일 판본을 사용한다.

### 3.1 규범 기준

- `purpose-and-philosophy.md` — 목적, AI 성장, 계승, 공동 브랜드, 가치 우선순위, 책임·비목표

### 3.2 연구 근거

- `research.md` — AAR, SRE, ADR, 조직기억, 안전, CBR, 품질관리의 1차 조사
- `research-human-ai-joint-tradition.md` — 인간–AI 공동인지, 에이전트 기억, 누적문화, 구현과학, 평가, 경제, 브랜드, 메모리 보안의 2차 조사

### 3.3 재검토 대상인 기존 초안

- `system-design.md`
- `monthly-review-playbook.md`
- `roadmap-and-evaluation.md`

### 3.4 확인된 저장소 맥락

- 전통 연구는 원천 오케스트레이터와 분리된 독립 프로젝트다.
- 원천 프로젝트는 범용 로컬 세션 오케스트레이터를 B0~B3 단계로 개발 중이며 아직 구축·테스트 단계다.
- B1 순차 실행 구성요소와 실제 smoke는 완료됐지만 전체 오케스트레이터가 운영 가능하다는 뜻은 아니다.
- B0/B1 반복 비교는 아직 완료되지 않았다.
- `tools/implementation-log/`와 `docs/operations/implementation-incidents/`에 개발 incident 하네스와 초기 사건이 있다.
- incident 하네스는 사실·사건의 한 출처 계층이며 공동 전통 전체와 동일하지 않다. 현재 기록은 개발·테스트 incident이므로 전통의 운영 효과 증거로 사용하지 않는다.
- `docs/operations/codex-revision-log.md`는 시간순 작업·검증 기록으로 참고할 수 있으나, 효력 있는 교리 저장소는 아니다.
- 현재 B1의 효율이나 오케스트레이션의 장기 이득을 확정할 실증 근거는 없다.
- 현재 단계에서는 T0를 수행했다고 가정하지 않는다. 제안서는 미래 T0의 진입 조건과 검증 방법만 설계한다.

## 4. 명시적 범위

### 4.1 반드시 설계할 것

- 전체 비전과 문제정의
- 사용자·AI·공동 전통의 관계
- AI 성장과 계승의 운영적 정의
- 개인 범용 전통과 프로젝트 전용 전통의 관계
- 사실·사건을 다음 작업의 실행 자산으로 바꾸는 정제 수명주기의 필요성, 비용, 대안
- 성공·실패·결정·실험·근접 실패·반례의 취급
- 기억 유형과 각 유형 사이의 관계
- 증거 수준, 적용 범위, 모순과 불확실성
- 교리·Skill을 채택할 경우 필요한 승격·강등·범위 축소·폐기 또는 이를 대체하는 더 단순한 통제
- 모델·도구 교체 시 이주와 재검증
- 사람 승인, 책임, 예외와 긴급 중단
- 비밀·개인정보·외부 입력·프롬프트 주입에 대한 기억 보안
- 검색·채택·적용·효과·유지와 음의 전이의 평가
- 월간 회고와 더 빠른 안전 루프, 개선 체계 자체의 메타 검토
- 외주·공모전 포트폴리오의 수익·학습·비용 관계
- 공동 브랜드가 실제 행동과 증거로 유지되는 방식
- 수작업 최소 단계와 검증 이후의 장기 방향
- 실패 모드, 중단·축소 조건, 미해결 질문

정제 수명주기가 원로그 검색이나 `incident + 체크리스트 + 골든 테스트` 최소안보다 낫다는 것은 미검증 가설이다. 설계자는 정제 수명주기를 채택하지 않을 수 있으며, 그 경우 비채택 근거와 원사건에서 실행 자산으로 이어지는 더 단순한 대안을 제시한다. 정제 구조를 채택하면 원로그 기반 축소판과 비교·철회할 경로를 함께 둔다.

### 4.2 설계자가 선택할 것

- 계층·객체·흐름을 설명하는 개념 모델
- 기억의 분류와 이름
- 교리·Skill·테스트의 관계
- 증거와 권고 강도를 표현하는 방식
- 프로젝트·범용 전통을 분리하거나 연결하는 방식
- A/B/C 활동과 즉시·월간·모델 이주 루프의 구체적 관계
- 승인 역할과 최소 분리 원칙
- 수작업 MVP의 범위와 장기 자동화 경계
- C 활동을 내부에서 수행할 범위와 외부 심사·공개 벤치마크·오픈소스 관행으로 외부화할 범위
- 최종 문서의 설명 순서와 시각화

### 4.3 이번 단계에서 하지 않을 것

- 실제 코드, CLI, 스키마 validator, RAG, 벡터 DB, 자동화 구현
- B1 코드, benchmark, 동결된 설계·연구 문서 변경
- incident 하네스의 스키마 또는 동작 변경
- 현재 로그 전체의 소급 변환
- 실제 모델 파인튜닝 또는 장기 메모리 서비스 도입
- 패키지 설치, 배포, 클라우드·데이터베이스 생성
- 실제 외주·공모전 참여 또는 외부 메시지·PR 작성
- 커밋·푸시
- 구현용 인수인계 문서나 인수인계 프롬프트 작성

데이터 구조는 개념적·논리적 수준까지 설계할 수 있지만 실행 가능한 전체 스키마나 코드를 만들지 않는다. 예시는 설계를 명확히 하는 최소량만 사용한다.

## 5. 설계의 핵심 긴장

설계는 다음 긴장을 한쪽 구호로 지우지 말고, 선택과 비용을 명시해야 한다.

| 긴장 | 피해야 할 단순화 |
|---|---|
| AI 성장 ↔ 인간 책임 | 인간 승인만 강조해 AI 계승을 없애거나, AI 성장을 이유로 책임 공백 만들기 |
| 원사건 보존 ↔ 비밀·망각 | 모든 것을 영구 저장하거나, 근거 없이 요약만 남기기 |
| 충실한 복제 ↔ 적응 | 과거 규칙의 기계적 복제 또는 모델별 변형으로 핵심 기능 소실 |
| 표준화 ↔ 다양성 | 하나의 범용 프롬프트 또는 무제한 에이전트 다양성 |
| 학습 ↔ 실제 납품 | 고객을 실험 대상으로 삼거나, 납품 때문에 학습 증거를 전혀 남기지 않기 |
| 엄밀성 ↔ 1인 운영비 | 거대한 거버넌스 또는 근거 없는 즉흥 운영 |
| 빠른 대응 ↔ 숙고 | 모든 것을 월간까지 기다리거나, 사건 직후 감정적으로 교리화 |
| 측정 ↔ 지표 게임 | 체감만 믿거나, 공개 고정 점수를 실제 가치로 대체 |
| 전통 유지 ↔ 폐기 | 역사라는 이유로 낡은 규칙 유지 또는 실패 이력 삭제 |
| 공동 브랜드 ↔ 신화화 | 행동 증거 없이 AI 인격이나 성공 이야기로 브랜드 구성 |

## 6. 필수 설계 질문

최종 제안은 최소 다음 질문에 명시적으로 답해야 한다.

### 6.1 목적과 경계

1. 이 체계의 사용자, 수혜자, 책임자는 누구인가?
2. 무엇을 성장으로 계산하고 무엇은 성장으로 계산하지 않는가?
3. 개인 기록, 조직 기억, AI 메모리, 브랜드의 경계는 무엇인가?
4. 사용자 가치와 AI 학습이 충돌할 때 어떤 원칙으로 선택하는가?

### 6.2 기억과 계승

5. 원사건, 해석, 교훈, 교리, Skill, 테스트, 브랜드 원칙은 어떻게 구분되는가?
6. 필요한 순간에 어떤 기억을 어떻게 선택하며, 검색 실패를 어떻게 드러내는가?
7. 원로그 RAG, 정제된 선례·Skill, 체크리스트·골든 테스트 최소안 중 무엇이 필요한가? 정제가 불필요한 조건은 무엇인가?
8. 새 모델은 무엇을 그대로 이어받고 무엇을 다시 시험해야 하는가?
9. 모델 중립 핵심과 모델·도구별 어댑터는 필요한가? 필요하다면 경계는 무엇인가?

### 6.3 증거와 교리

10. 사실, 추론, 제안, 사후 설명을 어떻게 분리하는가?
11. 증거 확실성과 행동 권고 강도를 어떻게 분리하는가?
12. 프로젝트 교리가 범용 교리로 승격되려면 어떤 전이 근거가 필요한가?
13. 서로 모순되는 성공 사례와 실패 사례를 어떻게 함께 유지하는가?
14. AI의 자기성찰이 잘못된 교훈을 만드는 것을 어떻게 막는가?
15. 잘못된 규칙을 어떤 신호와 권한으로 격리·강등·폐기하는가?

### 6.4 운영과 책임

16. 실제 프로젝트 중 언제 어떤 기록·판정이 일어나는가?
17. 보안·중대 품질 문제의 즉시 루프와 월간 회고는 어떻게 다른가?
18. 월간 표본이 부족할 때 억지 교훈 생성을 어떻게 막는가?
19. 한 사람이 여러 승인 역할과 C 활동을 맡을 때 무엇을 외부화하며, 최소한 어떤 독립성과 시간 분리를 유지하는가?
20. AI가 실질적으로 계승하면서도 사람 승인 절차가 형식적 도장이 되지 않게 하려면 무엇이 필요한가?

### 6.5 평가와 비용

21. 인간 단독·AI 단독·단일 AI 보조·오케스트레이션 중 무엇과 비교하는가?
22. 모델 향상, 사용자 숙련, 도구 변화와 전통의 한계효과를 어디까지 구분하며, 구분할 수 없을 때 인과 주장 강도를 어떻게 낮추는가?
23. near/far/migration transfer와 음의 전이를 어떻게 평가하는가?
24. 품질, 벽시계 시간, 인간 능동시간, 토큰·원화, 재작업, 중대 오류를 어떻게 함께 해석하는가?
25. 이 체계를 만들지 않거나 더 단순한 대조군에 머무는 편이 나은 조건과, 학습 가치가 운영비를 정당화하지 못한다는 신호는 무엇인가?

### 6.6 보안·비밀·브랜드

26. 외부 문서와 고객 자료가 장기 기억을 오염시키는 것을 어떻게 막는가?
27. 삭제·비밀 제거 요구가 생겼을 때 파생 기억과 Skill까지 어떻게 추적하는가?
28. 공동 브랜드의 약속을 어떤 관찰 가능한 행동과 결과로 증명하는가?
29. AI 기여와 인간 책임을 어떻게 투명하게 표현하는가?
30. 특정 모델이 사라져도 브랜드의 핵심이 남는가?

## 7. 필수 산출물 구조

제안서는 아래 문제 범위를 빠짐없이 다루되, 장 번호와 표현 방식은 바꿀 수 있다. 어떤 절의 구조가 불필요하다고 판단했다면 **비채택 근거와 더 단순한 대안**을 제시하는 것도 그 절을 다룬 것으로 인정한다.

### 7.1 설계 요약

- 설계를 한 문장으로 설명한다.
- 해결하려는 핵심 문제와 선택한 중심 원리를 밝힌다.
- 기존 초안과 가장 크게 달라지는 결정 5개 이내를 제시한다.
- 가장 큰 비용·위험·미확인 가정 3개 이상을 제시한다.

### 7.2 전제와 근거

- 확인된 사실
- 문헌에서 가져온 원리와 일반화 한계
- 현재 전통 연구와 원천 프로젝트에 적용한 설계 추론
- 아직 검증하지 못한 가정
- 설계가 틀렸음을 보여줄 반증 조건

각 핵심 결정은 가능한 한 `근거 → 판단 → 예상 이익 → 비용/위험 → 반증`의 연결을 보여야 한다.

### 7.3 개념 모델

- 체계의 경계와 외부 환경
- 사람, AI, 프로젝트, 기억, 교리, Skill, 테스트, 브랜드의 관계
- 사건에서 계승 가능한 능력으로 가는 전체 흐름
- 프로젝트 전통과 범용 전통의 관계
- 활성 기억과 역사·폐기 기억의 관계

관계를 설명하는 데 실제로 도움이 되는 작은 표·흐름도·상태도는 사용할 수 있다. 장식용 시각화는 사용하지 않는다.

### 7.4 정보와 수명주기

- 필요하다고 판단한 기억·지식 객체와 최소 의미, 또는 별도 객체가 불필요한 이유
- 각 객체의 출처·버전·적용 범위·반례·평가 연결
- 후보, 시험, 활성, 제한, 강등, 폐기, 대체 같은 상태가 필요하다면 그 최소 모델. 이 열거는 예시이며 같은 분류나 다단계 상태 모델을 채택할 의무가 없다.
- 모순·중복·낡음·음의 전이 처리
- 모델·도구·프로젝트 변화 시 파생 관계와 이주

완전한 실행 스키마 대신 설계 선택을 평가할 수 있는 논리 모델과 최소 예시를 제시한다.

### 7.5 운영 모델

- 실전 작업 전·중·후의 최소 활동
- 즉시 fast loop, 월간 또는 표본 기반 slow loop, 개선 체계 meta loop
- 사람과 AI의 역할·권한·승인·냉각 기간
- 성공·실패·결정·실험·근접 실패의 검토 방식
- 교리 없이 진행하거나 예외를 허용하는 방법
- 운영 부담을 줄이는 방법

### 7.6 검색·적용·실행 모델

- 어떤 상황에 어떤 기억이 제안되는가
- 검색된 내용을 명령이 아닌 증거로 다루는 방법
- 적용 여부와 변형을 기록하는 방법
- Skill의 모델 중립 핵심과 어댑터에 대한 선택
- 검색 실패, 오래된 기억, 잘못된 매칭, 컨텍스트 과부하 처리

### 7.7 평가와 실험

- 성장·계승·브랜드를 측정하는 지표 구조
- 기준선과 반사실 비교
- near/far/migration transfer 평가
- 평균 효과와 중대 오류·최악 사례의 균형
- 원로그 RAG, 정제 기억, 무기억 또는 체크리스트·골든 테스트 최소안의 필요한 비교
- 모델·사용자 숙련·도구 변화와 전통 효과를 가능한 범위에서 구분하는 방법. 분리가 불가능하면 인과 주장을 낮추는 규칙
- 사전 중단·축소·승격 조건

수치를 근거 없이 확정하지 않는다. 필요한 수치는 baseline을 얻은 뒤 정하도록 표시한다.

### 7.8 보안·개인정보·책임

- 신뢰 경계와 출처 계보
- 외부 입력 격리와 프롬프트 주입 방어
- 비밀·개인정보 제거와 제한 포인터
- 삭제·수정·철회가 파생 기억에 미치는 영향
- 사람 승인과 최소권한
- AI 기여와 인간 책임의 기록

### 7.9 최소 단계와 장기 방향

- 구현 없이도 검증 가능한 수작업 최소 운영
- 원천 프로젝트가 아직 구축·테스트 단계인 현재와, 실제 운영 자료로 T0를 시작할 미래 진입 조건의 구분
- 무엇이 입증돼야 다음 단계로 갈 수 있는가
- 어떤 마찰만 자동화할 것인가
- 장기적으로 가능한 검색·RAG·Skill·오케스트레이션 방향
- 확장하지 말아야 할 조건

최소 단계와 장기 비전을 섞어 처음부터 거대한 시스템을 정당화하지 않는다.

### 7.10 실패 모드와 이의

- 기술, 운영, 인지, 경제, 보안, 브랜드 실패 모드
- 설계 자체가 관료주의나 자기신화로 변하는 경로
- 헌장과 충돌하거나 수정이 필요하다고 보는 지점
- 채택하지 않은 주요 대안과 기각 이유
- 최종 판단자가 결정해야 할 열린 쟁점

## 8. 증거 작성 규칙

- 원자료·동료평가 문헌·공식 기관 자료를 우선한다.
- 조사 문서에 있는 인용을 재사용할 수 있지만 출처가 실제 주장과 맞는지 확인한다.
- 확인한 사실과 프로젝트 적용 추론을 문장 수준에서 구분한다.
- 인간 팀·군사·의료·문화 연구를 LLM의 직접 증거로 표현하지 않는다.
- 2026년 프리프린트는 동료평가 문헌과 구분하고 단독 핵심 근거로 삼지 않는다.
- 한 실험의 효과크기를 현재 프로젝트에 그대로 이전하지 않는다.
- 최신 모델·도구·가격·제품 동작을 주장하면 공식 최신 자료를 확인한다.
- 장기 인간–LLM 공동 성장의 직접 증거가 부족함을 숨기지 않는다.
- 출처 수보다 핵심 결정과 출처의 연결을 우선한다.

## 9. 설계 품질 규칙

- 모든 문제에 새 객체·역할·회의·자동화를 추가하지 않는다.
- 1인이 실제로 운영할 수 있는 최소 구조와 장기 구조를 분리한다.
- 하나의 범용 규칙보다 적용 조건과 예외를 표현한다.
- 사람 승인을 만능 안전장치로 사용하지 않는다. 사람이 무엇을 보고 어떻게 판단하는지 설계한다.
- AI를 단순 요약기로 축소하지 않는다. 기억 호출, 적용, 비평, 인계와 같은 AI 측 계승 능력을 설계한다.
- AI를 법적·도덕적 책임자로 가정하지 않는다.
- 문서량, 회고 횟수, Skill 수를 최종 성과로 삼지 않는다.
- 기존 incident 하네스는 좋은 사건 출처로 재사용하되 전체 전통으로 억지 확장하지 않는다.
- 선택하지 않은 대안과 손실되는 장점을 기록한다.
- 설계자가 선호하는 도구에 목적을 맞추지 않는다.

## 10. 독립성 규칙

- 설계안 A와 B는 작성 완료 전 서로의 본문·요약·중간 결론을 보지 않는다.
- 상대 설계를 추측하거나 미리 비평하는 데 시간을 쓰지 않는다.
- 기존 `system-design.md`는 볼 수 있지만 상대 제안은 볼 수 없다.
- 제안서는 별도 파일로 작성하며 기존 canonical 설계 문서를 수정하지 않는다.
- 공통 규격에서 모호한 부분은 합리적으로 가정하고 가정을 명시한다.
- 해결에 반드시 필요한 사용자 선택이 아니라면 질문을 기다리지 않고 완결된 안을 제시한다.
- 설계 중 발견한 추가 문헌은 사용할 수 있으나, 핵심 기준선 문서 자체를 수정하지 않는다.

## 11. 제안서 식별과 저장

최종 비교 전에는 모델·모드·작성자 이름보다 중립 식별자를 사용한다.

- 첫 번째 독립 결과: `docs/tradition/proposals/proposal-a.md`
- 두 번째 독립 결과: `docs/tradition/proposals/proposal-b.md`

각 파일에는 본문 앞에 다음 메타정보만 둔다.

```text
proposal_id: A 또는 B
brief_version: 1.0.0
baseline_version: 1.0.0
status: independent-draft
assessed_sources_until: YYYY-MM-DD
implementation: none
```

모델·모드 정보는 별도 비교 기록에서만 연결해, 최종 판단의 첫 단계가 이름에 끌리지 않게 한다. 두 제안은 커밋하거나 기존 문서를 덮어쓰지 않는다.

## 12. 최종 비교 평가표

두 설계자 모두 같은 평가표를 미리 안다. 점수는 길이나 기능 수가 아니라 선택의 품질을 비교하기 위한 보조수단이다. 객체·역할·상태·회의·자동화를 추가한 사실 자체에는 점수를 주지 않는다. 불필요한 구조를 근거 있게 삭제하거나 채택하지 않은 결정은 같은 문제를 더 복잡하게 처리한 안과 동등하게 만점을 받을 수 있다. 근거 없이 추가한 메커니즘은 관련 영역의 감점 사유다.

| 평가 영역 | 배점 | 핵심 질문 |
|---|---:|---|
| 목적·철학·공동 브랜드 정합성 | 15 | AI 계승과 증거로 드러나는 공동 브랜드라는 핵심 목적을 왜곡하지 않는가? |
| 계승·전이 설계 | 15 | 다른 세션·프로젝트·모델에서 무엇이 어떻게 이어지는가? |
| 증거·반증 가능성 | 15 | 사실과 추론을 구분하고 설계 실패를 판정할 수 있는가? |
| 1인 운영 가능성 | 15 | 최소 단계가 단순하고, 제거한 구조의 근거가 분명하며, 지속 비용을 감당할 수 있는가? |
| 수명주기·거버넌스 | 10 | 승격뿐 아니라 모순·강등·폐기를 실제로 처리하는가? |
| 보안·비밀·책임 | 10 | 영속 기억의 오염과 책임 공백을 막는가? |
| 평가·경제성 | 10 | 품질·시간·비용·위험·학습가치를 함께 다루는가? |
| 장기 적응성 | 5 | 모델·도구 변화와 자동화 확장을 견디는가? |
| 명료성·삭제·결정 추적 | 5 | 핵심 선택과 비채택·삭제 결정, 대안, 비용, 열린 쟁점이 분명한가? |
| 합계 | 100 |  |

### 12.1 치명적 결격 조건

총점과 무관하게 다음 중 하나가 있으면 해당 부분은 채택하지 않는다.

- 사용자·고객의 안전·비밀·명시적 의무보다 내부 학습을 우선한다.
- 모델 가중치가 자동 학습된다고 전제하거나 AI 인격 연속성을 사실로 주장한다.
- 사람 또는 AI의 자기평가만으로 교리를 자동 승격한다.
- 잘못된 교리를 격리·폐기할 경로가 없다.
- 분리가 불가능한 조건임을 인정하지 않은 채 전통·모델·사용자 숙련 중 하나의 인과 효과로 단정한다.
- 모든 원자료를 무기한 저장하도록 요구한다.
- 구현부터 시작하거나 기존 B1·benchmark·동결 문서를 변경한다.
- 1인이 운영할 수 없는 복잡성을 최소 단계의 필수조건으로 둔다.

### 12.2 점수 밖 최종 판단

최종 판단자는 다음을 별도로 기록한다.

- A에서만 발견된 중요한 문제와 해법
- B에서만 발견된 중요한 문제와 해법
- 두 안이 같은 근거 없이 합의한 위험한 가정
- 서로 충돌하지만 실험 전에는 결정할 수 없는 쟁점
- 채택, 수정 채택, 보류 실험, 기각 항목
- 통합으로 새로 생긴 복잡성과 모순

## 13. 완료 조건

한 독립 설계는 다음을 모두 만족할 때 완료다.

- 필수 설계 질문과 산출물 범위를 답하거나, 해당 구조를 비채택한 근거와 더 단순한 대안을 제시한다.
- 헌장에 대한 준수 또는 이의를 명시한다.
- 핵심 결정마다 근거·비용·위험·반증 조건이 연결된다.
- 최소 운영과 장기 방향이 분리된다.
- 구현 파일을 만들거나 canonical 설계를 수정하지 않는다.
- 확인 범위와 미확인 범위를 정직하게 구분한다.
- 최종 판단자가 다른 제안과 항목별 비교할 수 있는 단일 Markdown 제안서가 있다.

완료 기준은 “완벽한 미래 시스템”이 아니라, **두 개의 일관된 설계 철학을 공정하게 비교하고 최종 v2의 선택을 근거 있게 만들 수 있는가**다.
