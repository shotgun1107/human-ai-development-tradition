# 독립 설계 경쟁 입력 기준선 v1.1

> 기준선 버전: 1.1.0  
> 동결일: 2026-08-05  
> 상태: 설계안 A/B 착수 전 공통 입력으로 동결  
> 이전 판본: `design-competition-baseline-v1.md` v1.0.0  
> 해시: SHA-256, UTF-8 원본 파일 기준

## 0. v1.1 변경 이유

v1.0.0 동결 뒤 독립 Claude 심사와 Codex 판정, 사용자의 프로젝트 상태 정정을 받았다. A/B는 아직 시작되지 않았으므로 같은 수정판을 두 설계에 제공할 수 있다. v1.1은 핵심 철학을 바꾸지 않고 다음 문제만 교정한다.

- 원천 오케스트레이터가 아직 구축·테스트 단계이며 실제 운영 체계가 아니라는 경계
- 개발 incident를 전통 운영 효과의 증거로 오인할 위험
- METR 2026년 자료의 편향 방향과 연구진의 가속 판단 누락
- Engelbart C 활동의 비용·공동화 논거와 독자 시작 허용의 동시 반영
- Cochrane 전체 292개 연구와 6.2%p 추정에 사용된 177개 연구의 구분
- 외부 기억 세분화가 어려운 사례의 음의 전이와 망각을 늘릴 수 있다는 누락 결과
- 고객 납품 과제의 무단 조건 배정 금지
- 모델 향상·사용자 숙련·도구 변화와 전통 효과를 완전히 분리할 수 없을 때 주장 강도를 낮추는 규칙
- 정제 수명주기와 다단계 상태 모델을 정답으로 강제하던 설계 규격의 편향
- 최소안, 비채택, 삭제, C 활동 외부화가 정당한 설계 선택으로 평가받는 경로
- T0 즉시 수행이 아니라 운영 준비 조건 충족 뒤 수행한다는 단계 경계

Claude 심사의 점수와 해법 자체는 공통 입력이 아니다. 수용된 사실·전제 교정만 중립적인 문구로 반영했다.

## 1. 동결 목적

설계안 A와 B가 서로 다른 자료 판본을 보고 생긴 차이를 설계 철학의 차이로 오인하지 않도록 공통 입력을 고정한다. 두 설계자는 아래 파일의 정확한 판본과 `design-competition-brief.md`의 동일 과업 규격을 사용한다.

동결은 정제 수명주기, 교리 계층, 데이터 객체 또는 기존 초안을 정답으로 만든다는 뜻이 아니다. 두 독립 제안의 작성과 첫 비교가 끝날 때까지만 동일한 출발점을 보장한다. 문제를 발견한 설계자는 기준선 파일을 수정하지 않고 자신의 제안서에 이의·대안·근거를 기록한다.

## 4. 현재 단계에 대한 공통 사실

- 이 전통 연구는 원천 오케스트레이터와 분리된 독립 프로젝트다.
- 원천 오케스트레이터는 아직 구축·테스트 단계이며 실제 운영 체계가 아니다.
- B1 순차 실행 구성요소와 실제 smoke가 완료됐지만 전체 오케스트레이터의 효율·안정성·장기 이득은 입증되지 않았다.
- B0/B1 반복 비교는 아직 완료되지 않았다.
- 현재 incident는 개발·테스트 기록이며 전통 운영 효과의 증거가 아니다.
- 현재 단계는 구현이나 T0가 아니라 두 독립 기획·시스템 설계의 비교다.
- T0는 반복 가능한 실제 작업, 개입 전 기준선, 안전한 내부 trial, 사용자 승인 조건이 준비된 뒤 수행한다.

설계자는 존재하지 않는 운영 결과, T0 결과, 비용 절감, 전이 효과를 가정하거나 만들어내지 않는다.

## 5. 기준선에서 제외한 것

다음은 공통 설계 판단의 입력 판본으로 고정하지 않았다.

- `README.md`: 문서 탐색용이며 새 파일 링크에 따라 바뀔 수 있다.
- `mkdocs.yml`, 렌더링 환경: 가독성 도구이며 설계 내용의 근거가 아니다.
- `docs/prompts/tradition/`: 외부 심사 실행용 지시이며 설계 근거가 아니다.
- `docs/reviews/tradition/`: Claude 심사와 Codex 판정은 최종 판단자가 사용할 감사 자료다. 설계자에게 공통 해법 프레임을 주지 않기 위해 입력에서 제외한다.
- 원천 오케스트레이터의 B1 코드와 benchmark: 이번 설계 경쟁은 구현·성능 판정을 수행하지 않는다.
- 원천 오케스트레이터의 전체 revision log와 incident 원문: 현재는 개발·테스트 자료이며 운영 효과 증거가 아니다. 비밀·관련성·입력 불균형도 피한다.
- 설계안 A/B: 독립성이 깨지므로 상대 결과는 입력에 포함하지 않는다.

추가 자료가 반드시 필요하다고 판단한 설계자는 독립적으로 조사할 수 있다. 그 자료는 `추가 확인 자료`로 명시하며 공통 기준선의 일부인 것처럼 표현하지 않는다.

## 6. 해시 확인 방법

PowerShell에서 다음 형식으로 원본 일치 여부를 확인할 수 있다.

```powershell
Get-FileHash -Algorithm SHA256 docs\tradition\purpose-and-philosophy.md
Get-FileHash -Algorithm SHA256 docs\tradition\design-competition-brief.md
```

홈페이지 등 다른 환경에 파일을 업로드하거나 복사한 뒤에는 파일명이 아니라 내용과 해시를 기준으로 동일 판본인지 확인한다. 플랫폼이 줄바꿈이나 인코딩을 바꾸면 해시가 달라질 수 있으므로, 그 경우 원본 파일 자체를 다시 제공한다.

이 기준선 manifest 자체의 해시는 같은 디렉터리의 `design-competition-baseline-v1.1.sha256`에 별도로 기록한다. 자기 자신의 해시를 본문에 넣지 않는다.

## 7. 변경 규칙

- A/B 착수 전 외부 심사와 사용자 정정은 모든 입력 해시를 다시 계산한 같은 새 기준선으로 반영할 수 있다.
- A/B 중 하나라도 작성 중이면 기준선 파일을 수정하지 않는다.
- 치명적인 사실 오류·비밀 노출이 발견되면 두 작업을 모두 중단하고 같은 새 기준선으로 다시 시작한다.
- 단순 오탈자라도 한쪽에만 수정판을 제공하지 않는다.
- 기준선 변경 시 버전을 올리고 모든 해시와 별도 manifest 해시를 다시 계산한다.
- 새 기준선으로 재시작하지 않는다면 변경 사항은 최종 비교 단계의 `사후 발견`으로만 다룬다.
- 최종 합성 문서는 이 기준선의 일부가 아니다.

## 8. 기준선 완료 판정

다음 조건을 만족하므로 v1.1.0 입력 기준선으로 사용할 수 있다.

- 사용자 검토를 마친 목적·철학 헌장 v1.1이 있다.
- 원천 프로젝트의 구축·테스트 상태와 전통 운영 증거의 부재가 명시돼 있다.
- 1·2차 연구의 확인 사실과 설계 가설이 분리돼 있다.
- 공통 과업이 정제 수명주기·다단계 상태·기능 수를 정답으로 강제하지 않는다.
- 최소안·비채택·삭제가 평가에서 불리하지 않다.
- 고객 납품 과제를 열등할 수 있는 실험 조건에 배정하지 않는 경계가 있다.
- 분리할 수 없는 인과 효과를 정직하게 낮춰 말하는 경로가 있다.
- 모든 내용 입력의 해시가 기록돼 있다.
- 두 설계가 서로를 보지 않는 독립성 규칙이 있다.
- 구현, T0 수행, 원천 코드 변경을 요구하지 않는다.

이 기준선은 설계의 정답을 동결하는 것이 아니라 **두 설계가 같은 사실·제약·미확인 상태에서 출발했다는 사실**을 동결한다.
