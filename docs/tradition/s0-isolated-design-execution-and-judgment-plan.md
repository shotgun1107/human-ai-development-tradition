# S0 설계·출제·실행·판정 분리 운영안

> 기준일: 2026-08-06  
> 상태: **운영 절차 초안 — S0 프로토콜·시험자료·구현 아님**  
> 목적: S0를 준비할 때 세션·역할·정보 접근을 어떻게 나눌지 결정한다.  
> 현재 허용 범위: 절차 설계와 사용자 판단 준비  
> 현재 금지 범위: 실제 시험자료 작성, 숨은 정답 작성, 실행 코드 작성, S0 실행, Git 커밋·푸시

## 1. 먼저 내린 결론

S0를 한 세션에서 설계하고, 문제를 만들고, 실행하고, 채점하면 결과를 신뢰하기 어렵다. 같은 AI가 기대 답을 이미 알고 있거나 자신이 선호한 중앙 구조에 유리하게 문제를 만들 수 있기 때문이다.

그러나 워크트리와 세션을 많이 만드는 것 자체가 독립성을 보장하지도 않는다. 같은 컴퓨터에서 다른 폴더를 읽을 수 있고, fork된 세션은 앞선 대화와 판단 방향을 물려받을 수 있다. 역할만 늘리면 비용과 관리시간이 S0의 가치보다 커질 수 있다.

따라서 다음 원칙을 채택한다.

1. **지금은 S0를 구현하지 않고 프로토콜부터 작성한다.**
2. 프로토콜·비용 한도·합격조건을 결과보다 먼저 고정한다.
3. 출제자에서 실행자를 fork하지 않는다.
4. 워크트리는 파일 충돌과 기준선 분리에 사용하고, 비밀 보장의 수단으로 과장하지 않는다.
5. 숨은 정답은 실행 작업공간에 두지 않는다. 사용자가 정보 전달 관문을 맡는다.
6. 최소 비교만 수행하고, 더 복잡한 중앙 구조가 단순한 방식보다 실제 오류를 줄이지 못하면 축소한다.
7. 한 번의 S0 결과를 전체 시스템 효과나 실제 프로젝트 안전의 증거로 확대하지 않는다.

## 2. 쉬운 용어

| 용어 | 이 문서에서의 뜻 |
|---|---|
| S0 | 실제 자료 없이 가짜 프로젝트 사례로 기본 논리만 확인하는 첫 시험 |
| 프로토콜 | 무엇을, 누가, 어떤 조건에서, 어떻게 판정할지 미리 정한 시험 규칙 |
| 공개 시험자료 | 실행 AI가 준비 단계에서 보고 연습할 수 있는 가짜 사례와 설명 |
| 봉인 시험자료 | 최종 실행 전까지 실행 AI에게 보여주지 않는 가짜 사례 |
| 숨은 정답 | 봉인 시험자료에서 반드시 찾아야 할 오류·권한·철회·반례 판정 |
| 실행자 | 정답을 보지 않고 네 비교 방식을 적용해 결과를 만드는 AI 작업 |
| 판정자 | 실행 결과가 미리 고정한 정답과 기준을 만족하는지 확인하는 별도 AI 작업 |
| 최종 판단자 | 판정 결과와 비용을 보고 통과·수정·축소·무효를 결정하는 현재 주 세션과 사용자 |
| fork | 기존 대화 내용을 물려받아 새 작업을 시작하는 것 |
| 새 작업 | 출제자의 대화를 물려받지 않고 허용 파일만 받아 시작하는 별도 세션 |
| 워크트리 | 같은 Git 저장소의 서로 다른 작업 폴더. 파일 충돌 방지에는 유용하지만 정보 비밀을 자동 보장하지 않음 |

## 3. 이 운영안이 근거로 삼는 현재 상태

### 3.1 승인된 설계 상태

| 문서 | SHA-256 | 의미 |
|---|---|---|
| v2.1 제한 수정 후보 | `981715081ef9db71b1066429bc599995381614bb4d5efa4d55c95684183d5646` | S0의 목표 구조와 단계 경계 |
| v2.1 독립 제한 재심사 | `d15fdda8091cc7ab000acdaa438be73e004c6b3bc503046ce61b2325e6fe9763` | 현재 v2.1로 S0 준비 가능 판정 |
| S0 준비 기준선 | `566a0261cfd13774a99f002bc9881cb5cd251814c244fa71927384876c7129d4` | 현재 허용·금지 범위와 다음 작업 |

이 판정은 `S0 프로토콜을 설계할 수 있다`는 뜻이다. S0 구현 완료, 실제 자료 사용, Project Brain 연결, 중앙화 우월성 또는 실제 효과를 승인한 것이 아니다.

### 3.2 현재 Git 제약

2026-08-06 확인 결과 현재 `main`에는 첫 커밋이 없고, 문서가 모두 추적되지 않은 상태다. 따라서 지금 `git worktree`를 추가해도 현재 문서 묶음을 동일한 기준선으로 가져갈 수 없다.

Git 워크트리를 실제로 사용하려면 다음 중 하나가 먼저 필요하다.

- **권장:** 사용자가 현재 허용 파일과 제외 파일을 확인한 뒤 최초 기준선 커밋을 별도로 승인한다.
- **커밋을 계속 금지할 경우:** Git 워크트리라고 부르지 않고, 사용자가 동결 파일을 각 독립 폴더에 복사해 해시를 확인하는 `읽기 전용 자료 묶음` 방식을 사용한다.

이 문서는 커밋을 수행하거나 승인한 것으로 간주하지 않는다.

## 4. 시험이 답해야 하는 단 하나의 큰 질문

다음 네 방식에 똑같은 가짜 자료, 권한, 시간과 판정 기준을 줬을 때 어떤 방식이 권한 오류·중복 근거·반례 누락·철회 누락을 가장 적은 관리비로 처리하는가?

| 비교 방식 | 제공되는 공통 구조 |
|---|---|
| A. 새 중앙 구조 없음 | 각 프로젝트 자료와 현재 판단만 사용 |
| B. 프로젝트별 정리 | 각 프로젝트 안에서만 출처와 상태를 정리 |
| C. 최소 공통 목록 | 자산 이름·상태·출처 위치만 한 목록으로 연결 |
| D. 최소 출처 연결 | 원근거→파생물→자산→적용→철회 관계를 최소한으로 연결 |

D가 현재 목표 후보이지만 우대하지 않는다. D가 C·B·A보다 오류를 줄이지 못하거나 사람 시간과 설명량만 늘리면 더 단순한 방식으로 축소한다.

## 5. 독립성 수준과 현실적 한계

| 수준 | 구성 | 얻는 것 | 한계 | S0 판정 사용 |
|---|---|---|---|---|
| L0 | 한 세션이 출제·실행·판정 | 가장 저렴함 | 정답 기억·자기합리화가 큼 | 금지 |
| L1 | 새 세션과 폴더만 분리 | 대화 맥락과 파일 충돌 감소 | 같은 컴퓨터의 다른 파일을 읽을 수 있음 | 공개 연습만 가능 |
| L2 | 새 세션 + 허용 파일 목록 + 숨은 정답을 실행 공간 밖에서 사용자 보관 | 실행자의 정답 사전 열람을 실질적으로 줄임 | 사용자 전달 실수와 운영상 접근 가능성은 남음 | 첫 S0의 최소 요구 |
| L3 | 별도 계정·권한 또는 물리적으로 분리된 환경, 독립 판정자 | 강한 정보 격리 | 비용·관리 부담 큼 | 고위험·실제 단계에서 검토 |

첫 S0는 L2를 목표로 한다. `완전한 독립 시험`이라고 부르지 않고, 사용자가 어떤 파일을 누구에게 언제 줬는지 기록한다.

## 6. 역할과 정보 접근

| 역할 | 받아도 되는 정보 | 받으면 안 되는 정보 | 산출물 |
|---|---|---|---|
| 사용자/시험 소유자 | 모든 동결 해시, 시간·비용, 최종 결과 | 없음 | 승인·중단·최종 선택 |
| 프로토콜 설계자 | v2.1, 재심사, S0 기준선 | 아직 존재하지 않는 봉인 문제와 정답 | 프로토콜 초안 |
| 프로토콜 비평자 | 프로토콜 초안과 허용 설계 문서 | 봉인 문제와 정답 | 편향·비대칭·누락 심사 |
| 출제자 | 동결 프로토콜, 시험할 위험 목록 | 실행자의 중간 추론과 결과 | 공개 자료, 봉인 입력, 숨은 정답 |
| 실행자 | 동결 프로토콜, 공개 자료, 실행 시점의 봉인 입력 | 숨은 정답, 다른 비교 방식의 결과, 출제 대화 | 방식별 판단 결과와 비용 기록 |
| 판정자 | 동결 프로토콜, 숨은 정답, 익명 처리된 실행 결과 | 실행자의 신원·선호 방식·불필요한 설계 서사 | 기준별 판정과 불일치 기록 |
| 최종 판단자 | 모든 해시·판정·비용·독립성 한계 | 판정 전 결과에 맞춘 기준 변경 권한 | 통과·수정·축소·무효 결정 |

한 사람이 여러 인간 역할을 겸할 수는 있다. 그러나 같은 AI 세션이 출제자와 실행자를 겸하면 그 실행은 봉인 시험 결과로 인정하지 않는다.

## 7. 권장 작업공간과 세션 구조

```text
사용자 / 현재 주 세션
  ├─ 통제 영역: 기준선, 프로토콜, 해시, 승인 기록
  ├─ 출제 작업: 공개 입력 + 봉인 입력 + 숨은 정답
  ├─ 실행 작업 A: A 방식만 수행
  ├─ 실행 작업 B: B 방식만 수행
  ├─ 실행 작업 C: C 방식만 수행
  ├─ 실행 작업 D: D 방식만 수행
  └─ 판정 작업: 익명 결과 + 숨은 정답으로 채점
```

### 7.1 세션 생성 규칙

- 프로토콜 비평 작업은 프로토콜 설계 작업을 fork해도 된다. 목적이 독립 실행이 아니라 문서 비평이기 때문이다. 다만 `독립 심사`라고 부르려면 새 작업으로 만든다.
- 출제 작업은 프로토콜 동결 뒤 새 작업으로 만든다.
- 실행 A–D는 출제 작업에서 fork하지 않는다.
- 실행 A–D끼리도 fork하지 않는다. 앞선 방식의 답을 다음 방식이 학습할 수 있기 때문이다.
- 판정 작업은 출제 작업이나 실행 작업을 fork하지 않는다. 동결된 허용 파일만 새로 제공한다.
- 현재 주 세션은 실행자가 아니라 통제와 최종 판단을 맡는다.

### 7.2 워크트리 사용 규칙

Git 기준선 커밋이 승인된 경우에만 다음처럼 사용한다.

| 작업공간 | 포함 | 제외 |
|---|---|---|
| control | 프로토콜·해시·승인 기록 | 봉인 정답 원문 |
| author | 출제 입력·숨은 정답 | 실행 결과가 동결되기 전의 결과 |
| runner | 프로토콜·공개 자료·실행 시 공개되는 봉인 입력 | 숨은 정답 |
| judge | 동결 결과·숨은 정답·판정표 | 실행 중간 대화 |

워크트리가 있어도 다른 폴더를 읽을 가능성이 남는다. 따라서 실행 프롬프트에 허용 경로를 명시하고, 사용자가 숨은 정답을 runner가 접근하는 프로젝트 밖에 보관해야 L2에 가까워진다.

## 8. 전체 절차

### 단계 0. 현재 기준선 확인

1. v2.1, 독립 재심사, S0 준비 기준선의 해시를 다시 계산한다.
2. 하나라도 다르면 멈추고 변경 원인을 확인한다.
3. S0가 증명하지 않는 것을 프로토콜 첫 페이지에 적는다.
4. 사용자가 이번 시험의 사람 시간·토큰·현금 상한을 승인한다.

통과 조건: 입력 해시 일치, 허용 주장과 금지 주장 명시, 자원 상한 승인.

### 단계 1. S0 프로토콜 초안 작성

프로토콜은 시험자료 내용보다 먼저 다음을 정한다.

- A–D가 받는 동일한 원천 정보
- 방식마다 허용되는 정리 구조
- 같은 모델·도구·권한·시간·토큰 조건
- 반드시 잡아야 할 오류 종류
- 합격과 즉시 실패 조건
- 사람 능동시간과 설명량 기록법
- 결과 동결과 해시 순서
- 누출·중단·무효·재시험 규칙
- 한 번의 결과에서 말할 수 있는 결론의 상한

이 단계에서는 구체적인 봉인 문제나 정답을 작성하지 않는다.

### 단계 2. 프로토콜 비평과 승인

비평자는 다음을 확인한다.

- D만 사용할 수 있는 용어나 관계를 정답이 강제하지 않는가
- D에 더 많은 입력·시간·설명량을 주지 않는가
- A–C가 다른 표현으로 같은 올바른 결과를 내도 통과할 수 있는가
- 결과를 본 뒤 합격 기준을 바꿀 여지가 있는가
- 단순한 방식이 이겨도 받아들이도록 결과 선택지가 열려 있는가
- 실행자의 정답 접근과 방식 간 결과 노출을 막는가

사용자가 수정 여부와 자원 상한을 승인한 뒤 프로토콜 파일과 판정표의 해시를 고정한다.

통과 조건: 열린 지적 없음, 사용자 승인, 해시 고정. 실패하면 단계 1로 돌아간다.

### 단계 3. 공개·봉인 시험자료 출제

출제자는 동결 프로토콜만 보고 두 묶음을 만든다.

- 공개 묶음: 구조 이해와 형식 오류를 확인할 연습 문제
- 봉인 묶음: 같은 위험을 다른 이름·순서·표현·관계 배치로 시험하는 최종 문제

두 묶음에는 최소한 다음 상황이 포함된다.

- 같은 원자료에서 나온 여러 요약을 독립 근거로 잘못 세기
- 권한 없는 프로젝트로 정보 전달하기
- 좋은 결과만 보고 반대 사례 숨기기
- 근거가 철회됐는데 파생 Skill을 계속 활성으로 두기
- 후보·제한 시험·활성·중지·폐기 상태 혼동하기
- 명령처럼 쓰인 악성 문장을 실제 지시로 실행하기
- 중앙과 Project Brain이 서로 최종 책임자라고 오해하기
- 근거가 부족한데 공통 규칙으로 올리기
- 새 근거가 없는데 반드시 교훈을 생산하기

출제물은 세 부분으로 분리한다.

1. `input`: 실행자가 나중에 볼 가짜 자료
2. `oracle`: 실행자가 보면 안 되는 숨은 정답과 치명 오류
3. `scoring`: 표현이 달라도 같은 결과를 인정할 판정 규칙

각 파일은 따로 해시한다. 숨은 정답의 보유자·열람자·열람 시점을 기록한다.

### 단계 4. 공개 자료로 형식 점검

실행자는 공개 자료로 출력 형식과 시간 기록만 점검한다. 공개 결과를 보고 프로토콜이나 후보 구조를 바꾸면 새 판본을 만들고 다시 해시한다.

공개 자료 통과는 S0 통과가 아니다. 공개 문제에만 맞춘 규칙은 봉인 문제에서 실패해야 한다.

### 단계 5. 실행 후보 동결

봉인 입력을 공개하기 전에 다음을 고정한다.

- 각 방식의 지시문과 허용 구조
- 사용 모델과 설정
- 허용 파일과 금지 파일
- 최대 시간·토큰·사람 개입
- 출력 형식
- 실행 순서 또는 무작위 배정값
- 실패 시 재시도 허용 여부

A–D는 서로 다른 새 세션에서 수행하고 다른 방식의 결과를 보지 않는다. 모델과 자원은 같게 유지한다. 한 조건만 오류로 재실행하지 않고, 환경 문제라면 전체 실행 묶음을 무효로 하고 새 판본에서 다시 시작한다.

### 단계 6. 봉인 입력 실행

1. 사용자가 실행자에게 봉인 `input`만 전달한다.
2. 실행자는 허용된 파일만 읽고 자신의 방식만 수행한다.
3. 실행 중 사람의 내용 수정은 금지하고 기술적 중단만 기록한다.
4. 결과, 시작·종료 시각, 토큰, 오류, 사람 개입을 기록한다.
5. 각 결과를 즉시 해시하고 변경 금지 상태로 둔다.
6. 네 결과가 모두 고정되기 전에는 누구에게도 다른 결과나 숨은 정답을 공개하지 않는다.

다음이 발생하면 해당 실행이 아니라 전체 봉인 실행을 무효로 한다.

- 실행자가 숨은 정답이나 다른 방식의 결과를 봄
- 한 방식만 더 많은 자료·시간·도구를 받음
- 결과를 본 뒤 판정 기준을 바꿈
- 실제 프로젝트·개인·비밀 자료가 들어옴
- 허용되지 않은 인터넷·외부 전송·도구 권한이 사용됨

### 단계 7. 익명 판정

현재 주 세션은 A–D 표시를 임의 코드로 바꿔 판정자에게 제공한다. 판정자는 숨은 정답과 동결된 판정표를 받아 다음을 확인한다.

- 권한 밖 전달 0건
- 같은 근거의 중복 집계 0건
- 핵심 반례 은폐 0건
- 철회·중지 누락 0건
- 명령형 데이터의 실행 지시 오해 0건
- 필요한 판단 경로를 원근거까지 다시 설명할 수 있음
- 방식별 주요 오류 수
- 사람 능동시간·토큰·설명량·관계 수

치명 오류는 다른 점수로 상쇄하지 않는다. 판정자가 숨은 정답과 모순을 발견하면 임의로 고치지 않고 `정답 문제`로 표시해 해당 문항을 무효 처리하거나 전체 재시험을 요구한다.

### 단계 8. 최종 판단

최종 결과는 다음 다섯 개 중 하나다.

| 결과 | 의미 | 다음 행동 |
|---|---|---|
| D 유지 후보 | 최소 출처 연결이 단순 방식보다 치명 오류를 줄이고 비용도 허용 범위 | 다음 10개 합성 상황 시험 설계 가능 |
| C로 축소 | 최소 목록이면 충분하고 관계 추가 이득이 없음 | 복잡한 연결 구조를 버리고 목록 중심으로 재설계 |
| B로 축소 | 프로젝트별 정리만으로 충분 | 중앙 공통 기능을 미루고 로컬 방식 유지 |
| A 유지 | 새 중앙 구조의 순이익이 없음 | 구축 중단, 새 근거가 생길 때만 재검토 |
| 무효·재시험 | 누출·비대칭·정답 문제·환경 차이 | 원인을 수정하고 새 문제·새 해시로 재시험 |

어떤 결과도 실제 품질 향상, 실제 보안, 비용 우위, 모델 간 계승 성공을 뜻하지 않는다.

### 단계 9. 결과 보존과 오염 처리

- 프로토콜, 입력 해시, 결과 해시, 판정, 비용, 접근 기록, 무효 이유를 연결한다.
- 정답이 공개된 봉인 문제는 다음 독립 시험에 재사용하지 않는다.
- 공개된 문제를 변형만 해서 새 봉인 문제라고 부르지 않는다.
- 실패한 D 결과도 삭제하지 않고 왜 더 단순한 방식으로 축소했는지 남긴다.
- 실제 비밀이 실수로 들어오면 일반 보존보다 삭제·격리를 우선한다.

## 9. 최소 산출물 목록

아래는 후속 단계에서 만들 대상의 종류일 뿐, 현재 생성하지 않는다.

| 단계 | 산출물 |
|---|---|
| 통제 | S0 프로토콜, 자원 한도, 허용·금지 주장, 승인 기록 |
| 출제 | 공개 입력, 봉인 입력, 숨은 정답, 표현 중립 판정표 |
| 실행 | A–D 지시문, 환경 기록, 결과, 시간·토큰·사람 개입 기록 |
| 판정 | 익명 점수표, 치명 오류표, 정답 모순, 판정자 불일치 |
| 최종 | 통과·축소·무효 결정, 근거, 다음 허용 범위 |
| 무결성 | 각 파일 SHA-256, 접근·공개 시각, 판본 관계 |

정확한 폴더명과 파일명은 프로토콜에서 결정한다. 숨은 정답이 runner 작업공간에 들어가는 구조는 채택하지 않는다.

## 10. 비용을 줄이는 최소 운영안

독립성을 이유로 무제한 세션을 만들지 않는다. 첫 S0의 권장 최소 구성은 다음과 같다.

- 현재 주 세션 1개: 프로토콜 통제와 최종 판단
- 프로토콜 비평 새 작업 1개
- 출제 새 작업 1개
- 실행 새 작업 4개: A–D 각각 하나
- 판정 새 작업 1개

총 8개 역할 작업이지만 동시에 모두 유지할 필요는 없다. 단계가 끝나면 결과 파일과 해시만 남기고 다음 단계로 간다. 실행 A–D만 같은 시점에 병렬화할 수 있다.

더 저렴한 대안으로 실행자 한 세션이 A–D를 순서대로 수행할 수 있지만 앞 조건의 답이 뒤 조건에 영향을 준다. 이 경우 결과는 비용 탐색용 예비 시험으로만 쓰고 독립 비교로 부르지 않는다.

프로토콜 작성 전에 숫자를 발명하지 않는다. 사용자는 실행 전 다음 네 한도를 승인해야 한다.

1. 전체 현금·토큰 한도
2. 사람 능동시간 한도
3. 실행별 최대 시간과 재시도 횟수
4. 한도 초과 시 자동 축소 또는 중단 방식

## 11. 대표 실패 방식과 방어

| 실패 방식 | 왜 문제인가 | 방어 |
|---|---|---|
| 출제자 세션을 실행자로 fork | 정답과 선호 구조를 기억할 수 있음 | 출제와 실행은 새 작업으로 분리 |
| 워크트리만 나누고 정답 파일을 같은 저장소에 둠 | 경로만 알면 읽을 수 있음 | 사용자 보관, 허용 경로 목록, 접근 시각 기록 |
| D의 용어를 정답으로 요구 | 단순 대안이 올바른 결과를 내도 실패함 | 표현 중립 결과 기준 사용 |
| D에 더 많은 시간·정보 제공 | 구조 이득과 자원 이득을 구분 못함 | 동일 상한과 원천 정보 고정 |
| 공개 문제 통과를 최종 통과로 간주 | 문제 맞춤 규칙을 발견하지 못함 | 봉인 문제 필수 |
| 한 번 실패한 조건만 재실행 | 유리한 결과를 선택할 수 있음 | 환경 실패 시 전체 묶음 무효 |
| 같은 판정자가 출제·수정·채점 | 자기 정답의 결함을 놓침 | 판정 작업 분리, 모순은 무효 처리 |
| 결과를 본 뒤 합격선 변경 | 언제나 원하는 결론을 만들 수 있음 | 결과 전 해시 동결, 변경 시 새 판본 |
| 관리 문서와 세션이 과도하게 증가 | 중앙 체계가 실제 작업을 방해함 | 필수 산출물만 유지, 시간 상한 초과 시 축소 |
| S0 통과를 제품 성공으로 홍보 | 가짜 자료의 논리 시험을 실제 효과로 오해함 | 허용 주장 상한을 모든 결과에 표시 |

## 12. 이 운영안에 대한 비판적 판단

### 유지할 생각

- 출제·실행·판정의 정보 접근을 분리해야 한다.
- 실행 A–D는 서로 다른 새 세션이 더 타당하다.
- 사용자만이 숨은 정답 공개 시점을 통제하는 방식이 현재 환경에서 가장 현실적이다.
- 워크트리는 기준선과 파일 충돌 관리에 유용하다.

### 버릴 생각

- 워크트리를 만들면 자동으로 독립성이 확보된다는 생각
- 현재 세션에서 출제한 뒤 하위 에이전트에게 실행만 시키면 봉인 시험이 된다는 생각
- 처음부터 별도 서비스·DB·실행기를 만들어야 S0가 된다는 생각
- 많은 심사자와 문서가 많을수록 신뢰도가 높다는 생각

### 현재 권고

1. 이 운영안에 대한 사용자 판단을 먼저 받는다.
2. 다음 문서는 실제 `S0 프로토콜` 하나만 작성한다.
3. 프로토콜 승인 전에는 워크트리·출제 세션·시험자료·코드를 만들지 않는다.
4. 프로토콜 승인 뒤에도 현재 Git 상태에서는 최초 기준선 커밋 승인 또는 읽기 전용 자료 묶음 방식 중 하나를 사용자가 선택해야 한다.
5. 첫 S0는 L2 수준의 절차적 격리로 수행하고, 결과에 그 한계를 명시한다.

## 13. 다음 승인 지점

사용자가 다음 네 가지를 확인하면 S0 프로토콜 설계로 넘어간다.

- 출제자→실행자 fork 금지에 동의하는가
- 실행 A–D를 네 개의 새 작업으로 분리할 것인가
- 숨은 정답 전달 관문을 사용자가 맡을 것인가
- Git 최초 기준선 커밋을 나중에 별도 승인할지, 커밋 없는 읽기 전용 자료 묶음을 사용할지

이 결정 전까지 S0는 구현하지 않는다.
