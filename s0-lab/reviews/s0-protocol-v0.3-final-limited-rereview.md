## 2. 최종 판정

**현재 v0.3으로 schema·manifest 설계 가능**

v0.3은 v0.2 제한 재비평의 L01~L10을 모두 프로토콜 수준에서 충분히 반영했다. 제한 수정은 기존 시험 대상을 확장하지 않으면서 다음을 닫았다.

- 조건 표현에 oracle-derived 의미를 추가하는 경로
- byte 15%를 맞추기 위한 padding·내용 왜곡
- 한 block의 우연한 차이로 D를 선택하는 규칙
- §9에서 하나의 결과가 복수 또는 무결론으로 가는 경우
- 같은 원인의 C/M 중복 계수와 run-valid/M5 혼동
- 기술 실패·post-run oracle 결함 뒤 자동 재실행
- 역할 fork, 조건명·선호 가설 노출, 공개·봉인 순서 혼동

이 판정으로 열리는 최대 범위는 `answer.schema.json`과 common/condition-overlay/fixture manifest **형식의 설계·비평**이다. I0 구현, F0 공개·봉인 출제, oracle·scoring 작성, 변환기 실행, A–D 실행 또는 S0 판정은 열리지 않는다.

## 4. 지정 핵심 쟁점의 재확인

### 4.1 `supporting_fact_id`가 D에만 정답을 주는가

**문서상 그렇지 않다.**

v0.3에서 `supporting_fact_id`는 새 판단을 생성하는 근거가 아니라 C 표지·D 관계가 canonical의 어느 명시 사실을 재표현했는지 추적하는 provenance다. 변환기는 oracle·scoring을 읽지 못하고, canonical이 관계를 명시적으로 진술하지 않으면 관계 표지를 만들 수 없다. 최종 판단과 가까운 관계도 같은 명시 관계 사실을 네 조건이 모두 보유해야 한다.

D는 그 관계를 중립 코드와 포인터로 더 직접 표현하므로 탐색이 쉬워질 수 있다. 그러나 이것이 바로 사전에 선언된 `표현 구조` 처치다. D에만 새 사실이나 oracle 판단을 주는 것과는 구분된다. 실제 생성 파일에서 이 불변조건이 지켜지는지는 후속 fixture manifest와 사전 봉인 검토에서 따로 확인해야 한다.

### 4.2 byte 15%는 padding 목표가 아닌 무효 상한인가

**그렇다.**

§3.3은 15%를 초과하면 fixture를 무효로 하고, 그 수치에 맞추기 위한 whitespace·빈 필드·무의미 문장 padding을 금지한다. 사실·관계 의미를 훼손하는 삭제·축약·필드명 교체도 금지한다. token 계측이 가능할 때만 실제 값을 기록하고 불가능하면 추정하지 않으며, fact·record·질문·관계 수도 함께 남긴다. byte 하나를 정보 대칭의 충분조건으로 쓰지 않는다.

### 4.3 두 block 반복 우위와 §9는 total function인가

**그렇다.**

D와 하나의 eligible simple 사이 block별 major 관계는 다음 네 가지 중 하나로만 분류된다.

- 두 block 모두 D가 적음: `D 반복 우위`
- 두 block 모두 simple이 적음: `단순 반복 우위`
- 두 block 모두 같음: `완전 동률`
- 나머지 일곱 조합: `혼합`

이 네 관계는 상호 배타적이고 전체 경우를 덮는다. suite 수준에서도 다음 순서가 전체 상태를 덮는다.

1. suite 무효
2. eligible 0개
3. D 비적격 + simple 존재
4. D만 적격
5. D와 simple 동시 적격

마지막 경우에는 모든 simple에 대한 `D 반복 우위`만 D를 선택한다. 하나라도 혼합이면 비교 불충분, 혼합 없이 단순 반복 우위나 완전 동률이 있으면 `best_simple`이다. 규칙을 위에서 아래로 한 번만 적용하므로 하나의 입력 상태가 두 결론으로 가지 않는다.

두 block은 통계적 일반화를 만들지 않지만, 적어도 한 block의 단일 우위로 D를 선택하던 v0.2 모순은 제거한다.

### 4.4 C/M primary·C 우선·run-valid/M5 경계는 모순 없는가

**문서상 모순이 없다.**

- scoring은 질문·관찰 사건마다 하나의 primary error code를 사전 지정한다.
- 같은 질문·같은 원인에서 C와 M이 함께 성립하면 C만 센다.
- 독립된 원인만 별도 코드로 셀 수 있고 각 코드의 block 최대값은 1이다.
- 존재하고 파싱 가능한 JSON은 환경·해시·상한이 정상이면 run-valid다. 그 안의 질문 누락·중복·schema 오류는 M5다.
- 출력 없음·JSON 파싱 불가·입력 해시 불일치·상한 위반은 M5가 아니라 무효 사유다.

후속 scoring·schema는 이 경계를 그대로 기계화해야 한다. 특히 무효 사유를 M5로 낮추거나 M5를 재시도 가능한 기술 실패로 올리면 현재 동결 규칙을 위반한다.

### 4.5 기술 실패와 post-run oracle 결함이 자동 재실행을 허용하는가

**허용하지 않는다.**

기술 재시도는 의미 결과를 열기 전 로그 가능한 비의미 실패에만 적용되고 전체 suite 기준 최대 한 번이다. 봉인 입력 노출 뒤에는 새 두 block과 새 8개 세션이 필요하다. 그 허용 재시도도 실패하면 현재 시험은 끝나며 새 사용자 게이트 없이는 진행할 수 없다.

post-run primary oracle·scoring 모순은 개별 문항 삭제나 같은 게이트의 자동 재실행으로 처리하지 않는다. 현재 게이트와 suite를 종료하고, 새 봉인 판본·새 사전 검토·사용자 재승인을 요구한다. 이전 무효 결과와 구판 결과를 합칠 수도 없다.

### 4.6 fresh/non-fork, 익명 경로와 공개 순서는 닫혔는가

**문서상 닫혔다.**

- 사전 봉인 검토자와 사후 판정자는 출제·구현·실행 및 서로의 세션을 상속하지 않는 fresh 세션이다.
- A–D의 여덟 실행도 다른 역할과 다른 실행에서 fork하지 않는다.
- 실행자는 불투명 `input.json` 경로와 중립 관계 코드만 받고, 조건 문자·복잡도 순위·H0/H1·D 선호를 받지 않는다.
- 사후 판정자는 정확성 동결 전에 조건 고유 경로·관계 수·시간·byte를 받지 않는다.
- 공개 연습 묶음이 먼저 동결되고 I0는 그것만 사용한다. 이후 F0가 봉인 자료를 분리 작성하며 CONTROL은 oracle 없는 깨끗한 환경에서 canonical input만 변환한다.

실행자는 자신의 표현 형태 자체는 보게 되므로 이를 완전한 처치 맹검이라고 부를 수는 없다. v0.3이 숨기는 것은 조건 문자·복잡도 순위·비교 가설·목표 후보이며, 이 한계는 시험 목적과 일치한다.

### 4.7 schema·manifest 부재와 다음 게이트

**게이트는 유지된다.**

§13은 다음이 아직 없다고 명시한다.

- `answer.schema.json`
- common/condition-overlay/fixture manifest
- 구현과 공개·봉인 fixture
- oracle과 실행·판정 결과

따라서 현재 판정으로 허용되는 작업은 schema와 manifest 형식을 설계하고 다시 비평·동결하는 것뿐이다. 그 문서가 작성됐다는 사실만으로 I0·F0 또는 S0 실행을 열 수 없으며, 사용자가 별도 게이트를 열어야 한다.

## 5. 다음 schema·manifest 비평에서 확인할 항목

다음은 v0.3의 미반영이 아니라 아직 존재하지 않는 산출물에서 확인할 사항이다.

1. 실제 schema가 질문별 option ID, `affected_record_ids`, `short_reason`, M5를 v0.3과 동일하게 고정하는가
2. transformation schema가 oracle·scoring 없이 결정적으로 작동하고 모든 C 표지·D 관계에 유효한 `supporting_fact_id`를 요구하는가
3. common·overlay manifest가 조건 문자·복잡도·가설·목표 후보와 정답 예시를 실행자에게 노출하지 않는가
4. fixture manifest 형식이 byte 15%를 padding 없이 검사하고 fact·record·질문·관계·가능한 token 계측을 함께 기록하는가
5. scoring 형식이 primary code, C 우선, 독립 원인, primary/ancillary와 무효 처리를 결과 전에 고정하는가
6. 접근 manifest가 fresh/non-fork, 허용·금지 입력, 공개 시각과 해시를 역할별로 기록하는가
7. run manifest가 8개 실행, 모델·사고 수준·권한·상한·순서 seed·재시도 1회를 동결하는가

이 확인 전에는 schema·manifest가 v0.3을 실제로 충족한다고 주장할 수 없다.

## 6. 결론과 허용 범위

L01~L10은 모두 충분히 반영됐다. v0.3은 A–D 표현 비교의 프로토콜 기준선으로 schema·manifest 설계를 시작할 수 있다. 이 결론은 구현·fixture·oracle·S0가 준비됐거나 검증됐다는 뜻이 아니다.
