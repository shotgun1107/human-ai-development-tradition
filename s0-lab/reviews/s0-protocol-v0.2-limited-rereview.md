## 2. 최종 판정

**제한 수정 후 schema·manifest 설계 가능**

v0.2는 v0.1의 중심 결함을 다시 설계했다. canonical corpus에서 생성된 실제 A–D 파일을 시험 처치로 삼고, 공통 답안과 객관 실행 기록을 분리했으며, 두 block·8개 fresh 실행 단위, 실행 전 봉인 검토자와 별도 사후 판정자, 결과 전 자원 상한과 재시험 원칙을 도입했다. 이 변경으로 v0.1의 `중대한 수정` 사유는 해소됐다.

그러나 현재 문언에는 다음 세 종류의 국소 모순이 남는다.

1. `counterexample_to` 같은 D edge와 C의 상태·범위 표지가 canonical fact의 기계적 재표현인지 oracle 판단인지 보증하는 규칙이 부족하고, byte 15%를 맞추기 위한 padding·필드명 변경이 새 입력 차이를 만들 수 있다.
2. §2.3과 §9의 D 승리 조건이 서로 충돌하며 §9 결정표가 일부 결과를 하나의 끝 상태로 보내지 못한다.
3. C/M 교차 계수, post-run oracle 결함 뒤 재시험 상한, 판정자 입력·블라인드 세부에 제한된 사후 재량이 남는다.

이 결함은 전체 시험 구조를 다시 만들 필요는 없지만, schema·manifest가 그 모순을 상속하기 전에 프로토콜 문언에서 먼저 고쳐야 한다.

이 판정은 `answer.schema.json`, common/overlay manifest의 설계를 준비할 수 있다는 뜻일 뿐이다. I0 구현, F0 공개·봉인 출제, oracle 작성, 변환기 실행 또는 S0 실행을 허가하지 않는다.

## 4. 핵심 확인 항목

### 4.1 canonical corpus → A–D는 관찰 가능한 시험 처치인가

**판정: 관찰 가능하다.**

§2.2와 §3.2는 각 실행자가 canonical corpus 자체가 아니라 결정적으로 생성된 조건별 파일 하나를 받게 한다. 조건 차이는 파일·해시·fact manifest로 남고, 숨은 사고과정을 근거로 구조 준수 여부를 추정하지 않는다. v0.1의 `같은 원문을 보고 머릿속에서 무엇을 했는지 알 수 없음` 문제는 해소됐다.

다만 `표현 차이`와 `추가 정답 정보`는 아직 완전히 분리되지 않았다. D의 `counterexample_to`, `withdraws`와 C의 `상태·범위`가 canonical corpus의 명시 사실을 단순 재표현한 것인지, 출제자·변환기가 oracle 판단을 미리 붙인 것인지 현재 규칙만으로는 감사할 수 없다. 특히 §3.1은 반례·철회의 `원문 단서`를 보존한다고 하고 §3.2는 D에 해석된 edge를 준다. 이 edge가 단서에서 새로 추론된 것이라면 D에 답안 힌트를 추가한 셈이다.

**제한 수정 요구**

- 변환기는 `canonical-input + 공개 transformation schema`만 읽고 oracle·scoring을 읽을 수 없다고 명시한다.
- C의 모든 상태·범위 표지와 D의 모든 edge는 하나 이상의 `supporting_fact_id`를 가져야 한다.
- edge·표지가 허용되려면 canonical corpus가 그 관계를 명시적으로 진술해야 한다. 단서로부터 평가적 관계를 새로 추론하는 변환은 금지한다.
- `counterexample_to`처럼 최종 판단과 가까운 관계는 중립 관계 코드로 바꾸거나, 네 표현 모두에 같은 명시 관계 사실이 있음을 사전 봉인 검토자가 확인한다.

### 4.2 byte 15%와 fact 보존 규칙은 새 비대칭을 만드는가

**판정: fact ID·본문 해시 보존은 유효하지만 byte 규칙은 부분 수정이 필요하다.**

동일 fact 집합, record ID, 정규화 본문 해시는 내용 삭제를 막는 좋은 불변조건이다. 그러나 UTF-8 byte가 비슷하다고 모델 입력 기회가 같은 것은 아니다. JSON 공백 padding은 모델이 읽을 무의미한 입력을 한 조건에 더 주고, 동일 길이 필드명 매핑은 필드의 해석 난도나 힌트 강도를 바꿀 수 있다. byte 한도를 맞추려고 표현을 왜곡하면 구조 자체가 아닌 padding·명명 차이를 측정하게 된다.

**제한 수정 요구**

- 15%는 `초과 시 fixture 무효`인 상한으로만 사용하고, 그 수치에 맞추기 위한 whitespace padding을 금지한다.
- 사실·관계 의미를 보존하지 못하면 byte를 맞추기 위해 삭제·축약·필드명 교체하지 않고 fixture를 재설계한다.
- 선택 모델의 tokenizer 계측이 가능하면 실제 input token 수도 기록한다. 불가능하면 추정하지 말고 byte, fact 수, record 수, 질문 수, 명시 관계 수를 함께 공개한다.
- 공통 필드명과 조건 고유 필드명의 의미·길이·설명량을 overlay manifest에서 따로 비교한다. byte 차이 하나로 정보 대칭을 통과 처리하지 않는다.

### 4.3 공통 중립 JSON은 D scaffold를 제거했는가

**판정: 프로토콜 수준에서는 제거했다.**

§6의 답안은 질문별 decision, 직접 record ID, 영향 record ID, 불확실성, 짧은 이유만 요구한다. 이는 계보 node·edge나 증거 계열 수를 만들어 내라는 요구가 아니며, 조건명과 실행 비용도 답안 밖으로 이동했다. `human_approval_required: true` 같은 고정 답도 사라졌다.

`activate|limit|suspend|retire`, `data_only`, `human_decision`은 결과 의미를 나타내는 공통 선택지이지만, 한 전역 enum으로 제시하면 질문 유형별 예상 답을 미리 암시하거나 무효 조합을 만들 수 있다. 실제 schema에서는 다음을 확인해야 한다.

- 질문별 허용 decision 집합을 중립 option ID로 묶거나 조건부 schema로 제한한다.
- `short_reason`에 조건 파일명, field명, edge명을 쓰지 않게 해 사후 판정자가 조건을 추정하지 못하게 한다.
- `affected_record_ids`가 필요 없는 질문에는 빈 배열을 강제할지 필드를 생략할지 하나로 고정한다.
- 사후 판정자에게 `answer.schema.json`과 질문 manifest의 동결 해시를 함께 제공한다. 그래야 M5를 판정할 수 있다.

이 네 항목은 schema 설계의 합격 조건이지 현재 구현 허가가 아니다.

### 4.4 두 block·8 fresh 세션은 단일 우연 문제를 줄이는가

**판정: 줄이지만, 현재 D 승리 규칙은 그 이득을 끝까지 사용하지 않는다.**

조건×block마다 별도 fresh 세션을 두므로 앞 조건·앞 block의 답이 다음 실행에 섞이는 문제는 줄었다. 서로 다른 두 사건군을 쓰는 것도 단일 fixture 배치에 대한 맞춤을 일부 줄인다. 문서가 통계적 일반화를 금지한 점도 적절하다.

그러나 각 cell은 여전히 한 번만 실행된다. 더구나 §2.3은 `한 block만의 우연한 우위는 D 승리가 아니다`라고 하면서, §2.3과 §9.2 규칙 6은 D가 두 block에서 나쁘지 않고 **최소 한 block**에서만 엄격히 나아도 D를 유지하도록 한다. 즉 선언과 결정표가 충돌하며, 한 번의 우연한 차이가 D 승리의 유일한 근거가 될 수 있다.

**제한 수정 요구**

- 8개 실행 단위를 유지하려면 D 승리에 필요한 우위가 두 block 모두에서 반복되도록 정한다.
- 한 block 엄격 우위·다른 block 동률을 허용하려면 `한 block만의 우연한 우위는 승리 아님` 문구를 삭제하고 결과를 `제한적 D 신호` 또는 `비교 불충분`으로 낮춘다.
- 어느 선택이든 결과 전에 한 규칙으로 고정하며, 단일 cell의 stochastic 출력 차이를 통계적 효과로 표현하지 않는다.

### 4.5 사전 봉인 검토자와 사후 판정자 분리는 닫혔는가

**판정: 프로토콜 구조상 닫혔다.**

S0-04는 실행 전에 input·oracle·scoring·fact manifest·A–D 표현을 검토하고, 결과를 보지 않는다. 사후 판정자는 결과 동결 뒤 새 세션으로 생성되고 익명 정확성만 먼저 채점한다. CONTROL은 그 판정 해시 뒤 조건을 복원한다. 출제자 한 명의 oracle을 결과 후 처음 받아 그대로 적용하던 v0.1 문제는 해소됐다.

실제 manifest에는 다음을 빠뜨리면 안 된다.

- 사전 검토자와 사후 판정자는 F0·I0·A–D·서로에게서 fork하지 않은 fresh 세션이다.
- 두 역할의 허용 입력과 금지 입력, 접근·공개 시각, 산출물 해시를 각각 기록한다.
- 사후 판정자는 schema·질문 manifest도 받지만 조건 overlay·비용·관계 수는 정확성 동결 전 받지 않는다.
- runner-facing 파일명은 불투명하게 하고, 표현 종류는 보이더라도 A–D 문자·복잡도 순위·H1·D 선호는 보이지 않게 한다.

표현 처치 자체는 실행자가 보게 되므로 완전한 처치 맹검이라고 부르면 안 된다. 숨겨야 하는 것은 조건 문자, 비교 순위와 선호 가설이다.

### 4.6 C/M 단일 계수와 완전 결정표는 모든 끝 상태를 하나로 보내는가

**판정: 아직 아니다.**

같은 코드·같은 block의 최대 계수를 1로 둔 것은 v0.1보다 명확하다. 그러나 같은 잘못이 C4와 M4처럼 서로 다른 코드·등급에 동시에 들어갈 때의 우선순위가 없다. `오류 중복 계수 없음`이라는 사전 검토 문구만으로는 scoring 작성자의 선택을 고정하지 못한다.

또한 §9에는 다음 모순·누락이 있다.

1. D가 eligible이지만 A보다 두 block 모두 major가 많으면 규칙 5에서 D는 탈락한다. 규칙 3은 `D가 eligible이 아닐 때`만 적용되므로 어느 단순 조건을 최종 선택할지 정해지지 않는다.
2. D가 A보다 block-1에서 낫고 block-2에서 동률이면 규칙 6은 D 유지를 허용하지만 규칙 7은 `하나라도 동률`인 A를 선택하게 한다.
3. D가 한 block에서 낫고 다른 block에서 나쁘면 규칙 5는 D 탈락, 규칙 8은 `비교 불충분`을 동시에 지시한다.
4. §9.1은 schema가 유효해야 `valid`라고 하면서 §8.2는 schema 위반을 M5로 센다. schema 위반이 조건 탈락인지 채점 가능한 M5인지 둘 다일 수 없다.

**제한 수정 요구**

- `best_simple`을 먼저 하나의 함수로 정의한다: eligible A–C 중 두 block의 사전 정의 비교값이 최선인 조건, 동률은 A→B→C.
- D와 각 simple의 비교 결과를 `D 반복 우위 / simple 우위 / 교차 / 완전 동률` 중 정확히 하나로 분류한다.
- 위 분류 조합마다 `D 유지 / best_simple / 비교 불충분 / 모든 구조 실패 / 시험 무효` 중 하나만 반환하는 표를 만든다.
- 한 관찰 사건에 하나의 primary 오류 코드만 허용할지, 서로 다른 오류 차원을 동시에 세는지 scoring 규칙에 명시한다. 단일 계수를 주장하려면 C가 M보다 우선하고 같은 질문·같은 원인에 M을 추가하지 않는 식의 precedence가 필요하다.
- `valid`는 환경·무결성 판정으로 한정하고, 파싱 가능한 schema 위반은 M5로 셀지 정한다. 파싱 불가·출력 없음·해시 불일치의 별도 끝 상태도 고정한다.

### 4.7 기술 실패·oracle 결함·재시험의 사후 재량은 닫혔는가

**판정: 기술 실패는 대체로 닫혔고 oracle 결함은 일부 남았다.**

§10.2는 기술 실패를 로그 가능한 비의미 사건으로 좁히고, 의미 결과 열람 전 CONTROL이 판정하며, 봉인 input 공개 전/후를 나눠 같은 자료 재사용 여부를 고정한다. 한 실행만 다시 돌릴 수 없고 전체 suite 재시도는 1회이며 가장 이른 유효 suite만 사용한다. 이 부분은 사후 선택을 실질적으로 줄였다.

남은 문제는 다음과 같다.

- 허용된 한 번의 기술 재시도도 실패했을 때 최종 결과가 명시되지 않았다.
- post-run oracle 결함은 새 봉인 판본을 요구하지만, 같은 프로토콜 아래 몇 번까지 다시 실행할 수 있는지와 누가 새 게이트를 여는지 없다.
- `주요 결과와 연결된 모순`인지 여부를 결과 뒤 정할 수 있다. primary/ancillary 분류를 scoring에 미리 두지 않으면 문항 삭제 금지 규칙을 우회할 수 있다.

**제한 수정 요구**

- 허용된 기술 재시도 실패는 즉시 `시험 무효—새 게이트 필요`로 끝낸다.
- 실행 뒤 oracle/scoring 결함은 현재 S0 gate를 종료하고, 새 봉인 판본의 사전 검토와 사용자 재승인 없이는 자동 재실행하지 못하게 한다.
- primary/ancillary 항목과 각 결함의 `전체 무효/보고 전용` 처리를 scoring 해시에 결과 전에 넣는다. primary 항목은 사후 삭제할 수 없다.
- oracle 결함 재실행을 허용한다면 전체 suite attempt 상한에 포함하고, 모든 이전 무효 결과·해시·이유를 보존한다.

### 4.8 실행자에게 조건 이름·가설·선호가 숨겨지는가

**판정: 비교 가설은 숨겨지지만 runner-facing 명명은 더 중립화해야 한다.**

§7.1은 A–D 문자, 복잡도 순서, H0/H1, D가 목표 후보라는 설명을 실행자에게 주지 않고 CONTROL이 불투명 매핑을 보관하게 한다. 이는 필요한 가설 맹검을 명시한다.

다만 §3.2의 예시 파일명 `common-list.json`, `minimal-lineage.json`과 D 고유 edge명이 그대로 runner-facing 경로·필드가 되면 실행자는 자신의 표현 종류와 목표 설계 언어를 강하게 추정할 수 있다. 처치의 형태를 숨길 수는 없지만, `lineage`가 목표 후보라는 인상을 줄 필요는 없다. 실제 overlay·파일명은 불투명 코드로 바꾸고 공통 데이터 사전은 의미 이해에 필요한 만큼만 제공해야 한다. `short_reason`에도 이 명칭이 되풀이되지 않게 해야 사후 판정자 맹검이 유지된다.

### 4.9 아직 없는 schema·manifest가 다음 게이트를 잘못 여는가

**판정: 현재 문언은 게이트를 올바르게 닫는다.**

§13은 answer schema·manifest가 아직 없다고 명시하고, v0.2 재비평 뒤 열 수 있는 최대 범위를 schema·manifest 설계로 제한한다. §11도 schema와 manifest를 별도로 비평·동결한 뒤에야 구현·출제로 이동한다. 따라서 이 재비평으로 구현·출제·oracle·S0 실행을 승인하는 해석은 허용되지 않는다.

다만 §11의 공개 자료와 구현 순서는 schema·manifest 단계에서 정리해야 한다. 구현자가 공개 자료를 받는 단계보다 공개 자료 작성자가 뒤에 나타나므로, `F0 공개 묶음 작성·동결 → I0 공개 묶음만 사용` 순서를 명시해야 한다. 봉인 canonical input을 결정적 변환기에 누가 입력하고 누가 생성 결과를 해시하는지도 접근 manifest에 고정해야 한다.

## 5. schema·manifest 설계 전에 필요한 제한 수정

다음 수정은 새 역할·새 제품 기능·시험자료 작성을 요구하지 않는다.

1. §3에 변환기 oracle/scoring 접근 금지와 C 표지·D edge의 `supporting_fact_id` provenance 규칙을 추가한다.
2. byte 15%를 padding 목표가 아닌 무효 상한으로 바꾸고 whitespace padding을 금지한다.
3. §2.3과 §9의 두 block 우위 기준을 하나로 통일한다.
4. §9를 실제 total function으로 다시 쓰고, `best_simple`, 교차·동률·D 탈락의 끝 상태를 하나씩 고정한다.
5. C/M 교차 계수 precedence와 `valid`–M5 경계를 명시한다.
6. post-run oracle 결함의 재승인·attempt 상한과 허용된 재시도 재실패의 종료 상태를 명시한다.
7. 사전 검토자·사후 판정자의 fresh/non-fork와 허용 입력, 사후 판정자의 schema 입력을 명시한다.
8. runner-facing 파일·필드명과 short reason에서 조건 문자·복잡도·목표 설계 명칭이 드러나지 않게 한다.
9. §11의 공개 묶음 작성→구현 점검 순서와 봉인 변환기 실행 책임을 정리한다.
10. 변경 장부의 P1-03·P1-04·P1-06 상태를 `부분 반영—제한 수정 필요`로 맞춘다.

위 수정판과 SHA-256을 확인한 뒤 열 수 있는 최대 작업은 다음뿐이다.

- `answer.schema.json` 설계
- common manifest 설계
- condition overlay manifest 설계
- 이들 문서의 표현 중립성·자원 대칭·게이트 비평

schema·manifest가 작성됐다는 사실만으로도 구현·출제 게이트는 열리지 않는다. 별도 비평·동결과 명시적 다음 게이트가 필요하다.

## 6. 문서 수정으로 알 수 없는 항목

다음은 제한 수정과 schema·manifest 동결 뒤에도 실제 분리 실행에서만 확인할 수 있다.

- 변환기가 네 표현에 같은 fact를 실제로 보존하고 oracle-derived 힌트를 넣지 않았는지
- 두 봉인 block이 실제로 서로 다른 사건·표현·정답 위치를 가졌는지
- 8개 실행이 fresh 세션이고 다른 block·조건·가설·oracle을 보지 않았는지
- 동일 모델 표시·사고 수준·권한·시간·출력 상한이 실제 적용됐는지
- 사전 검토자와 사후 판정자의 접근·비노출·해시 순서가 지켜졌는지
- C/M 단일 계수와 total decision function이 결과 변경 없이 기계적으로 적용됐는지
- D의 우위, H0 유지, 교차 우위 또는 모든 구조 실패 중 무엇이 관찰되는지

다음은 S0로도 판단할 수 없다.

- 실제 자료·실제 권한·실제 Project Brain 통합
- 실제 품질·안전·비용·경제성·모델 전이
- 복수 자산·다중 프로젝트·승인 피로·장기 운영
- 내부·외부 브랜드 효과나 대외 주장

## 7. 결론

v0.2는 v0.1의 차단 결함을 해소할 수 있는 방향으로 충분히 축소·구체화됐고, 다시 전면 설계할 필요는 없다. 다만 byte/fact 동등성, D 우위의 두 block 반복 조건, 완전 결정표, C/M precedence, oracle 결함 재게이트를 먼저 제한 수정해야 한다.
