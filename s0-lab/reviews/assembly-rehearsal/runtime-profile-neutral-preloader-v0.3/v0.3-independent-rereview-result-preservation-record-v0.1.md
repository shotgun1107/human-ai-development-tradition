## 4. Findings

### RPNP3-RR-001 — MAJOR — guard cannot prove verifier-wide handle absence or exact-list provenance

Affected artifacts and sections:

- `public-assembly-runtime-profile-neutral-preloader-design-revision-v0.3.md`
  §§4.1 and 4.3;
- `public-assembly-runtime-profile-neutral-preloader-interface-map-v0.3.json`
  keys `bootstrap_guard.native_validation` and `inherited_handle_policy`;
- `public-assembly-runtime-profile-neutral-preloader-acceptance-plan-v0.3.md`
  §§5.1–5.3.

The design requires the native guard to establish that opposite pipe ends and
every extra handle are absent from the verifier and that the five locators
derive from the exact preloader handle list. The guard receives only five
locator values and an admission frame whose digest covers five semantic
role/object/access descriptors. Its frozen native call surface can inspect
those five known handles, but it has neither verifier handle-table enumeration
nor an independently authenticated exact-list attestation.

Counterexample: launch a verifier with five valid located handles plus an
unexpected sixth inherited handle or an opposite pipe end. Every validation
applied to the five locators and their descriptor digest can pass. The listed
`GetHandleInformation`, `GetFileType`, `GetNamedPipeInfo`, `NtQueryObject`, and
other frozen calls cannot discover an unknown sixth handle merely from the five
supplied values.

The authenticated preloader construction may prove which handle list it asked
the kernel to inherit, but that is not the same observation as guard-side
verifier-wide absence. The current design assigns the same proposition to both
without defining how the guard observes it.

Smallest sufficient correction:

1. allocate exact-list construction, standard-handle exclusion, duplicate
   closure, opposite-end absence, and no-extra-handle provenance explicitly to
   the authenticated preloader/launcher plus trusted kernel semantics and
   source/binary review; and
2. limit the guard to validating the five located live objects and their
   admission, nonce, and process bindings.

Alternatively, add an exact authenticated enumeration or kernel-attestation
mechanism and freeze its API, profile, implementation, and hostile tests.

Impact: inherited-handle interface, channel peer/provenance threat model,
native guard call surface, acceptance mutations, and complete closure of
`RPNP2-RR-001`.

### RPNP3-RR-002 — MAJOR — v0.3 schema does not force the closure promised by the design

Affected artifacts and sections:

- `public-assembly-runtime-profile-neutral-preloader-design-revision-v0.3.md`
  §§2, 3.2–3.3, and 6;
- `runtime-profile-v0.3.schema.json` top-level `required` and objects
  `platform_binding`, `bootstrap_guard`, `inherited_handle_policy`, and
  `atomic_root_policy`;
- `public-assembly-runtime-profile-neutral-preloader-interface-map-v0.3.json`
  keys `atomic_root_create`, `bootstrap_guard`, `inherited_handle_policy`, and
  `package_composition`;
- `public-assembly-runtime-profile-neutral-preloader-acceptance-plan-v0.3.md`
  §§4–6 and 8.

The design says the v0.3 profile freezes the guard source/binary/build/import
closure, compiler/linker and loaded-image identities, initialization and CRT
imports, per-handle access and opposite-end policy, complete atomic-root ABI
and postconditions, retained/duplicate object identity, and exact four-row
package composition. The schema requires only a subset.

The reviewer constructed a Draft 2020-12-valid counterinstance in memory using
all required fields and constants while omitting, among other things:

- compiler and linker identities;
- guard loaded-image identity;
- a virtual path for the import manifest;
- Python-extension initialization and CRT import closure;
- per-role handle access and opposite-end policy;
- root returned-handle, status, and object postconditions;
- duplicate-object equality and continuous retention; and
- package effective row names and order.

The schema accepted that counterinstance.

Smallest sufficient correction: add required, closed schema objects or exact
policy identifiers for every promised guard/build/import/platform,
per-handle, atomic-root/postcondition/retention, and package-composition
predicate. Bind the import manifest by path and hash, make the required
cross-profile and predecessor relationships explicit, and add mutations that
prove omission or weakening of every predicate rejects.

Impact: runtime-profile schema, runtime/native trust closure, atomic-root
interface, package exact-set authority, and acceptance evidence. A
schema-conforming profile currently need not express the design's claimed
security closure.

## 5. Required semantic-question dispositions

### 5.1 Replacement scope and predecessor closure

The v0.3 replacement scope is appropriately limited to handle discovery and
private binding, atomic output-root creation and related failure routing, and
terminal retry semantics. Unrelated v0.1/v0.2 trust, channel, process/job,
commit, receipt, routing, and claim-limit predicates remain conjunctive.

`RPNP2-RR-002` and `RPNP2-RR-003` are closed at design level. v0.3 removes the
locator-discovery circularity from `RPNP2-RR-001`, but its replacement
overclaims guard-side exact-list and opposite-end verification, so full closure
fails under `RPNP3-RR-001`.

The v0.2 result record is correctly treated as CONTROL normalization, not a
reviewer signature or approval.

### 5.2 Handle discovery and locator authority

The command line exposes all five roles without prior admission-frame access.
Order, fixed-width lowercase representation, count, distinction, malformed or
extra argument rejection, standard-handle exclusion, and `sys.argv` scrubbing
are specified. Numeric locators are non-authoritative, and a substituted,
stale, closed, wrong-type, wrong-direction, or overprivileged located handle
must reject before wrapper publication. Verifier-wide extra/opposite-end
absence remains unprovable by the frozen guard under `RPNP3-RR-001`.

### 5.3 Native bootstrap guard

The prose requires source, build recipe, compiler/linker, binary, imports,
origin, hash, and loaded-image authentication before use. `bind_once_v3`
consumes its process-global latch before validation, so both success and
failure preclude a second authority. The located-object and admission checks
precede authority publication, and the specified partial-return, copying,
alias-import, reload, and generic-FFI routes do not provide a second authority.

The remaining defects are the guard-side allocation in `RPNP3-RR-001` and the
schema underconstraint in `RPNP3-RR-002`.

### 5.4 Atomic output-root construction

The design specifies one parent-relative `NtCreateFile` call that creates the
absent leaf and returns the sole retained root handle. Its x64 ABI, eleven
arguments, access, attributes, share, disposition, options, object flags,
null arguments, `FILE_CREATED`, and status/handle requirements are internally
consistent. Relative naming, `OBJ_DONT_REPARSE`, `FILE_CREATE`, exact post-call
checks, no reopen, continuous retention, and case-collision rules close the
original create/open race at the prose/interface level.

### 5.5 Runtime and native trust closure

The direct `ntdll.dll!NtCreateFile` import is compatible with the declared
external CONTROL-launcher and Windows-kernel trust roots, provided the frozen
identity and export checks happen before the first authoritative native call.
The design and interface map describe the required policies, but the schema
does not force all of them under `RPNP3-RR-002`.

### 5.6 State and commit ordering

The effective order is absent-root intent, atomic creation and retained
identity, suspended verifier creation, native handle binding into
`ROOT-CREATED-BOUND`, publication, commit request, preloader recheck, reply,
and the same-process consumer. Invalid nonterminal transitions enter
`REJECTED`; attempts against `SPENT` or `REJECTED` fail without state mutation.
`OK`, output presence, exit code, stdout, stderr, or copied authority cannot
independently produce PASS.

### 5.7 Failure routing and residue

Pre-create authentication failure remains root-absent `AR-AUTH/0`. Every
failure after `FILE_CREATED` and before verifier admission remains
`AR-BOUNDARY/0` with quarantined-root residue. Native guard failure cannot be
caught and downgraded, and cleanup diagnostics cannot upgrade a failure.

### 5.8 Implementability and acceptance evidence

The locator, one-use guard, `NtCreateFile`, handle duplication, and transition
mechanisms are otherwise concrete enough for later implementation on the
admitted Windows profile. The guard-wide absence proposition is not
implementable with the frozen observation surface. The acceptance plan covers
the relevant positive, malformed, hostile, race, state, source/build,
binary/import, status, and object cases and retains a later real-platform proof
gate.

### 5.9 Security and claim boundaries

Implementation, compilation, dependency installation, runtime-profile
materialization, platform probe, official rehearsal, real native calls, F0,
oracle, provider/model/network, S0/E0, central system, Project Brain,

integration remain closed. This verdict does not open implementation.
