## 2. 판정

**중대한 수정 후 재비평**

v0.1은 실행 전 통제의 큰 항목을 열거했지만, 현재 상태로는 A–D의 차이가 무엇인지 관찰 가능하게 고정되지 않았고, 공통 JSON이 D의 핵심 용어와 일부 정답을 모든 조건에 제공한다. 또한 봉인 `oracle`·`scoring`은 결과 전에 독립 검토되지 않으며, 비용 상한·단일 실행의 변동성·정답 결함·기술 재시도의 선택 규칙에도 결과 후 재량이 남아 있다. 이 결함들은 실행 결과가 어느 구조의 효과인지, 혹은 출력 양식·출제자·재실행 선택의 효과인지 구분하지 못하게 하므로 제한 문구 보완만으로 동결할 수준이 아니다.

이 판정에 따라 §12의 프로토콜 자체 합격 조건은 충족되지 않았다. I0 구현과 F0 출제 게이트를 열어서는 안 된다.

## 3. 구현 전에 반드시 고칠 결함

### P1-01. A–D의 실험적 차이가 관찰 가능하게 정의되지 않았다 — 차단 결함

**확인 사실**

- §3은 네 조건의 차이를 `허용되는 공통 정리 구조`로 한정한다.
- §3.1은 네 조건 모두에게 같은 전체 원문을 주고, A–C도 메모·추론·교차 확인을 허용한다.
- §7은 실행을 한 번의 turn으로 제한한다.
- §8은 모든 조건에 동일한 관계 중심 JSON을 요구한다.
- §9.2는 `허용 구조 밖의 공통 표현을 사실상 사용`한 경우를 중대 오류로 두지만, 이를 관찰할 별도 조건 산출물이 없다.

**판단**

현재 설계에서는 A–C가 내부 추론 중 임시로 출처 관계를 구성해도 외부에서 확인할 수 없다. 이를 허용하면 네 조건은 사실상 서로 다른 짧은 지시문을 받은 동일한 원문 추론이 되고, 금지하면 보이지 않는 추론을 추정해 벌점을 주게 된다. 반대로 동일 JSON이 관계·철회·근거 묶음을 모두 요구하므로 A–C도 최종 출력 단계에서는 D와 유사한 구조를 만들어야 한다. 따라서 결과 차이를 `공통 구조`의 차이로 귀속할 수 없다.

**최소 수정**

1. 시험 대상을 하나로 고정한다.
   - 권고: `같은 원문을 받은 동일 모델이 조건별로 허용된 명시적 중간 산출물을 만든 뒤, 그 산출물로 같은 후속 판단을 수행할 때의 오류·비용 차이`로 정의한다.
   - 한 번의 turn 지시문 비교만 유지한다면 결론도 `네 프롬프트 절차의 일회성 차이`로 낮추고, 구조 유지·축소 결정을 내려서는 안 된다.
2. `공통 중립 답안`과 `조건 고유 정리 산출물`을 분리한다.
3. 조건 고유 산출물의 허용 필드·최대 크기·작성 시간을 사전에 동결하고, 구조 준수는 이 명시적 산출물만으로 판정한다. 비공개 추론 과정은 채점하지 않는다.
4. 후속 판단 단계에서 원문과 조건 고유 산출물 중 무엇을 다시 볼 수 있는지 네 조건별로 명시한다. 초기 원천 corpus의 제공 기회는 같게 유지하고, 이후 접근 차이가 실험 처치라면 그 사실을 명시한다.

### P1-02. 공통 JSON이 표현 중립적이지 않고 일부 답을 고정한다 — 차단 결함

**확인 사실**

§8의 공통 JSON은 다음을 모든 실행자에게 미리 제공한다.

- `independent_evidence_count`, `counterevidence_ids`
- `candidate|limited_trial|active|suspended|retired|no_change`
- `withdrawal_impacts`의 원근거→영향 대상 관계
- `audit_trace`의 decision path
- `brain_boundary_decision.human_approval_required: true`

또한 `condition_code`와 실행 시간·문자 수·사람 개입 같은 계측값을 실행자 자신이 출력하도록 한다.

**판단**

이 스키마는 D가 주장하는 증거 계열, 상태 수명주기, 철회 영향 관계와 감사 경로를 A–C에도 해법의 골격으로 준다. 특히 `human_approval_required`를 리터럴 `true`로 제시한 것은 사례를 읽기 전에 답을 고정한다. 반대로 이 필드를 정확히 채우도록 요구하면서 A–C의 관계 표현을 금지하면 A–C에는 모순된 과제가 된다. 실행자가 자기 시간·문자 수를 보고하는 방식도 객관적 비용 기록이 아니다.

**최소 수정**

1. 공통 답안은 사례별 관찰 가능한 결과만 요구한다. 예: `question_id`, `decision`, `cited_input_ids`, `affected_output_ids`, `uncertainty`, `short_reason`.
2. D 고유 명칭인 증거 계열·계보·상태 이름·관계 경로는 공통 정답 필드에서 제거하고 조건 고유 산출물로 이동한다.
3. 사람 승인 여부가 필요한 경우 고정값이 아닌 일반 boolean 또는 사례별 결정으로 받고, 사례에 따라 `true`와 `false`가 모두 가능해야 한다. 항상 참이라면 필드를 제거하고 공통 규칙으로만 둔다.
4. `condition_code`는 실행 결과 본문에서 제거하고 CONTROL의 외부 매핑에 둔다.
5. 시작·종료 시각, 경과시간, 출력 byte/문자 수, 파일 수, 재시도, 사람 개입은 실행 도구나 CONTROL이 별도 `run-record`에 기록한다.
6. 예시 JSON이 아니라 기계 검증 가능한 JSON Schema 판본, 필수/선택 필드, null 처리, 정렬·정규화, 형식 실패 판정을 동결한다.
7. C1–C7과 각 중대 오류가 어느 입력 사실과 어느 중립 출력 필드로 관찰되는지 `criterion-to-observable` 표를 만든다. 숨은 추론을 근거로 채점하지 않는다.

### P1-03. 자원 대칭과 출력 기회가 선언 수준이며 비교 단위도 충분히 고정되지 않았다 — 차단 결함

**확인 사실**

- §7은 모델·사고 수준을 후속 `run-manifest`에 맡기고 20분 벽시계 상한만 적는다.
- 토큰·출력 크기·조건 고유 산출물 크기·도구 호출 수의 상한은 없다.
- §9.4는 D가 `프로토콜 상한` 안에 있어야 한다고 하지만 시간 외 비용 상한이 프로토콜에 존재하지 않는다.
- §4는 일부 사건 수만 고정하며 총 문서 수, 총 입력 크기, 프로젝트별 분량, 주장 수, 무관 정보량, 오류별 채점 기회 수를 고정하지 않는다.
- §7의 `실행 입력 파일과 해시가 동일`하다는 문구와, §6의 조건별 지시문 제공은 구분되어 있지 않다.

**판단**

현재 F0가 corpus 크기와 오류 기회 수를 조절해 D에 유리하거나 불리한 난도를 만들 수 있다. 조건별 지시문은 필연적으로 다르므로 `입력 동일`만으로는 대칭을 입증하지 못한다. D의 유지 조건에 필요한 관리비 상한도 비어 있어 선택 규칙을 실행할 수 없다.

**최소 수정**

1. 실행 전 해시할 대칭 manifest를 다음처럼 분리한다.
   - 모든 조건 공통인 system/project 지침과 원천 corpus
   - 조건마다 다른 최소 overlay 지시문
   - 공통 중립 출력 스키마
   - 조건 고유 산출물 스키마
2. overlay마다 허용 정보, 힌트, 예시, 길이를 검토해 한 조건에만 정답 단서를 주지 않았다는 표를 동결한다. 조건 지시문이 다르다는 사실 자체는 숨기지 않는다.
3. 모델 표시명·가능한 버전 정보·사고 수준·도구·권한·세션 신선도·실행 창·순서 또는 무작위화 값·시간 상한·출력 상한·파일 상한을 `run-manifest`에 고정한다. 제공자가 내부 모델 판본을 보장하지 않으면 그 한계를 기록하고 완전 동일 모델이라고 과장하지 않는다.
4. 총 corpus byte/token, 프로젝트별 범위, 채점 대상 사건 수, 오류 코드별 기회 수, 무관 정보 범위를 fixture manifest에서 결과 전에 고정한다.
5. 토큰 사용량을 얻을 수 없다면 모든 조건에서 같은 입력·출력 상한을 강제하고, 비교 비용에는 관찰 가능한 값만 사용한다.
6. 자원 값과 전체 시험 예산은 봉인 자료 작성과 구현 전에 사용자가 승인하고 해시해야 한다. `나중에 정함` 상태로 프로토콜을 frozen으로 바꾸지 않는다.

### P1-04. H0는 문언상 열려 있지만 선택 규칙이 완전히 반증 가능하지 않다 — 차단 결함

**확인 사실**

- §2.2의 H0는 A–C를 하나의 복합 대안으로 묶고, H1의 `A–C보다 하나 이상`은 어느 단순 조건과의 비교인지 모호하다.
- §9.4는 먼저 중대 오류 수와 단순성으로 선택하면서, D 유지 조건에서는 C와의 차이와 미정 비용 상한만 별도로 요구한다.
- 중대 오류는 코드·중복 계산 단위·동일 사건의 다중 계수 규칙이 없다.
- 모델 출력은 변동 가능하지만 조건별 실행은 한 번뿐이며, 단 한 건의 중대 오류 차이로 구조 후보를 바꿀 수 있다.

**판단**

동률이면 단순 조건을 택하므로 H0가 형식상 이길 수는 있다. 그러나 어느 대조가 H1을 지지하는지, 오류 하나를 몇 건으로 세는지, 비용과 오류가 엇갈릴 때 무엇을 택하는지, 한 번의 우연한 모델 출력 차이를 언제 구조 차이로 인정하는지가 고정되지 않았다. 현재 규칙만으로는 같은 결과표에 복수의 합리적 최종 판정이 가능하다.

**최소 수정**

1. H0/H1의 비교 단위를 네 개의 개별 조건과 사전 정의된 봉인 block으로 다시 쓴다.
2. `유효성 → 치명 오류 존재 여부 → 사전 코드별 중대 오류 수 → 비용 자격 → 단순성`의 순서처럼 완전한 결정표를 만들고, 가능한 모든 끝 상태를 한 가지 결론에 매핑한다.
3. D는 모든 유효한 더 단순한 조건보다 사전 정의 오류 기준에서 엄격히 나을 때만 유지 후보가 되게 한다. 동률, 교차 우위, 비용 상한 초과는 각각 단순 조건 선택 또는 `비교 불충분`으로 명시한다.
4. 중대 오류에도 고정 코드를 부여하고, 한 입력 사건이 여러 필드에 나타날 때 한 번만 세는지 코드별로 세는지 정한다.
5. 비용은 `자격을 박탈하는 하드 상한`, `동률 해소`, `보고만 하는 지표` 중 어느 역할인지 지표별로 고정한다. 서로 다른 단위의 비용을 사후 합성 점수로 만들지 않는 원칙은 유지한다.
6. 모델 변동성에 대한 최소 반복 규칙을 사전 동결한다. 권고 최소안은 서로 독립적으로 동결된 봉인 block을 둘 이상 사용하고, D 선택에 필요한 우위가 한 block의 단일 우연에만 의존하면 `비교 불충분`으로 두는 것이다. 단일 실행만 유지하면 결과를 구조 선택 근거가 아닌 예비 절차 점검으로 제한한다.

### P1-05. 봉인 oracle·scoring의 사전 독립 검토가 없고 판정자의 입력도 불완전하다 — 차단 결함

**확인 사실**

- §5와 §11에서 F0가 봉인 `input`, `oracle`, `scoring`을 모두 작성한다.
- J0는 네 실행 결과가 동결된 뒤 처음 `oracle`과 `scoring`을 받는다.
- §6의 J0 허용 입력에는 봉인 `input` 자체가 없다.
- J0는 한 명이며, 기준선이 요구한 판정자 불일치 처리의 발생·해결 절차가 없다.
- §7의 실행 기록과 §9.3의 관계 수·표현량을 J0가 함께 보면 실제 조건명을 지워도 D를 추정할 수 있다.

**판단**

F0가 의도치 않게 D 용어를 정답으로 만들거나 oracle을 모순되게 작성해도 결과 전에는 독립 검사가 없다. 결과 뒤 J0가 문항 무효 또는 재시험을 고르면 성과 분포를 본 상태에서 시험 정의를 바꾸게 된다. 봉인 input 없이 oracle만 대조하는 판정자는 잘못된 참조 ID, 누락된 원문 맥락, oracle의 자기모순을 충분히 감사할 수 없다. 비용·관계 메타데이터는 익명 조건을 추정하게 해 정확도 판정에 편향을 줄 수 있다.

**최소 수정**

1. 실행 전에 fresh J0 또는 별도 봉인 검토자가 `input + oracle + scoring + 각 해시`를 모두 받아 다음만 검증하게 한다: 내부 일관성, C1–C7 관찰 가능성, 표현 중립성, 오류 중복 계수, 정답 모순, 조건 비대칭.
2. 불일치가 있으면 실행 전에 F0로 되돌리고 새 판본·새 해시로 다시 검토한다. 승인된 해시 외의 scoring은 실행 후 사용할 수 없게 한다.
3. 같은 J0가 사전 검토와 사후 적용을 맡을 수는 있지만 실행·출제 대화는 받지 않고, 사전 승인 기록을 결과 전에 동결한다. 이 경우 실제 독립성 수준을 그대로 보고한다.
4. 사후 J0에도 봉인 input을 제공한다. 원문 사실과 출력 참조를 직접 대조할 수 있어야 한다.
5. 정확성 채점 단계에서는 조건명, 조건 고유 산출물, 관계 수, 시간, 출력 길이 등 조건을 드러내는 메타데이터를 숨긴다. 정확성 판정을 고정한 뒤 CONTROL이 조건을 복원해 비용·복잡도와 결정표를 기계적으로 결합한다.
6. 복수 판정자를 쓰지 않는다면 `판정자 간 일치`를 결과에서 제거하고 단일 판정 한계를 명시한다. 복수 판정자를 쓴다면 불일치의 재심 주체·우선 규칙·무효 조건을 결과 전에 고정한다.
7. 봉인 보유자, 실제 저장 위치 범주, 생성·해시·검토·공개 시각, 접근자, 전달 경로, 누출 판정자를 기록하는 sealed-access manifest를 필수 산출물로 추가한다. 해시와 저장소 밖 보관만으로 비밀성이 증명된다고 보지 않는다.

### P1-06. 무효·정답 결함·재시험 규칙에 결과 후 선택 여지가 남아 있다 — 차단 결함

**확인 사실**

- §7.1은 기술 실패 때 네 조건 전체를 새 run ID로 재실행하도록 하지만 전체 재시도 횟수 상한, 판정자, 같은 봉인 묶음 재사용 조건을 정하지 않는다.
- §10은 한 조건만 재시도하지 않는다는 중요한 원칙을 두지만, 무효 run의 보존·선택 순서를 정하지 않는다.
- 상위 운영안 단계 7과 현재 프로토콜의 판정 구조는 정답 모순 발견 시 `문항 무효`와 `전체 재시험` 사이의 선택을 남긴다.
- 누출과 판정 기준 변경은 전체 무효지만, 새 봉인 자료가 반드시 필요한 경우와 같은 자료를 다시 쓸 수 있는 경우가 분리되지 않았다.

**판단**

전체 묶음을 다시 돌린다는 것만으로 선택적 재실행이 사라지지 않는다. 기술 실패를 넓게 해석해 불리한 네 결과를 통째로 다시 뽑을 수 있고, 결과를 본 뒤 불리한 문항만 `정답 문제`로 제거할 수도 있다.

**최소 수정**

1. 기술 실패를 결과 의미와 무관하게 로그로 확인 가능한 사건으로 한정하고, 판정 권한과 전체 suite 재시도 최대 횟수를 run-manifest에 고정한다.
2. 재시도 결정은 가능하면 의미 결과를 열기 전에 내리고, 새 A–D fresh 세션을 모두 사용한다.
3. 모든 무효 run도 결과·로그·해시·무효 이유를 보존한다. 사전 규칙상 가장 이른 유효 run만 선택하며 여러 유효 run 중 유리한 것을 고르지 않는다.
4. 실행자가 봉인 입력을 봤거나 oracle·scoring·판정 기준에 결함이 있으면 새 봉인 판본과 전체 재시험을 요구한다. 단순 전송 실패가 봉인 입력 공개 전에 끝났을 때만 같은 묶음 재사용을 허용할 수 있다.
5. 주요 결과에 연결된 oracle/scoring 모순은 결과 뒤 개별 문항 삭제로 처리하지 않고 전체 run을 무효로 한다. 부수 문항 제외를 허용하려면 제외 가능 코드와 전체 조건에 동일하게 적용하는 규칙을 실행 전에 적는다.
6. 문턱·오류 코드·비용 역할·JSON 의미가 바뀌면 새 프로토콜, 새 scoring, 새 run으로 취급하고 구판 결과와 합쳐 선택하지 않는다.

## 5. v0.2의 최소 재비평 수락 조건

다음은 기능 추가 요구가 아니라, 현재 시험을 판정 가능하게 만드는 최소 통제다.

1. 시험 대상과 조건별 실험 처치가 관찰 가능한 산출물로 정의돼 있다.
2. 공통 중립 답안과 조건 고유 정리 산출물이 분리되고, 비공개 추론을 채점하지 않는다.
3. 공통 JSON에서 D 전용 명칭·고정 정답·자기보고 계측을 제거하고 실제 JSON Schema를 동결한다.
4. 공통 입력, 조건 overlay, corpus 규모, 모델·권한·시간·출력 기회와 사용자 승인 자원 상한을 별도 해시로 고정한다.
5. C1–C7과 코드화된 중대 오류가 입력 사실→관찰 필드→단일 계수 규칙으로 연결된다.
6. H0/H1, 모든 동률·교차 우위·전원 실패·비용 초과를 하나의 결과로 보내는 결정표와 최소 반복 규칙이 있다.
7. 봉인 input·oracle·scoring을 실행 전에 독립 검토하고, 동일 해시만 사후 판정에 사용한다.
8. J0의 봉인 input 접근, 정확성 우선 블라인드 채점, 조건 복원 뒤 비용 결합 순서가 명시돼 있다.
9. 기술 실패, 누출, oracle 결함, 문턱 변경별로 같은 봉인 묶음 재사용 여부·전체 재시험·최대 횟수·유효 run 선택 규칙이 고정돼 있다.
10. 실제 자료·실제 권한·실제 Project Brain·효과·브랜드 금지 문구가 그대로 유지된다.

v0.2 재비평에는 수정 프로토콜과 변경 장부·SHA-256만 있으면 된다. 이 재비평을 위해 fixture, oracle, 구현 또는 실행 결과를 만들 필요가 없다.

## 6. 프로토콜 수정으로 통과시킬 수 없는 항목

다음은 위 결함을 문서로 고친 뒤 실제 분리 실행에서만 확인할 수 있다.

- A–D가 실제로 같은 모델 표시·권한·원천 corpus·시간·출력 기회를 받았는지
- 실행 세션이 fresh였고 다른 조건 결과·oracle·scoring을 보지 않았는지
- 봉인 자료의 생성·보관·공개 순서와 접근 기록이 실제로 지켜졌는지
- 공개 예제 맞춤이 독립 봉인 block에서 발견되는지
- 판정자가 익명 상태에서 같은 rubric을 일관되게 적용하는지
- 각 조건의 C1–C7, 중대 오류, 객관 비용과 모델 출력 변동성
- D가 단순 조건보다 반복적으로 오류를 줄이는지 또는 H0가 유지되는지
- 결과 뒤 문턱 변경·선택적 재시도·유리한 run 선택이 실제로 없었는지

다음은 S0로도 알 수 없고 기존 후기 관문에 그대로 남는다.

- 실제 자료의 대표성·권리·보안·재식별·삭제·복구
- 실제 Project Brain 통합과 책임 경계의 운영 적합성
- 실제 품질·비용·안전·경제성·모델 간 전이
- 다중 프로젝트·복수 자산·승인 피로·장기 운영
- 내부·외부 브랜드 효과와 대외 주장 적합성

## 7. 최종 결론

현재 v0.1은 실제 단계 관문을 닫는 데는 성공했지만, A–D를 공정하고 반증 가능하게 구별하는 시험 규칙은 아직 동결 가능하지 않다. 특히 조건 차이의 관찰 가능성, 표현 중립 출력, oracle/scoring 사전 독립 검토, 완전한 선택·비용·재시험 규칙을 먼저 고쳐야 한다.
