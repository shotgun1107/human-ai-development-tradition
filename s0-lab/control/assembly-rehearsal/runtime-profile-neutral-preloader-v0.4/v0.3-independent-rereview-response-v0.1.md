## 2. Finding dispositions

### RPNP3-RR-001 — accepted and corrected in design

v0.4 removes the unobservable claim from the native guard. Responsibility is
now explicit:

- the authenticated preloader constructs the sole ordered five-handle
  `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, excludes opposite ends and unrelated
  handles, fixes `STARTUPINFOEXW`, flags, size, count, and `CreateProcessW`
  inputs, and produces canonical launch evidence;
- the pinned Windows kernel applies that exact list under the documented API
  contract;
- future source/binary review proves what the preloader constructed;
- a separately gated real-Windows decoy probe proves that omitted inheritable
  handles and opposite ends are unusable on each admitted build; and
- the guard validates only the five known live handles and explicitly makes no
  verifier-wide enumeration or unknown-handle-absence claim.

This is the smallest correction because the original guard call surface can
inspect a known handle but cannot discover an arbitrary unknown sixth value.
No undocumented enumeration API or new authority root is invented.

### RPNP3-RR-002 — accepted and corrected in design

The v0.4 schema is a closed supplement that requires all design-promised
groups:

- v0.1/v0.2/v0.3 profile pins and exact five-row package closure;
- runtime-files manifest and exact package row order;
- platform and loaded-PE manifests;
- kernel32 and ntdll path/hash/file/PE/export identities;
- guard source, build recipe, compiler, linker, import and CRT-import
  manifests, binary, loaded-image identity, initialization symbol, direct
  import policy, semantic calls, and PDB disposition;
- process-creation API, flags, attribute-list shape, exact five role/kind/access
  triples, standard/opposite-handle policy, and responsibility allocation;
- launch evidence, postcreation admission binding, and locator policies;
- complete atomic-root ABI, postcondition, retention, same-object duplicate,
  no-reopen/no-second-create, and residue policies;
- terminal-state rules; and
- ten exact cross-object semantic relations plus the separately authenticated
  validator identity required to execute them.

The acceptance plan requires one valid placeholder construction, exhaustive
recursive required-property deletion, fixed-value/order/weakening mutations,
unknown-property rejection at every depth, and one negative case for every
semantic relation. Schema validity remains construction evidence only.

## 3. Nonregression disposition

v0.4 does not replace the v0.3 atomic root or terminal corrections.
`RPNP2-RR-002` and `RPNP2-RR-003` remain closed at design level. The v0.3
locator mechanism and known-handle validation remain, while the unobservable
portion of `RPNP2-RR-001` is reassigned to the correct components and future
evidence.

The effective trust roots remain the externally authenticated CONTROL launcher
and pinned Windows kernel. The authenticated preloader and guard are measured
components inside that closure, not new external roots. No environment,
numeric locator, admission-frame value, Python object, reviewer statement, or
Microsoft web page is authority by itself.
